Document behavior that exists in the source. Keep proposals, implementation plans,
and release coordination in GitHub issues and pull requests. Historical releases
belong in release notes, not in the current setup or API reference.

| Content | Location |
| --- | --- |
| A task users can perform | `docs/guides/` |
| Agent lifecycle and tool contracts | `docs/sdk/core/` |
| Reusable SDKs | `docs/sdk/` |
| Detailed implemented component contracts | `docs/spec/` |
| Commands, development, and troubleshooting | `docs/reference/` |
| Version-specific changes | `docs/releases/` |

## Before editing

Read the implementation and its tests. Check the command's actual `--help`,
constructor signature, return shape, and defaults. Distinguish the Python CLI,
the Go TUI, the flagship subprocess, and daemon-backed sidecars. Their flags,
permissions, and state lifetimes differ.

Maintain one canonical explanation of each contract. Link to it from guides
instead of copying signatures, model lists, installation matrices, or tool counts.
When removing a page, update inbound links and navigation; add a redirect only
when there is a useful maintained replacement. Git history preserves retired plans.

## Validate

New pages use MDX frontmatter (`title`, `description`, `icon`) and must appear in
`docs/docs.json`. Link to implementation files from technical references.

From the repository root:

```bash
python util/check_doc_links.py --internal-only
python util/check_doc_code.py
python util/check_doc_versions.py
```

From `docs/`, validate Mintlify:

```bash
mintlify broken-links
```

Run changed examples where their dependencies are available, and run the existing
tests that exercise documented contracts. Syntax compilation alone does not prove
an example can import or execute. Report service-dependent checks that were not run.
