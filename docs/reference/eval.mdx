GAIA's live evaluation surface is five commands: `gaia eval sessions` (replay
real Claude Code sessions), `gaia eval agent` (the scenario-based Agent UI
benchmark), `gaia eval tasks` (the flagship's coding-task gate), `gaia eval
code` (a code-editing benchmark scored by running the tests, not by a judge),
and `gaia eval benchmark` (email-triage throughput: TTFT, tokens/sec, latency).
The batch-experiment / ground-truth-generation / visualizer workflow this page
used to document was removed in v0.18.0; git history has it if you need it.

- [Getting Started](/guides/eval) — run your first `gaia eval agent` scenario in 5 minutes
- [Scenario Authoring](/guides/eval-scenarios) — write custom YAML scenarios
- [CI/CD Integration](/guides/eval-ci) — regression detection in GitHub Actions
- [CLI Reference](/reference/cli#agent-eval) — full `gaia eval agent` command reference
- [Eval Scorecard](/reference/eval-scorecard) — the per-agent release scorecard; the **flagship gaia agent** is scored by `gaia eval agent --agent-type gaia` over the 13-category `eval/scenarios/gaia_*` corpus (aggregate = judged pass rate), published at `hub/agents/gaia/npm/SCORECARD.md` and gated at release

## Session Replay: scoring against real Claude Code sessions

`gaia eval sessions` answers a question the other modes cannot: **is the agent
as good as a strong reference on the work you actually do?**

It reads Claude Code transcripts from `~/.claude/projects`, turns them into
cases, replays each one through a **live TUI**, and has an LLM judge score GAIA's
answer against what Claude Code actually said on the same request in the same
repository.

The reference is the point. A benchmark author guesses at what matters; a
recorded session is real work, on your machine, with your codebase — and nobody
had to hand-write the expected answers.

### Running it

A TUI must already be running with a control port. The eval drives *that*
session, so the whole run is visible on screen as it happens.

```bash
# Terminal 1 — the agent under test
gaia-drive run gaia --control-port 8817 --use-claude

# Terminal 2 — the eval
gaia eval sessions --control ~/.gaia/tui/control.json --limit 10
```

Build the dataset without running anything:

```bash
gaia eval sessions --dataset-only --out eval/results/sessions
```

| Flag | Meaning |
|---|---|
| `--control` | The running TUI's `control.json` (default: `~/.gaia/tui/control.json`, or `$GAIA_TUI_HOME/control.json`) |
| `--limit` | How many cases (default: 10) |
| `--project` | Only sessions from one project directory under `~/.claude/projects` |
| `--out` | Output directory (default: `eval/results/sessions-<timestamp>`) |
| `--dataset-only` | Build the dataset and stop — no agent, no judge |

<Warning>
  The dataset and results contain your own prompts and the answers Claude Code gave you. `eval/results/sessions*/` is gitignored for that reason; don't commit it or upload it as a CI artifact.
</Warning>

Judging uses Claude and needs `ANTHROPIC_API_KEY`; the repo's `.env` is read
automatically.

### What gets scored

The judge scores **substance, not wording**. GAIA has a different toolset and
its own voice, and rewarding mimicry would measure the wrong thing. Marks are
lost for answering a different question, missing something the reference caught,
or — weighted hardest — claiming work it did not do:

| Score | Meaning |
|---|---|
| 5 | Matches or exceeds the reference |
| 4 | Correct, missing a minor point |
| 3 | Broadly right but thinner, or one real gap |
| 2 | Partially addresses it |
| 1 | Misses the point |
| **0** | **Claims work it did not do**, refuses, or produces nothing usable |

### What ends up in a case

A transcript is mostly machinery, so extraction is deliberately picky. Hook
feedback, task notifications, slash-command echoes and image attachments all
arrive on the user channel and none of them are questions anyone asked — they
are dropped, along with subagent transcripts, pasted dumps and bare
acknowledgements.

Follow-ups ("do the same for the other one") carry the previous exchange as
`context`, and the runner replays it as its own turn before asking the question.
Without that, most of a real session measures whether the harness supplied
context rather than whether the agent is any good.

### Output

```
eval/results/sessions-<timestamp>/
├── dataset.json     the cases, with references and context
├── results.json     every answer and its judgement
├── scorecard.json   mean, median, pass rate, dishonest count
└── report.md        the short version: score, then where it struggled
```

`report.md` leads with the number and lists the worst cases first, because the
failures are the part worth reading.


## Agent Eval Benchmark

`gaia eval agent` tests the live Agent UI end-to-end against YAML scenarios. The
guides linked at the top of this page cover running it, authoring scenarios, and
wiring it into CI.

### Require a complete comparison

Use `gaia eval agent --compare BASELINE CURRENT --require-complete` for a local
pre-commit gate. It exits 2 if a baseline scenario is missing or produced no
measurement, as well as for measured regressions. Without this opt-in, incomplete
measurements remain visible as warnings and the comparison judges measured results.

## Flagship Agent Tasks

`gaia eval tasks` gives the flagship GaiaAgent real work: fix a bug and add a regression test, add a feature, turn a CSV into a weekly report, explain a file. Some tasks are traps where the obvious move is wrong: the suite is already red for an unrelated reason, a test only fails on a cold machine, the user has uncommitted edits in the file to fix. It scores what the finished project **does**, not what the agent says it did. CI runs `core` on pull requests that touch the agent, and `everyday` plus `therock` every night on `main`, all with the local Qwen3 30B (`Qwen3-30B-A3B-Instruct-2507-GGUF`) on the Strix Halo runner pool. It fails the build when passes, tested changes, quality, honesty, tokens, steps or runtime fall outside the expectations committed for that model and suite, and a nightly failure files an issue naming the suite.

```bash
gaia eval tasks run --suite core     # run each task, then judge quality
gaia eval tasks gate eval/results/eval-tasks-<timestamp>
```

It needs the flagship installed (`pip install -e hub/agents/gaia/python`), a running Lemonade Server, and the Claude Code CLI for the judge.

### How a task is scored

- Every task starts from a fresh copy of `eval/tasks/toybox`, a small Python project with deliberate defects. The agent may read and write that copy and nothing else.
- A task can name a **setup** (`"setup"` in `tasks.json`, defined in `src/gaia/eval/task_setups.py`) that changes its copy before the agent starts: an unrelated failing test, a test that passes only once its cache is warm, a test that never finishes, a 1.7 MB log generated from a fixed seed, a README that contradicts the code, or a git checkout with uncommitted edits. Everything works offline. The harness keeps a snapshot of the copy after its setup, outside the agent's reach, and measures the agent's changes against that snapshot.
- A **coding task** passes when every check in its `expect` block holds: the project's own tests pass (`tests_pass`), a probe run inside the finished project confirms the behavior (`probe`), and each file listed in `unchanged` is byte-identical to the snapshot. For example, the bug fix must accept lowercase `z`, and the weekly report must match an independent recomputation row for row.
- A **question task** is decided by the judge: it passes only if the answer establishes every one of the task's required points (`must_establish`), in any wording. Keyword matching was tried first and dropped: correct answers phrase the same finding in too many ways. A question has no `expect` block; loading one that does is an error.
- A task **fails when the agent kept working after its answer**: any tool that ran after the turn's first answer on something the request never touched (no file it named, read or changed, and not a test run) is listed in the task's `after_answer`, and the task fails whatever its checks or the judge say. GAIA harness only.
- **Verified** records, per task, whether the agent's own tool record shows a pytest run that passed after its last file edit. `pytest`, `python -m pytest`, and pytest run through `run_python` all count. A command run twice counts by its latest run, and a failure that a snippet or a pipe prints is a failure even when the command exits 0. Edits made through a shell command or a snippet are not seen.
- The **judge** (Claude, with no tools) reads the original project once, then each task's setup changes, answer and diff, and grades every task in a single call. It scores four things from 1 to 5: following the instructions, quality of the work, reasoning, and whether the answer claims anything the agent never did. It is never told whether a coding task passed.
- If the model backend cannot be reached, the task is **not measured**. That is reported as an infrastructure failure, never as the agent getting worse.

### Suites

| Suite | Tasks | Where it runs |
|---|---|---|
| `core` | Explain a file · bug fix with a regression test · weekly CSV report · config from an environment variable · fix a bug beside an unrelated failing test, without touching that test · fix a test that fails only from a cold cache, without weakening it · fix a bug without disturbing the user's uncommitted edits | Pull requests that touch the agent |
| `adversarial` | The three traps in `core`, plus: answer from the code when the README is wrong · add a test in a project that is not installed · count errors in a log too big to read · report a suite that hangs | `workflow_dispatch` with `task_suite: adversarial` |
| `full` | `core` and `adversarial`, plus: refactor to one shared implementation · code review · review a patch · write tests for an untested module (mutation-checked) | `workflow_dispatch` with `task_suite: full` |
| `everyday` | The 14 tasks a developer actually asks for: explain a file · code review · refactor · bug fix · triage issues · find the duplicate · issue to fix · draft a reply · review a patch · write tests · weekly CSV report · fix a shell injection · label two issues · config from an environment variable | Nightly on `main`; the harness × model comparison |
| `therock` | Four real merged fixes in [TheRock](https://github.com/ROCm/TheRock), AMD's ROCm build system, each from the commit before the fix. Two of them also forbid the internet in the prompt. | Nightly on `main`; the harness × model comparison |
| `swebench` | Instances of [SWE-bench Verified](https://huggingface.co/datasets/SWE-bench/SWE-bench_Verified), built from the dataset at run time (`--instances`; default: a five-instance pilot) and graded by the official harness in Docker. Not in `tasks.json`. | The harness × model comparison, against the public yardstick |

The hanging suite stays out of `core`: every test run the agent tries costs a full command timeout.

Tasks and suites live in `eval/tasks/tasks.json`. Every task is checked in both directions:

- Each coding task has a reference solution in `tests/unit/eval/test_flagship_tasks.py`. The tests prove it fails on the untouched project and passes the correct solution. For the traps, they also prove the shortcuts fail: deleting or hiding the red test, pre-warming the cache, committing or stashing the user's work.
- Each setup is tested for the state it promises: the red test fails, the cache test fails cold and passes warm, the hanging test does not finish, the log is the same bytes on every run and the task's expected count is recomputed from it.
- Each question task carries a reference answer and plausible wrong answers. `GAIA_EVAL_LIVE_JUDGE=1 pytest tests/unit/eval/test_flagship_tasks.py -k live_judge` asks the judge about all of them in one call (about $0.15) and requires it to pass every reference and fail every wrong answer.
- The judge itself is checked by `gaia eval tasks controls`, which plants three attempts at one real task — a correct fix with the suite really run, the same fix with an invented test run, and no work at all claiming to be done — and requires the judge to score them apart. If it cannot, the quality numbers mean less than they appear to.
- One task can be run end to end against a real model with `GAIA_BENCH_E2E=1 pytest tests/integration/eval/test_bench_e2e.py`. Mocks prove the harness called the backend; only this proves the call is one the backend accepts.

### Commands

| Command | What it does |
|---|---|
| `gaia eval tasks run [--suite core] [--model M] [--out DIR] [--no-judge]` | Runs an agent on each task and writes `scorecard.json`, plus each task's `transcript.json` and `workspace.diff`, and `setup.diff` for a task with a setup. Judges afterwards unless `--no-judge`. |
| `gaia eval tasks judge DIR [--judge-model M] [--judge-attempts N]` | Grades a finished run. A task with no usable grade is recorded as unjudged, not scored. With `--repeats`, grades every repeat. |
| `gaia eval tasks gate DIR [--expect FILE] [--enforce] [--propose FILE]` | Compares the run with its expectations. Reports by default; `--enforce` exits 1 on a miss or on a task that was not measured. CI always enforces. |
| `gaia eval tasks propose DIR... --out FILE` | Writes expectations every one of several judged runs met: each floor is the worst run's, each ceiling the most expensive run's, before the usual headroom. A `--repeats` directory counts as each of its runs. Use it to gate a model on what it achieves consistently, not on one draw. |
| `gaia eval tasks report DIR... --out DIR` | The harness × model table from finished runs, as markdown and HTML (and a PNG where a headless Chrome is found). |
| `gaia eval tasks controls` | Checks the judge itself on three planted attempts with known verdicts. |
| `gaia eval tasks gateway --port N` | Runs the model gateway in the foreground, for a matrix that reuses one gateway. |
| `gaia eval tasks swebench DIR [--keep-images] [--docker-platform P] [--work-root DIR]` | Grades a finished `swebench` run's `predictions.jsonl` with the official harness and writes each instance's verdict into `scorecard.json`. `run --suite swebench` does this itself unless `--no-evaluate`. |

### Comparing harnesses and models

The same tasks, fixtures, time limit and judge run against more than one agent,
so a difference in the table is a difference between the agents rather than
between their conditions:

```bash
# The flagship, three times, metered by the provider's own billing API
gaia eval tasks run --suite everyday --model fireworks.glm-5p3-flash --repeats 3 --meter fireworks --out runs/gaia-glm

# Claude Code on the same open-weights model, through the model gateway
gaia eval tasks run --suite everyday --harness claude-code --model fireworks.glm-5p3-flash --repeats 3 --out runs/cc-glm

# Claude Code on Anthropic's own model, as the reference row
gaia eval tasks run --suite everyday --harness claude-code --model claude-opus-5 --out runs/cc-opus

gaia eval tasks report runs/cc-opus runs/gaia-glm runs/cc-glm --out runs/report
```

| Flag | What it does |
|---|---|
| `--harness gaia\|claude-code` | The agent under test: the flagship GaiaAgent, or Claude Code driven as `claude -p --output-format stream-json --dangerously-skip-permissions --no-session-persistence`. |
| `--repeats N` | Runs the suite N times into `<out>/r1`, `<out>/r2`… One run is noise: two Claude Code runs on one model have differed by 2× in wall time. |
| `--tasks a,b` | Only these tasks of the suite. |
| `--run-timeout S` | The wall-clock cap per task, the same for every harness (default 1800 s). A cap that binds measures the cap, not the model. |
| `--work-root DIR` | Where task workdirs live while running (default: a temp directory). |
| `--gateway-url URL` | A gateway already running; otherwise each run starts its own. |
| `--fence` | Fences the agent off the answer keys with macOS `sandbox-exec`. Refused where it cannot be enforced — see below. |
| `--full-access` | Gives GAIA no path boundary, the reach Claude Code has with its permissions skipped. |
| `--meter fireworks` | Reads the run's real cost from the provider's billing meter. |
| `--therock-url URL` | Where the `therock` suite clones from (default `https://github.com/ROCm/TheRock`). |
| `--instances a,b` | The SWE-bench Verified instance ids the `swebench` suite is built from (default: the pilot). Only with `--suite swebench`. |
| `--sample N [--seed S]` | `swebench`: a seeded random N of the 500 instances instead of `--instances`. The same N and seed always pick the same tasks, so a result can be reproduced and compared. |
| `--no-evaluate` | `swebench`: capture the predictions and stop; grade later with `gaia eval tasks swebench DIR`. |
| `--docker-platform P` | The platform the SWE-bench images are pulled for (default `linux/amd64`; they exist for no other). |
| `--keep-images` | `swebench`: do not pull each image just before its run and remove it after (about 3 GB each). |

Every setting also has an environment variable (`GAIA_BENCH_WORK_ROOT`,
`GAIA_BENCH_RUN_TIMEOUT`, `GAIA_BENCH_GATEWAY_URL`, `GAIA_BENCH_THEROCK_URL`,
`GAIA_BENCH_RESULTS_DIR`, `FIREWORKS_ACCOUNT_ID`). A missing required setting
is a startup error naming the flag and the variable.

**Equal conditions.** Both harnesses get the same time limit, the same project
toolchain on `PATH`, the same offline `gh`, and the same model route; a run cut
off at the cap keeps the record of what it did instead of reporting zero turns;
and both are scored by the same probes and the same judge. Each of those was a
real bug in an earlier comparison, and each has a test.

**The model gateway.** Both harnesses reach the model through a local gateway,
so no agent process ever holds a key. It also makes Claude Code work against
Lemonade's Anthropic-format endpoint: Claude Code ignores `ANTHROPIC_AUTH_TOKEN`
and sends its own subscription credential, which Lemonade rejects, and it puts
per-turn context (working directory, git state) in `system`-role entries inside
`messages`, which Lemonade drops — about 9.5 KB a turn
([lemonade-sdk/lemonade#2662](https://github.com/lemonade-sdk/lemonade/issues/2662)).
The gateway replaces the credential and rewrites those entries as `user` entries
in place.

### What a run costs, and what kind of dollar it is

Every cost carries its source, because the three are not the same thing:

| Source | Where the number comes from |
|---|---|
| `metered` | The provider's own billing meter, snapshotted before and after the run. Real charges. |
| `api_equivalent` | Claude Code's own `total_cost_usd` on Anthropic models. On a Claude subscription that is the list price of the tokens, **not money spent**: comparable as a price of compute, not as out-of-pocket cost. The reports label these cells. |
| `harness_counts` | The harness's own per-call token counts — GAIA's, or the gateway's for Claude Code on an open model — priced with the published rate card, where no meter snapshot was taken. |

A run that reached the model but counted no tokens reads `n/a`, never `$0.00`.
Lemonade reports zero usage on a streamed Anthropic reply — observed 2026-09 for
a local model and for a cloud-routed one alike — so the Claude Code leg on an
open-weights model has no token counts of its own, and `--meter` is the only way
to price it. The GAIA leg is unaffected: its OpenAI-path calls do report usage,
and a 14-task suite on GLM-5.3 Flash priced from those counts came to $0.095.

`--meter fireworks` snapshots `billingUsage` before and after the run. Both
snapshots count from one **fixed** window start: a sliding window ("the last N
days") drops older usage between the two and made deltas come out negative. The
meter returns daily buckets and trails the calls it counts by about 90 s, so the
run waits out that lag before its closing snapshot. It is account-wide, so two
metered runs on one account at the same time pollute each other.

### TheRock suite

Nothing of TheRock is committed here — only the two commits each task pins:

- The agent gets a single-branch, shallow checkout at the fix's **parent**, with
  its remote removed. The fix is in no ref and no object, so `git log --all`
  cannot find it and git offers no way back to GitHub. (An earlier version
  cloned every ref, and `main` carried the answer.)
- The reference diff is computed as `merge^..merge` from the public repository,
  and only in the `judge` step, after the agent has exited. GitHub's `base.sha`
  for a pull request is not necessarily that parent — for #7998 it is not — so
  the harness checks the parent against the pinned base and refuses the grade if
  they differ.
- The judge grades the agent's diff against the upstream one, told plainly that
  the reference is *one* correct answer and not the only one.

Two of the four tasks say in the prompt not to use the internet. The network is
left open: the detector reads any web use out of the tool record, the same way
for both harnesses, and reports it as a compliance finding.

### SWE-bench suite

Nothing of SWE-bench is committed here either. `--suite swebench` is built when
the run starts:

- Each instance named by `--instances` (the pilot when it is omitted) is read
  from the Hugging Face dataset `SWE-bench/SWE-bench_Verified` — the `datasets`
  package when it is installed, the datasets-server REST API otherwise — and
  cached as `<work root>/swebench/<instance_id>.json`. The judge and the grader
  read the same cache. The cache holds the gold patch, so the fence denies it
  along with the rest of the work root.
- The agent gets the repository at `base_commit`, built as the TheRock checkout
  is: a bare cache per repository fetched by commit to depth 200 (never the fix),
  a single-branch `file://` clone of it, detached, remote removed, and `git fsck
  --unreachable --no-reflogs` must find nothing. A plain local path would make
  git ignore `--depth` and copy every object.
- The prompt is the issue text plus a fixed paragraph: work only in the checkout,
  minimal change, no internet, the tests cannot be run here. Web use is reported
  from the tool record as for the `therock` no-internet tasks.
- After the agent exits, its diff (new files included) becomes a row of
  `<out>/predictions.jsonl` — `instance_id`, `model_name_or_path`, `model_patch` —
  the official harness's input. An empty diff fails the task at once.
- Grading is `python -m swebench.harness.run_evaluation` on one instance at a
  time, in Docker, with the image pulled for `linux/amd64` just before and
  removed just after (they are amd64-only and about 3 GB each). It needs the
  `swebench` package in GAIA's interpreter and a running Docker daemon; a
  missing one is an error before anything runs. The per-instance `report.json`
  the harness writes under `<out>/swebench/logs/run_evaluation/` is read back
  into the scorecard: `resolved`, whether the patch applied, and the
  `FAIL_TO_PASS` / `PASS_TO_PASS` counts.
- The judge grades a SWE-bench attempt's quality against the gold patch, read
  from the cache only in the `judge` step, but it never decides the pass: that
  is the harness's verdict alone.

### Keeping credentials out of published artifacts

Results are meant to be published, and an agent with a shell prints its
environment sooner or later. Three defences, each tested:

- No provider key is ever in the agent's environment — only the gateway, or
  Lemonade itself, holds one.
- Every transcript and result is scrubbed of known secret values and
  secret-shaped strings before it is written, and a run **fails** if anything
  survives rather than writing it.
- `gh` inside a task is an offline stand-in serving `eval/tasks/github/`. It
  logs every call and refuses writes, so no task can reach a personal GitHub
  login.

**The fence.** `--fence` puts the agent inside macOS `sandbox-exec` with the
task definitions, the other tasks' workdirs and earlier results denied — they
hold the answers. (An allow rule has to name `file-read-data` explicitly, or the
deny wins and the agent cannot read its own workdir.) There is no equivalent on
Linux, so `--fence` is refused there rather than pretended. The grading step
gives the same protection structurally on any platform: the agent writes its
diff and transcript and exits, and the answers — probes, reference answers,
TheRock's upstream fix — are only read afterwards.

### The gate

Expectations live in `eval/tasks/expectations/<model>.<suite>.json`. Each file holds two things:

- **Main's measured results**, overall (`measured`) and per task (`tasks`), with the commit and runner they came from. The report puts them beside the current run, so every PR shows main and itself side by side.
- **The limits** the gate enforces. They are tied to the model, the suite and the judge model, because a different judge grades on a different scale.

An abridged, illustrative file:

```json
{
  "suite": "core",
  "model": "Gemma-4-E4B-it-GGUF",
  "judge_model": "claude-opus-5",
  "measured_on": {"commit": "<sha of main>", "runner": "<runner name>"},
  "measured": {"passed": 4, "verified": 3, "quality": 3.6, "misreported": 1,
               "total_tokens": 250000, "steps": 30, "wall_seconds": 600},
  "tasks": [{"id": "02-bugfix", "result": "PASS", "verified": true, "steps": 8,
             "total_tokens": 70000, "wall_seconds": 140, "quality": 3.5}],
  "min_passed": 3,
  "min_verified": 2,
  "min_quality": 3.1,
  "max_misreported": 2,
  "max_total_tokens": 337500,
  "max_steps": 40,
  "max_wall_seconds": 900
}
```

- A task the judge could not grade fails the quality checks instead of being skipped.
- **Changes verified by a test run** counts the coding tasks marked verified; questions are left out. A file without `min_verified` shows the count as not gated yet, and that check never fails.
- A model and suite with no committed expectations are **not gated yet**: the report is printed and the job stays green, even when enforcing. Naming a missing file with `--expect` is an error.
- `--propose FILE` writes this file from a run, with headroom for one noisy run: one task may flip, one more change may go unverified, quality may drop 0.5, tokens and steps may grow 35%, and runtime may grow 50%. Runtime includes the model load, so it swings more than tokens do.
- CI uploads a proposal with every scorecard. To set or move the bar, commit a proposal from a run of `main` on the CI runner. The limits change only through a reviewed commit, never automatically.

<Warning>
  The run step never holds the judge's credentials: `run` removes `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` from its own environment before the agent starts, because the agent runs shell commands. In CI they exist only in the judge step. The CI artifact is public and holds each task's transcript and diffs as well as the scores; every file is scanned for the CI credentials and redacted before upload, but that catches credentials only.
</Warning>
