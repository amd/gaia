## Installation Issues

<AccordionGroup>
  <Accordion title="Installer fails or hangs" icon="circle-exclamation">
    **Generate detailed logs:**
    ```powershell
    gaia-windows-setup.exe /LOG=install_log.txt
    ```

    **Common causes:**
    - **Hardware Compatibility**: The installer detects available hardware capabilities
    - **Driver Incompatibility**: For Ryzen AI systems, ensure you have compatible NPU drivers
    - **PATH issues**: If the installer can't update your PATH, a warning will be displayed

    If PATH update fails, add GAIA directories to PATH manually.
  </Accordion>

  <Accordion title="uv not recognized after install" icon="terminal">
    Restart your terminal, or manually add to PATH:

    **Windows (PowerShell):**
    ```powershell
    $env:Path = "$env:USERPROFILE\.local\bin;$env:Path"
    ```

    **Linux:**
    ```bash
    source ~/.bashrc
    ```
  </Accordion>

  <Accordion title="PowerShell script execution error" icon="ban">
    Run this once to allow script execution:
    ```powershell
    Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
    ```
    Then retry the activation command.
  </Accordion>

  <Accordion title="CERTIFICATE_VERIFY_FAILED on a corporate network" icon="shield-halved">
    GAIA verifies HTTPS against your operating system's certificate store, the same one
    your browser and pip use, so a TLS-inspecting proxy (Zscaler and similar) works
    without extra setup as long as its root certificate is installed in the OS store.

    If GAIA still fails with `CERTIFICATE_VERIFY_FAILED`:

    - **A warning says GAIA "could not switch HTTPS verification to the system
      certificate store"** — the `truststore` package is missing or broken. Run
      `pip install --upgrade "truststore>=0.10.0"` in GAIA's environment. The warning
      appears in the terminal, or in `gaia daemon logs` (add `--agent <id>` for an
      agent's own requests).
    - **No such warning in either place** — the proxy's root certificate is not in the OS
      store. Ask IT to install it there; opening the failing URL in a browser on the same
      machine tells you whether the OS trusts it.
  </Accordion>

  <Accordion title="Python version issues" icon="python">
    GAIA requires Python 3.10-3.12. If `uv venv` fails:
    ```bash
    # Specify Python version explicitly
    uv venv .venv --python 3.12
    ```
    uv will automatically download Python if not installed.
  </Accordion>

  <Accordion title="Lemonade install fails with 404 errors (Linux)" icon="download">
    If `gaia init` fails with 404 Not Found errors when installing dependencies:

    **Cause:** Your apt package cache is stale. Ubuntu repositories are updated frequently, and old package versions get removed.

    **Solution:** Update your package cache first:
    ```bash
    sudo apt update
    gaia init --profile minimal
    ```

    **Example error:**
    ```
    E: Failed to fetch http://archive.ubuntu.com/ubuntu/pool/... 404 Not Found
    E: Unable to fetch some archives, maybe run apt-get update or try with --fix-missing?
    ```

    The GAIA installer now runs `apt update` automatically, but you may need to run it manually if you see these errors.
  </Accordion>

  <Accordion title="gaia init fails with a Node.js version error (dev/source installs)" icon="node-js">
    **Cause:** `gaia init` builds the Agent UI frontend from source, which requires a
    minimum Node.js version. If the `node` on your `PATH` is older than that, `gaia init`
    now fails with an actionable error naming the required version, the version found, and
    the exact `node` path in use — instead of silently reporting success with a broken UI.

    **Solution:** Install or switch to a newer Node.js. If you already have one installed
    via nvm/fnm/volta, make sure it comes first on `PATH` — a system-installed Node can
    shadow it in non-interactive shells (e.g. `ssh host 'gaia init'`).

    **Workaround:** To skip the Agent UI frontend build entirely (the CLI still works),
    pass `--skip-webui-build` or set `GAIA_SKIP_WEBUI_BUILD=1`.
  </Accordion>

  <Accordion title="GAIA runs a second Lemonade next to mine" icon="clone">
    GAIA runs its own private Lemonade Server unless you tell it to use yours, so a
    PC that already runs Lemonade can end up with two servers and two copies of each
    model. Point GAIA at yours with `gaia lemonade connect http://localhost:13305`, or
    in the Agent UI under **Settings → Advanced → Model server**. Switching stops
    GAIA's own server. See
    [Use a Lemonade you already run](/guides/install#use-a-lemonade-you-already-run).
  </Accordion>

  <Accordion title="Connecting a cloud provider fails while GAIA uses my Lemonade" icon="plug-circle-xmark">
    While GAIA uses a Lemonade you run, it never changes that server's setup, so it
    won't register Fireworks AI or the AMD LLM Gateway there or hand it a key. The
    error says your server has no working provider. Set the provider up on your
    server yourself, with its key (`LEMONADE_FIREWORKS_API_KEY` or
    `LEMONADE_AMD_API_KEY`) in your server's environment, then connect again. Or go
    back to GAIA's own server with `gaia config set lemonade_mode gaia`.
  </Accordion>

  <Accordion title="Use GAIA's own says GAIA's server is not installed" icon="box-open">
    Switching back from your Lemonade needs GAIA's own server, and on this PC it was
    never installed (or only partly). The switch is refused and GAIA keeps using
    yours. Run `gaia init --gaia-lemonade` to install GAIA's own and switch in one
    step.
  </Accordion>

  <Accordion title="gaia init can't download or start Lemonade Server" icon="cloud-slash">
    `gaia init` downloads GAIA's own Lemonade Server from GitHub into `~/.gaia/lemonade`
    and starts it on a private port. It needs no admin rights and never uses a package
    manager. The error names which part failed:

    - **`Failed to download …` / `dropped mid-transfer`** — GAIA could not reach
      `github.com`. Check your network or proxy and re-run `gaia init`.
    - **`Checksum mismatch …`** — the download was corrupted. Re-run `gaia init`; if it
      keeps happening, the release asset changed and GAIA needs an update.
    - **`not published for <OS>/<arch>`** — there is no Lemonade build for this machine
      (for example, Intel Macs). Run Lemonade Server on another machine and point GAIA at
      it with `LEMONADE_BASE_URL`.
    - **`exited immediately` / `did not answer`** — the server started but failed. Its own
      error is in `~/.gaia/lemonade/lemond.log`.
    - **`could not bind port …: it was taken by another program first`** — another
      program took each port GAIA picked before the server could bind it. GAIA tries three
      ports, and logs each retry. Free a port and start it there with
      `gaia lemonade embedded start --port <port>`. With `--port`, the error reads
      **`it is in use by another program`** instead, and GAIA does not try another port.
    - **`busy loading or swapping a model; requests wait for it`** in
      `gaia lemonade embedded status` — its health check is slow while a model loads or
      unloads. It is working: don't stop it.
    - **`is running but not answering on port …`** — the server answers nothing, or its
      model backends have done no work for over 5 minutes. Check
      `~/.gaia/lemonade/lemond.log`; if it shows no progress, run
      `gaia lemonade embedded stop`, then start it again.

    To start over with a fresh copy, run `gaia init --force-reinstall`.
  </Accordion>

  <Accordion title="GAIA says the Lemonade Server is stuck or not answering" icon="hourglass">
    A Lemonade Server that is loading or swapping a model answers its health check
    slowly, so GAIA waits for it rather than calling it down. It reports one of these
    only when the server answers nothing, or its model backends have done no work at all
    for 5 minutes. Waiting longer will not help.

    - **`GAIA's Lemonade Server … is running but stuck`** or **`Embedded Lemonade … is
      running but not answering`** — GAIA's own server. Check
      `~/.gaia/lemonade/lemond.log` for what it was doing. If it shows no progress, run
      `gaia lemonade embedded stop`, then start it again (or run `gaia init`).
    - **`… is stuck rather than loading a model`** — the Lemonade you installed. Restart
      it with the command the error names, then retry.
  </Accordion>

  <Accordion title="gaia init can't install the GAIA agent from the Agent Hub" icon="store">
    `gaia init` installs the GAIA agent from the Agent Hub (`https://hub.amd-gaia.ai`, or
    `GAIA_HUB_URL`). If the hub can't be reached, setup finishes everything else, then
    reports the setup incomplete and exits with code 1. The Agent UI setup shows the same
    error instead of "GAIA is ready".

    - **`CERTIFICATE_VERIFY_FAILED`**: your network inspects HTTPS. Install the proxy's
      root certificate in the system certificate store (IT usually can).
    - **Anything else**: check your internet connection, proxy settings, or `GAIA_HUB_URL`.

    Then run `gaia hub install gaia`. The full error is in `~/.gaia/gaia.log`.
  </Accordion>
</AccordionGroup>

## Agent & SDK Issues

<AccordionGroup>
  <Accordion title="Agent says a tool 'requires explicit user approval'" icon="shield-halved">
    Dangerous tools — shell commands, file writes, email send / forward /
    permanent delete, calendar RSVP — only run after you approve them. If nothing
    can ask you, the tool is denied rather than run silently:

    ```
    'send_now' requires explicit user approval and cannot run unattended…
    ```

    You'll see this when the agent is driven without a terminal: output piped or
    redirected (`gaia chat -q "…" > out.txt`), a CI job, or a host process such as
    the OpenAI-compatible `gaia api` server, which has no way to show a prompt.

    - **Working interactively?** Run the command in a terminal without redirecting
      stdout, and answer the `[y]es / [N]o / [a]lways` prompt. In the Agent UI,
      approve the permission dialog instead.
    - **Genuinely unattended run you trust** (CI, a batch job, a host that already
      asked the user): export `GAIA_AUTO_APPROVE_TOOLS=1` in the environment that
      launches GAIA. Every tool approved this way is logged with its name. A `.env`
      file cannot set it — that would let a project directory switch off your
      prompts.

    <Warning>
      Don't leave `GAIA_AUTO_APPROVE_TOOLS=1` set on a machine with a mailbox
      connected: it lets the model send, forward, and permanently delete mail
      without asking.
    </Warning>
  </Accordion>

  <Accordion title="Memory recall fails with an OpenMP runtime error (macOS)" icon="triangle-exclamation">
    On macOS, `faiss-cpu` and `torch` each ship their own copy of
    `libomp.dylib`. With both loaded in one process, the next FAISS search
    initialises the second copy and macOS kills the process outright —
    `OMP: Error #15`, no traceback, nothing an error handler can catch. GAIA
    refuses the search instead:

    ```
    Procedure recall search would abort this process: 2 OpenMP runtimes are loaded…
    ```

    Keep the two apart in the environment GAIA runs in. No GAIA extra installs
    `torch`, so it arrives from something else in the environment — another
    package, or code a skill runs in-process. Memory recall needs `faiss-cpu`;
    a virtual environment holding only GAIA and its extras is the fix.

    If your host runs both runtimes together without aborting, set
    `GAIA_ALLOW_FAISS_TORCH_OMP=1` to search anyway. Check it in a throwaway
    process first — when the host is not in fact safe, the override restores the
    crash rather than working around it.
  </Accordion>

  <Accordion title="Agent not found after install" icon="magnifying-glass">
    ```bash
    # Verify package is installed
    uv pip show amd-gaia

    # Reinstall in editable mode (for developers)
    uv pip uninstall amd-gaia -y
    uv pip install -e .
    ```
  </Accordion>

  <Accordion title="Module not found errors" icon="file-circle-xmark">
    Ensure imports use the correct package paths:
    ```python
    from gaia.agents.base.agent import Agent  # ✅ Correct
    from gaia import Agent  # ❌ Won't work unless exported
    ```
  </Accordion>

  <Accordion title="Tools not registering" icon="wrench">
    The `@tool` decorator must be inside `_register_tools()`:
    ```python
    # ✅ Correct - inside _register_tools
    def _register_tools(self):
        @tool
        def my_tool():
            pass

    # ❌ Wrong - at class level
    @tool
    def my_tool():
        pass
    ```
  </Accordion>

  <Accordion title="LLM not responding" icon="robot">
    You shouldn't have to start the model server yourself — `gaia daemon`
    resolves, starts and supervises it, and every front-end asks the daemon
    instead of making you launch anything. So the question is why that didn't
    happen.

    Start with the daemon, which reports the model server it supervises:
    ```bash
    gaia daemon status
    ```

    If no daemon is running, start it:
    ```bash
    gaia daemon start
    ```

    If the daemon is up but the model server isn't, the start attempt failed
    and the reason is in the daemon log:
    ```bash
    gaia daemon logs --lines 100
    ```

    The usual cause is that Lemonade isn't installed at all. `gaia init`
    installs the server and pulls the model:
    ```bash
    gaia init
    ```
  </Accordion>

  <Accordion title="Lemonade Server won't stop" icon="circle-stop">
    Use the kill command to force stop Lemonade and child processes:
    ```bash
    gaia kill --lemonade
    ```
  </Accordion>

  <Accordion title="The local model didn't respond in time" icon="hourglass-end">
    You're seeing an error like:

    > The local model didn't respond in time. The Lemonade Server is
    > running, but its model call timed out — usually because the model
    > is still warming up (cold KV cache) or the prompt is too large
    > for the current hardware on a fresh load.

    **What it means.** Lemonade Server itself is reachable; the upstream
    inference call (libcurl → child `llama-server`) didn't return a
    first token before Lemonade's internal timeout. This is distinct
    from the connection-refused / unreachable case and uses its own
    typed error (`LemonadeUpstreamTimeoutError`).

    **Why it happens.**

    - **Cold KV cache** — the first request after a model load or swap
      always pays a one-time prompt-processing cost. The same query
      will usually complete in a fraction of the time on the second try.
    - **Prompt too large for the hardware** — heavy RAG retrieval or a
      multi-doc index can push the request past the iGPU/NPU
      prompt-processing budget on lower-spec systems. Reducing
      retrieved chunks is the most direct fix.
    - **Stale model state** — a recent unload/swap can leave the
      llama-server child in a half-loaded state.

    **Remediation, in order:**

    1. Wait 30s and resend the same query. The first call primes the KV
       cache; the second is materially faster.
    2. Reduce retrieved RAG chunks for large documents:
       ```bash
       gaia chat --max-chunks 2 --index your_document.pdf
       ```
    3. Restart the model server cleanly. This stops it and its child
       processes; the daemon starts a fresh one on the next request:
       ```bash
       gaia kill --lemonade
       ```
    4. Close other GPU/NPU-heavy apps competing for the device (image
       generators, other LLM servers, GPU benchmarks).

    See [#1030](https://github.com/amd/gaia/issues/1030) for the
    original report and the system-prompt-trim fix that reduces the
    per-request prompt size by ~5× to keep this from firing on typical
    indexed-PDF workflows.
  </Accordion>
</AccordionGroup>

## API Server Issues

<AccordionGroup>
  <Accordion title="Connection refused" icon="plug-circle-xmark">
    **Ensure server is running** (default port is 8080):
    ```bash
    gaia api start --port 8080
    ```

    **Check if port is in use:**
    ```powershell
    # Windows
    netstat -ano | findstr :8080
    ```
    ```bash
    # Linux
    lsof -i :8080
    ```
  </Accordion>

  <Accordion title="Model not found error" icon="circle-question">
    `AGENT_MODELS` is empty by default, so `/v1/models` returns no models until
    one is registered:
    ```bash
    curl http://localhost:8080/v1/models
    ```
    See [Adding New Agents](/reference/api-spec#adding-new-agents).
  </Accordion>

  <Accordion title="Agent processing failed" icon="triangle-exclamation">
    Confirm the model server is up — the daemon starts it and reports it here:
    ```bash
    gaia daemon status
    ```

    You don't need to set a context size. GAIA picks the window for each model
    when it loads it — 32,768 for NPU (FLM) models, 65,536 or more for GPU
    models — so a mismatch means something else loaded the model. Run the
    command again and GAIA reloads it at the right size.
  </Accordion>

  <Accordion title="Port already in use" icon="ban">
    Stop existing server or use a different port:
    ```bash
    gaia api start --port 8081
    ```
  </Accordion>
</AccordionGroup>

## Not enough free memory

GAIA checks free memory before it loads a model, so a PC that is short on memory
gets a message instead of a crash. The message says how much the model needs and
how much is free:

```
Not enough free memory to load Gemma-4-E4B-it-GGUF with a 32,768-token window:
it needs about 7.8 GB and only 6.0 GB is free.
```

**Fix:** close apps that use a lot of memory, then send your message again.
Web browsers, games, other AI apps and another Lemonade server with models loaded
are the usual ones. On a 16 GB PC, about 8 GB free is the least Gemma-4-E4B loads
in, and about 11 GB free when GAIA starts gets it the full window.

What GAIA does on a small PC:

- **The context window shrinks to fit.** Gemma-4-E4B loads with a 65,536-token
  window when there is room, and otherwise steps down in 8,192-token steps to no
  less than 32,768. The log says so. Restart GAIA after freeing memory to get the
  full window back.
- **Below 32,768 tokens, GAIA refuses.** The flagship's prompt and tools alone
  take about 20,000 tokens, so a smaller window could not answer.
- **Under 24 GB of RAM, the Agent UI loads the model with your first message**,
  not at startup. That first answer takes longer.
- **Another Lemonade counts as used memory.** GAIA runs its own Lemonade, so a
  server you started yourself keeps its models loaded beside GAIA's. To have GAIA
  use that server instead, set `LEMONADE_BASE_URL` (see
  [`gaia init`](/reference/cli#init-command), "Another Lemonade Server").

On a graphics card, GAIA reads free memory only for an AMD card on Linux.
Elsewhere a model that does not fit the card fails in Lemonade with its own
error. To run the chat model in the cloud instead, see
[AI providers](/guides/ai-providers).

## Model Issues

<AccordionGroup>
  <Accordion title="Model appears corrupted or gives errors" icon="file-circle-exclamation">
    Models can become corrupted from partial downloads or disk issues. Re-run init with force-models:
    ```bash
    gaia init --force-models
    ```

    Or delete all models and re-download:
    ```bash
    gaia uninstall --purge --purge-models --yes
    gaia init
    ```
  </Accordion>

  <Accordion title="Model download stuck or failed" icon="cloud-arrow-down">
    Check your network connection and retry. For large models, ensure sufficient disk space (~25GB for chat profile).

    ```bash
    # Retry with verbose output
    gaia init --verbose
    ```
  </Accordion>

  <Accordion title="gpt-oss answers nothing after reading a file or page" icon="file-lines">
    gpt-oss reads `<|channel|>`, `<|message|>` and similar markers as its own reply
    structure, so a file or web page containing them used to leave the reply empty, or
    make the model server return an error. GAIA now breaks those markers up (`< |channel|>`)
    before gpt-oss sees them, in every message and in the arguments of its earlier tool
    calls, so the text still reads the same. Other models get the text unchanged. One
    trade-off: gpt-oss sees `< |channel|>`, so an edit it asks for that quotes those exact
    characters will not match the file; ask for that edit on another model. If an answer
    is still empty, report it with `gaia diagnostics`.
  </Accordion>

  <Accordion title="Wrong model version installed" icon="code-branch">
    Force re-download to get the latest version:
    ```bash
    gaia init --force-models --yes
    ```
  </Accordion>
</AccordionGroup>

## RAG & Document Issues

<AccordionGroup>
  <Accordion title="Missing RAG dependencies" icon="puzzle-piece">
    `gaia init` installs the RAG extra and fails, showing the installer's error, if that install fails. To install it yourself into the one-line installer's environment (no `pip`, not activated):
    ```bash
    uv pip install --python ~/.gaia/venv/bin/python "amd-gaia[rag]"
    # Windows: uv pip install --python "$env:USERPROFILE\.gaia\venv\Scripts\python.exe" "amd-gaia[rag]"
    ```

    In an activated virtualenv of your own:
    ```bash
    uv pip install "amd-gaia[rag]"
    ```

    Or for development:
    ```bash
    uv pip install -e ".[dev,rag]"
    ```
  </Accordion>

  <Accordion title="PDF processing errors" icon="file-pdf">
    - Ensure PDFs have extractable text (not scanned images)
    - For scanned PDFs, use OCR preprocessing first
    - Check file permissions
  </Accordion>

  <Accordion title="Slow document indexing" icon="clock">
    - Use `--stats` to monitor progress
    - Larger documents take more time
    - Consider chunking very large documents

    When another model or app is using the GPU or CPU the embedding model runs on, indexing waits for it. A document still indexing says how long the embedding model has taken on its current batch. Each batch of 25 chunks gets one 300-second wait and is not resent after a timeout, so busy hardware doesn't get the same work queued again. A batch still unanswered after that fails with `did not answer within 300s; the GPU or CPU it runs on is likely busy`. Index the document again once the other work finishes.
  </Accordion>

  <Accordion title="Context not being used" icon="brain">
    - Verify documents were indexed successfully at startup
    - Check console output for indexing confirmation
    - Ensure document path is correct
  </Accordion>

  <Accordion title="Embedding model downloaded but won't load (memory and document search off)" icon="triangle-exclamation">
    You see `Memory is unavailable this session: the embedding model ... is downloaded but would not load`, or indexing fails with `model_load_error` / `llama-server failed to start`.

    GAIA loads its embedding model on the GPU, using the llama.cpp backend Lemonade picks for your machine (Vulkan on most Windows and Linux PCs, Metal on a Mac). With ROCm it uses the CPU instead (see the next entry). If the GPU load fails to start, GAIA loads the embedding model on the CPU backend instead and logs a warning naming the model, the backend that failed, and the error:

    ```
    Embedding model 'user.embeddinggemma-300m-GGUF' failed to load on llama.cpp's vulkan backend (...). Loading it on the CPU backend instead
    ```

    Memory and document search keep working on the CPU, but indexing is slower and keeps several CPU cores busy. GAIA saves the CPU choice in Lemonade, so Lemonade's own later loads of the embedding model use the CPU too. Each time GAIA starts, it tries the GPU again and saves it back if the load works, so after a driver update you only need to restart GAIA. To retry without waiting, restart GAIA's server:

    ```bash
    gaia lemonade embedded stop
    ```

    ```bash
    gaia lemonade embedded start
    ```

    The first GPU failure seen was llama.cpp's Vulkan cooperative-matrix path crashing on AMD Radeon GPUs ([#1831](https://github.com/amd/gaia/issues/1831)). Starting Lemonade with `GGML_VK_DISABLE_COOPMAT=1` also avoids that crash, but it slows prompt processing for every model: Qwen3 30B A3B on a Radeon 8060S drops from about 1,290 to 680 tokens/s. Generation speed is unchanged.

    If the CPU load fails too, the cause is something else: out of memory, or a context size the model can't take. Lemonade's server log has llama-server's own error.
  </Accordion>

  <Accordion title="GPU stuck at 100% on ROCm with two models loaded" icon="microchip">
    With llama.cpp's ROCm backend, the chat model and the embedding model both resident on the GPU can hold it at 100% even while idle. It is an amdgpu kernel driver issue, reported fixed in Linux kernel 7.4.

    GAIA avoids it by loading the embedding model on the CPU whenever llama.cpp uses ROCm, either as Lemonade's default backend or as the backend you chose for chat models in **Settings → Advanced → Model server**. That panel then reads:

    ```
    Embedding model runs on the CPU with ROCm to avoid a known GPU driver issue.
    ```

    and GAIA's log has the same line at INFO. The chat model stays on the GPU. Memory and document search keep working; indexing a large folder is slower and uses more CPU cores. Vulkan and Metal are unchanged: the embedding model stays on the GPU there.

    If you still see the GPU pinned on ROCm, use the Vulkan backend or update to kernel 7.4 or later.
  </Accordion>
</AccordionGroup>

## Evaluation Issues

<AccordionGroup>
  <Accordion title="`--compare` reports no baseline" icon="scale-balanced">
    `gaia eval agent --compare` only *diffs* scorecards — it does not run an eval.
    - **Fix**: Run the eval first (`gaia eval agent --category <cat>`); it prints the run dir and writes `<run-dir>/scorecard.json`.
    - **Then**: `gaia eval agent --compare <baseline>/scorecard.json <run-dir>/scorecard.json`.
    - **Baseline**: flagship baselines live in `tests/fixtures/eval_baselines/gaia-flagship/`. None is committed yet, so until the first one lands there is no regression verdict to report, only the scores the run measured.
  </Accordion>

  <Accordion title="Eval runs fail with chaotic context/model errors" icon="clipboard-question">
    Symptoms like `request exceeds the available context size`, spurious `INFRA_ERROR`, or `llama-server failed to start` usually mean two evals raced the same Lemonade server.
    - **Rule**: run at most one `gaia eval agent` process at a time — never in parallel (`&`). Chain runs serially instead.
    - **Backend**: the Agent UI backend must be running (`python -m gaia.ui.server --port 4200`).
    - **Judge access**: if the run errors with `ANTHROPIC_API_KEY not found`, export the key for the judge/simulator.
  </Accordion>

  <Accordion title="Dependency compatibility issues" icon="cubes">
    If you encounter numpy/pandas/sklearn import errors:

    **Symptoms:**
    - `ValueError: numpy.dtype size changed`
    - `ImportError: cannot import name 'ComplexWarning'`

    **Fix:**
    ```bash
    uv pip uninstall -y numpy pandas scikit-learn
    uv pip install numpy pandas scikit-learn
    ```
  </Accordion>
</AccordionGroup>

## AppImage on Linux

<AccordionGroup>
  <Accordion title="Ubuntu 24.04 LTS minimal: AppImage fails to mount" icon="linux">
    **Cause:** AppImage v2 requires FUSE 2. Ubuntu 24.04 LTS ships FUSE 3
    by default, and the minimal installer does not include `libfuse2` at all.

    **Fix:** install the FUSE 2 compatibility package:
    ```bash
    sudo apt install libfuse2
    ```

    After installing `libfuse2`, re-launch the AppImage:
    ```bash
    chmod +x gaia-agent-ui-*.AppImage
    ./gaia-agent-ui-*.AppImage
    ```
  </Accordion>

  <Accordion title="Chromium sandbox / --no-sandbox on Ubuntu 24.04.1+" icon="shield-halved">
    Starting with **GAIA 0.17.5**, the Linux AppImage is packaged with
    `--no-sandbox` by default. This works around Ubuntu 24.04.1's
    AppArmor-based unprivileged-userns restriction
    (`kernel.apparmor_restrict_unprivileged_userns=1`), which otherwise
    aborts Chromium with a FATAL sandbox error on first launch.

    **Security note:** `--no-sandbox` disables Chromium's renderer sandbox
    entirely — it is *not* a partial reduction. A compromised renderer can
    reach anything the user account can: files in your home directory, the
    keychain, network access. OS-level isolation (user account, AppArmor
    profiles if any) is the only layer that remains. The `.deb` package
    (`gaia-agent-ui-*-amd64.deb`) ships with the same `--no-sandbox`
    posture as the AppImage for the same AppArmor-userns reason, so
    switching packaging formats does not restore the Chromium sandbox on
    Ubuntu 24.04.1+.

    Older AppImages (&le; 0.17.3) require the user to pass `--no-sandbox`
    manually:
    ```bash
    ./gaia-agent-ui-0.17.3.AppImage --no-sandbox
    ```
  </Accordion>

  <Accordion title="Resetting a broken bootstrap" icon="rotate-left">
    If the Python backend bootstrap (uv, virtualenv, `amd-gaia[ui]` install)
    got interrupted or is in a half-installed state, clear the cached state
    and relaunch:

    ```bash
    rm -rf ~/.gaia/venv ~/.gaia/electron-install-state.json
    ./gaia-agent-ui-*.AppImage
    ```

    The AppImage will re-run its first-launch bootstrap from scratch.
  </Accordion>

  <Accordion title="Log files" icon="file-lines">
    The Linux AppImage writes logs under `~/.gaia/`:

    - `~/.gaia/electron-install.log` — Python backend bootstrap (uv, venv,
      pip install) output.
    - `~/.gaia/gaia.log` — runtime backend log from `gaia chat --ui`.
    - `~/.gaia/electron-main.log` — Electron main-process stdout/stderr,
      teed to disk so errors are visible even when the app was not launched
      from a terminal.

    `gaia.log` is capped at 10 MB. When it fills, it moves to `gaia.log.1`
    (older copies shift to `gaia.log.2` and `gaia.log.3`, and the oldest is
    deleted), so all of GAIA's logs together stay under about 40 MB. Change
    the cap with `GAIA_LOG_MAX_MB` and the number of copies with
    `GAIA_LOG_BACKUPS`. A `gaia.log` already larger than the cap is moved to
    `gaia.log.1` the first time GAIA starts, not deleted.

    To inspect all active TCP listeners (the backend uses a dynamic port, not always 4200):
    ```bash
    ss -tlnp
    ```
  </Accordion>

  <Accordion title="Collecting a diagnostics bundle for bug reports" icon="box-archive">
    GAIA ships a `gaia diagnostics` command that bundles the logs above,
    including the rotated `gaia.log.1`, `gaia.log.2`, ... copies,
    together with a short system-info snapshot (`uname -a`, distro info,
    relevant environment variables, `ss -tlnp (all TCP listeners)`) into a single
    tarball:

    ```bash
    gaia diagnostics
    # → ~/.gaia/diagnostics-<YYYYMMDD-HHMMSS>.tgz
    ```

    Options:
    - `--output <path>` — write the bundle to a custom path.
    - `--no-logs` — omit log files (useful if logs might contain sensitive
      chat content). State and system info are still included.

    Attach the resulting `.tgz` to your GitHub issue.
  </Accordion>
</AccordionGroup>
