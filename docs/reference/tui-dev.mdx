# GAIA Terminal UI — Developer Manual

For working *on* the TUI, or driving it from a test or an assistant. Using it
day to day is the [user manual](/guides/tui).

## What it is made of

Three processes, and knowing which one you are looking at saves most of the
debugging time:

```
gaia-cli            Go. The terminal app and the control API.
  └─ the agent      A subprocess, spawned once per session. The agent loop and
                    every tool. Either gaiacpp (C++) or gaia-agent (Python).
       └─ Lemonade  HTTP server. Runs local models and routes cloud chat.
```

The readiness gate straddles all three: the **GAIA agent** and **Lemonade** rows
are checked by the Go side. The **Language model** row depends on the agent
program: for `gaia-agent` it shells out to `gaia init --check`, which is Python
and talks to Lemonade; for `gaiacpp` the Go side asks Lemonade directly.

### Which agent program runs

The flagship has two programs behind it: the Python one, `gaia-agent`, and the
native one, `gaiacpp`. `gaia-cli` runs `gaia-agent` unless `gaiacpp` is asked
for, the same default as the Agent UI and the daemon, so an installed `gaiacpp`
the user never picked can't take away `--use-claude` or `--resume`. The header says
which is answering: `agent gaia v<x> (gaiacpp · Beta)` for the native agent, plain
`agent gaia v<x>` for the Python one.

When `gaiacpp` is asked for by name, it is looked for in this order, and the
first match wins:

1. The file `GAIA_GAIACPP_PATH` names, when it is set and is a file
2. `~/.gaia/bin/`, where both apps download it. This is the `bin` folder
   of GAIA's home, so `GAIA_HOME` (or, without it, `GAIA_CONFIG_DIR`) moves it
3. The folder `gaia-cli` itself is in
4. `PATH`
5. `~/.gaia/agents/gaia/`, then its `bin/`. `catalog.InstallRoot` follows GAIA's
   home too, as `gaia_agents_dir` does, so the "looked in" list names the real folder

The first four are the Agent UI backend's order
(`native_flagship_candidates` in `src/gaia/daemon/sidecars/fetch.py`), so both
apps run the same file for one saved choice. `GAIA_GAIACPP_PATH` is shared with
the Agent UI; `GAIA_TUI_AGENT` and `--agent-program` are the terminal UI's own.

The copy that is found is checked before it is run (`catalog.VerifyNative`,
the counterpart of `verified_native_flagship`). When a `gaiacpp.install.json`
sits beside a file named `gaiacpp` (`gaiacpp.exe` on Windows), which is what the
Agent UI's download writes, the file's SHA-256 must equal the record's
`sha256`. A mismatch, an unreadable record or one with no checksum is an error
that names the file and the record; no other copy and no other program is run
in its place. No record means no check: an installer's copy or a build of your
own has none. A path given to `--agent-program` or `GAIA_TUI_AGENT` is checked
the same way. `TestNativeNamesMatchTheBackend` fails when the record's file
name or the variable's name drifts from the Python side.

A build in your checkout is **not** picked up by itself: starting `gaia-cli`
from inside a repository never runs whatever sits in its `cpp/build`.

Which program a launch runs is decided by the first of these that is set
(`agentChoice` in `internal/cli/root.go`):

| Order | Source | Value | Session |
|---|---|---|---|
| 1 | `--agent-program` | A name or a path, from the table below | Pinned |
| 2 | `GAIA_TUI_AGENT` | The same | Pinned |
| 3 | `flagship_agent` in `~/.gaia/config.json` | `gaiapy` (runs `gaia-agent`) or `gaiacpp`; any other value stops the launch with an error naming the file and the key | Free |
| 4 | Nothing | `gaia-agent`, even when `gaiacpp` is installed | Free |

It applies to the flagship only, so `gaia-cli run email` ignores it and never
reads the saved choice. A named or saved program that is not found is an error
that lists where it looked; the other program is never run in its place.
`--mock` replaces whichever was chosen, skips the saved choice, and pins the
session.

`/agent` in the chat lists both programs and `/agent gaiapy` / `/agent gaiacpp`
relaunches the flagship on the other program in the running session
(`switchProgram` in `internal/ui/root/agentprogram.go`). The program is
resolved again from what is installed (`catalog.ForFlagship`), then goes
through the readiness gate and `launchAgent` like an `/agents` switch. Only
once it is running is `flagship_agent` written (`commitProgramSwitch`, through
`preflight.WriteFlagshipAgent`: the same locked read-modify-write as the other
shared keys, and the key the Agent UI and `gaia config set flagship_agent`
use), so a switch that is cancelled at the gate or fails to start saves
nothing. In a pinned session the choice is saved and the session is left
alone. The switch
to `gaiacpp` is refused, with nothing saved, in a `--use-claude` session and in
a reopened one, the two cases a `gaiacpp` launch refuses on the command line.

#### Downloading gaiacpp

A `gaiacpp` that is missing (`catalog.MissingProgramError`) or fails its check
(`catalog.NativeIntegrityError`) is offered as a download rather than refused
(`internal/ui/root/programfetch.go`). The terminal UI does not fetch it itself:
`internal/gaiaprogram` shells out to the hidden `gaia agent-program` command,
which wraps `gaia.daemon.sidecars.gaiacpp_fetch`, the code behind the Agent UI's
`/api/agent-programs` routes. One implementation owns the release lookup, the
checksum check, the version check and the install record.

| Command | Prints | Exit |
|---|---|---|
| `gaia agent-program status --json` | One object: `installed`, `path`, `target`, `can_download`, `size_bytes`, `version`, `reason`, `retry` (`true` when the release could not be reached) | `0` when it can be downloaded, else `1` |
| `gaia agent-program download --json` | One object per line: `progress` (`bytes_done`, `bytes_total`), then `done` (`path`) or `failed` (`error`) | `0` installed, `1` failed |

The offer is answered by Enter or Esc only while the chat is idle
(`ChatModel.Idle`: no turn running, no panel open, nothing typed), so typing
over it never answers it. Progress rewrites one status line
(`ChatModel.ReplaceStatus`). After a download `switchProgram` runs again with
`programFetched` set, so a `gaiacpp` that is still not found is an error and
not a second offer. `FlagshipModel.WithProgramFetch` replaces both calls in
tests; `TestAgentProgramSwitchEndToEnd` drives the whole path.

To exercise the download without a published release, point
`GAIA_GAIACPP_ASSETS_URL` at a folder (`file://…` or `https://…`) holding
`gaiacpp-<platform>` and `gaiacpp-SHA256SUMS.txt`.

At launch, a saved `gaiacpp` that fails the same two ways opens
`internal/ui/agentrecovery` (`recoverSavedAgent` in `internal/ui/agentrecover.go`)
before the main program: download again, use Full-featured (the Python agent),
or quit. Full-featured runs only when it is picked, and the pick is then saved.
A flag or `GAIA_TUI_AGENT` is a demand for that launch and still fails with the
error, as does a launch with no terminal to ask in. The control API names the screen
`agent-recovery`; it is a separate Bubble Tea program, so the control server
restarts when the main session takes over.

| Value | What runs |
|---|---|
| `gaiacpp` | The first `gaiacpp` in the five places above, then `cpp/build/Debug`, `cpp/build/Release` and `cpp/build` in the working directory and up to seven folders above it |
| A path to `gaiacpp` | That file. It counts as `gaiacpp` when it is named `gaiacpp` or `gaiacpp-<platform>`, as the release assets are |
| `gaia-agent` or `gaiapy` | The Python agent as installed: the first `gaia-agent` on `PATH`, in a finished install under `~/.gaia/agents/gaia/`, or in `cpp/build`. On an install whose record puts the flagship behind the daemon (`artifact_kind: binary`) it stays behind the daemon, and the first chat frame says so, because the `gaia-agent` file in that install is the daemon's HTTP sidecar |
| A path to `gaia-agent` | That file, spawned by `gaia-cli` itself, even on a daemon install |

On Windows `gaiacpp.exe` and `gaia-agent.exe` are accepted for the two names.
`gaiacpp` is always a child process of `gaia-cli`, whatever the install record
says.

```bash
GAIA_TUI_AGENT=gaia-agent gaia-cli                      # the Python agent
gaia-cli --agent-program ../cpp/build/Release/gaiacpp   # a build of your own
```

What changes with `gaiacpp` (`catalog.Agent.Native`):

| | `gaiacpp` | `gaia-agent` |
|---|---|---|
| Launched as | `gaiacpp --stdio`, plus `--dev`, `--full-access`, `--accept-edits`, `--model <id>` as needed | `gaia-agent`, plus the same and `--use-claude`, `--claude-model <id>` |
| Claude | Not available. `--use-claude` is refused before any screen opens, and `/model <claude id>` is refused in the chat; neither reaches the agent, which would exit on the flag | Available |
| Slash commands | `/sessions`, `/context`, `/skills`, `/research` and `/image` are refused in the chat with a line naming the Python agent, and left out of `/help` and the palette (`nativeLacks` in `chat/commandgate.go`). The rest work | All |
| Model server address | Passed in its environment: `LEMONADE_BASE_URL`, and `LEMONADE_API_KEY` when the server has a key. Inherited `LEMONADE_BASE_URL`, `LEMONADE_API_KEY`, `GAIA_BASE_URL` and `GAIA_API_KEY` are removed first, so the child only ever gets the address and key `gaia-cli` resolved | Reads GAIA's saved choice itself |
| Language model row | Lemonade lists the launch model: a cloud model its provider serves, or a local one that is downloaded (`Gemma-4-E4B-it-GGUF` when none was chosen). Nothing is loaded and no embedding model is needed | `gaia init --check --load` |

Setup still needs the Python `gaia` CLI on either agent: installing Lemonade
from the gate (`f`), `/setup`, and adding a model from a link.

`gaia-cli chat --subprocess "gaiacpp --stdio …"` also reads the canonical
events; without `--stdio` it is refused, because `gaiacpp` would open its own
prompt on the pipe.

<Warning>
**The agent subprocess is spawned once and outlives your edits.** Change Python
source and the running TUI keeps executing the old code — a measurement taken
without restarting is a measurement of the previous build. Restart the TUI
after touching anything under `src/gaia/` or `hub/agents/`, or after rebuilding
`gaiacpp`. This is the single easiest way to waste an hour.
</Warning>

## Building

Needs `git`, [Go](https://go.dev/dl/), and a Python env with `gaia` installed.

```bash
cd gaia && uv venv && uv pip install -e .
cd tui && make build          # -> tui/bin/gaia-cli (.exe on Windows)
```

Other targets: `test`, `test-race`, `lint`, `vet`, `cover`, `mock-agent`,
`dev` (build + mock-agent), `clean`.

For a dev run against your checkout:

```bash
scripts/dev/run-tui.sh --dev --control
```

There is one screen. `--dev` changes nothing on it: it turns on the control API
(like `--control`), logs that API's input counts, state changes and waits, and
the transport's diagnostics, to `$GAIA_TUI_HOME/gaia-tui.log`, and puts agents
the TUI spawns at DEBUG in `~/.gaia/logs/gaia-agent.log`. Debug detail lives
elsewhere:

| Where | What |
|---|---|
| `Ctrl+O` | Each call's command or code, timings, full outcomes, and the turn's metrics (when the agent ran with `GAIA_TURN_LOG`) |
| `--trace=<path>` | Every event as JSONL, tool arguments and results included. A traced launch also puts agents the TUI spawns at DEBUG in `~/.gaia/logs/gaia-agent.log` |
| `gaia-tui.log` | Transport diagnostics under `--dev`. Metadata only, never input contents |

To profile the TUI's own startup and rendering, add `--pprof 127.0.0.1:6060`
(loopback addresses only) and read it with Go's profiler:

```bash
go tool pprof http://127.0.0.1:6060/debug/pprof/profile?seconds=20
```

### Point it at your checkout, not the published sidecar

`mode: user` runs the **published frozen sidecar**, which is routinely older
than source. When testing an agent from a checkout, set the matching mode on the
TUI launch so its ensure request agrees:

```bash
GAIA_GAIA_AGENT_MODE=dev gaia-cli     # flagship
```

Starting a dev sidecar separately while the TUI still defaults to `user` creates
a mode conflict. `GET /daemon/v1/agents` shows the `api_version` actually in
use.

The mode applies to the Python agent only. With gaiacpp chosen
(`flagship_agent: "gaiacpp"`) the daemon starts the same binary either way and
lists it as `user`; a `dev` launch attaches to it without a conflict.

### Switching models on the relayed route

On the subprocess route `/model <id>` is a turn: the agent's stdio loop
intercepts it and confirms with a model-state ping. The relay has no such turn,
so `/model`, `/provider` and the startup restore go through
`client.TurnModelSwitcher` instead: the TUI checks the flagship's contract
(2.14 or newer moves a retained session in place), checks that Lemonade lists
the id, then sends it as `model` on every following `/query`. The first `final`
on it saves the choice; a 409 `could not switch session` puts the previous model
back (`client.ModelSwitchRefusedError`).

### Know which branch you built

Stacked branches are siblings; no single branch has everything. A leaf build
shows behaviour already fixed elsewhere — that has produced bug reports for
things fixed on another branch. Build from a merged integration branch, or state
explicitly which slice you tested.

The header's `agent gaia v<x>` and the welcome line's `GAIA core <y>` come from
the running agent only: the `agent_version` and `gaia_version` fields of its
model-state `status` ping (stdio), or the peer's own version (HTTP). Never from
`~/.gaia/agents/<id>/.installed`. No version on screen means the agent that
answered predates those fields, which is itself the answer to "which build?".

### Patched dependencies

`tui/third_party/` holds patched copies of upstream modules, wired in with
`replace` in `tui/go.mod`; its `README.md` lists each patch and why. Bubble Tea
is one of them: v1.3.10's Windows console reader drops the Ctrl state on
Backspace and Delete, so the copy reports Ctrl+Backspace as `ctrl+h` and adds a
`ctrl+delete` key (also mapped from `ESC[3;5~` on VT terminals). Upgrading Bubble
Tea means re-applying the lines marked `GAIA patch`, or dropping the copy once
upstream has the fix.

### Status and error lines

A status or error line is one sentence on what is wrong plus the one next step.
Daemon errors implement `daemon.Briefer`; render `daemon.Brief(err)` on the line
and keep `err.Error()` (route, alternatives, log path) for a `d details` pane.
Harness lines (`Step 4/50`, a plan's "Following the plan to …" headline,
`Plan: a → b`) never reach the screen in any mode; they are in the trace.

### The chat view

A turn renders as one bullet per event (`internal/ui/chat/workview.go`), led by
what the action does in plain words. `headline()` picks the words, best first:

1. the call's `description` (or `purpose`) argument, sanitised by
   `cleanDescription` and refused if it is placeholder text;
2. the goal the agent announced before the call, if it reads as a goal
   (`goalLike`): not a stage line ending in `-ing`, not the model musing, not a
   template;
3. a summary derived from the tool and its parsed arguments (`describeCall` in
   `actions.go`), e.g. `Run a 42-line Python script that reads 3 spreadsheets`.

What is running now is not a bullet but the status line, drawn by `View()`
outside the viewport (`statusLine`). Motion (`motion.go`) rides the spinner's
20 fps tick and redraws only that line, a pending prompt's title, and the
finished turn's recap for one sweep. A tick never rebuilds the transcript.
Turn it off with `reduced_motion` in `~/.gaia/config.json` or
`GAIA_TUI_REDUCED_MOTION=1`; `NO_COLOR` and a non-TTY stdout turn it off too.

Files a turn changed are found by `findDeliverables` (`deliverables.go`) and
peeked without running anything: sheet names and row counts for xlsx, slide
count for pptx, word count for docx and text, rows for csv.

Golden frames of whole screens live in `internal/ui/chat/testdata/frames/`.
After an intended change, regenerate them and review the diff:

```bash
cd tui && go test ./internal/ui/chat -run TestFrame -update
```

### Delegated work in the work log

`delegate_task` is drawn as one bullet, like any other tool
(`internal/ui/chat/delegation.go`). It is recognised by the shape of its
result — a `summary` string and a `helpers` list — never by its narration,
which differs between `gaiacpp` ("Handing 4 tasks to helpers") and
`gaia-agent` ("Handing work to helpers").

| When | What is drawn |
|---|---|
| Running | A `status` with `phase: "helpers"` is stored on the newest open tool and shown on the status line after its headline, with the word "helpers" dropped: `Handing 4 tasks to helpers · 3 of 4 done, 1 failed…`. It is never a bullet of its own and never becomes the model phase. With no tool open it is an ordinary status |
| Finished, folded | The `└` line is the result's `summary`. `status: "partial"` draws it in the warning colour and leaves the bullet unfailed; `status: "error"` is a failed step (`error: …` while the turn runs, `✗ failed: …` once it ends). When any helper is not `ok`, a faint `· Ctrl+O details` follows the summary if the row has room for all of it. Two delegations in a row are never joined into one bullet |
| Finished, `Ctrl+O` | The summary, then one clipped row per helper, in id order: `✓` / `~` / `✗`, the id, the task in a column of about two fifths of the row, then the first line of `conclusion`. A `partial` helper reads `stopped short (<reason>): …` and a `failed` one `failed: <reason>`, with `reason` in plain words (`step_limit` is "out of steps"). Past 16 helpers the list ends `… N more` |

The result's `advice` and `error` are written for the model and are never
drawn. A result the agent cut down on the wire (`{"truncated": true, …}`) has
no `helpers`, so only the summary line is drawn, from the event's `preview`.

## The control API

Off by default. `--control` auto-assigns a port; `--control-port N` pins one. It
binds `127.0.0.1` only and is bearer-token authenticated.

The token is written to `$GAIA_TUI_HOME/control.json` (mode 0600), defaulting to
`~/.gaia/tui/control.json`. Set `GAIA_TUI_HOME` to keep parallel sessions from
colliding.

```bash
TOKEN=$(python3 -c "import json;print(json.load(open('$GAIA_TUI_HOME/control.json'))['token'])")
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8815/control/v1/status
```

### Endpoints

All under `/control/v1/`.

| Endpoint | Method | Body | Returns |
|---|---|---|---|
| `status` | GET | — | view, agent, streaming, size, pid, frame_seq |
| `screen` | GET | `?format=plain\|ansi` | rendered frame |
| `keys` | POST | `{"keys": ["p"]}` | `{sent, seq, settled}` |
| `text` | POST | `{"text": "..."}` | `{sent_runes, seq, settled}` |
| `wait` | POST | see below | blocks server-side |
| `resize` | POST | `{"cols": 160, "rows": 50}` | — |
| `frames` | GET | — | frame history |

<Warning>
**`keys` takes an array of strings, not a string.** `{"keys": "p"}` is rejected
with `cannot unmarshal string into Go struct field keysRequest.keys of type
[]string`. Named keys go in the same array: `["down"]`, `["enter"]`, `["esc"]`,
`["ctrl+d"]`.
</Warning>

`text` types into the composer but does **not** submit. Follow it with
`{"keys":["enter"]}`.

To answer an approval prompt, wait until it is on screen and send `{"keys":["y"]}`
or `{"keys":["n"]}`: a batch that ends on the letter answers as soon as it lands.
"Always" takes two keys, `{"keys":["a","enter"]}`. A sentence sent with `text`
while a prompt is up goes to the composer and never answers it, and with text in
the composer the
letters are typed too — answer with `{"keys":["tab","enter"]}` (once),
`["tab","tab","enter"]` (always, where offered) or `["esc"]` (deny).

### Wait, never sleep

`POST /control/v1/wait` blocks server-side until a condition holds, with
`timeout_ms`:

```jsonc
{"contains": "Landed", "timeout_ms": 120000}
{"absent":   "streaming", "timeout_ms": 180000}
{"state":    {"view": "chat"}, "timeout_ms": 120000}   // conditions are ANDed
```

A turn takes anywhere from 30s to several minutes depending on the model and the
tools it reaches for. A fixed `sleep` is either a wasted minute or a
half-rendered capture.

<Note>
`{"state": {"streaming": false}}` can match the instant *before* a turn starts,
because it was not streaming yet either. Submit, confirm `streaming` went true,
and only then wait for it to go false — or poll `status` until it reports false.
</Note>

### State values

`view` is `splash` · `preflight` · `chat` · `unknown`. There is no hub screen:
the TUI boots into one agent's chat behind the readiness gate.

On `preflight`, `blocker` names the row refusing the launch: `binary`,
`lemonade`, `model`, `daemon`, `sidecar`, `mailbox`. Wait on
`{"state": {"view": "chat"}}` rather than a screen substring.

A `daemon` or `sidecar` row that is simply not running is started by the gate
itself, once per launch (`Row.AutoFix` in `internal/ui/preflight`). While that
runs the row is `[..] starting…` and there is no `blocker`; only a start that
failed, a foreign daemon record, or a remote `LEMONADE_BASE_URL` leaves it
waiting on `f`. To reproduce a reboot, stop the daemon you started for the
drive (`GAIA_DAEMON_HOME` set) and relaunch.

`esc` quits on `preflight` (there is no screen behind it) and clears the
composer on an idle `chat`. With the `d` details pane open, it closes the pane
first.

## Copy and selection keys

The terminal owns the mouse by default, so a plain drag is the terminal's own
selection and the app never sees it. That selection can't scroll the
transcript, which is why the app has its own.

| Input | What happens | Code (`internal/ui/chat/`) |
|---|---|---|
| `Ctrl+T` | Toggles the app mouse (Cell-Motion capture); the status bar names the current owner | `selectmode.go`, `mousecapture.go` |
| Drag, app mouse | In-app selection by content row, so it survives scrolling. Past the top or bottom edge a 50 ms tick scrolls up to 5 lines and extends it. Release copies over OSC 52 | `selection.go` |
| `Shift`+click, app mouse | Extends the current selection and copies it | `selection.go` |
| `Enter` / `Esc`, with a selection | Copies it again / clears it | `model.go` (`handleKey`) |
| `/copy`, `/copy all` | Message picker (`↑`/`↓`, `Enter`, `Esc`) / whole transcript as markdown. Both run mid-turn | `copycmd.go` |
| `Ctrl+Y`, `Ctrl+B` | Last answer / its last code block | `clipboard.go` |

Copied text is plain: each message's span records its chrome (`msgSpan.gutter`,
`bodyStart`/`bodyEnd`), and a message covered end to end is copied from its
source markdown. The control API's `mouse` actions are single-point gestures, so
a drag can't be driven through it; `selection_test.go` covers it, decoding the
OSC 52 payload. OSC 52 is write-only, so a screen capture can't confirm a copy.

## Giving it a terminal

The TUI queries terminal size and colour support at startup, so it needs a real
pty. Two things that do **not** work from a tool call or CI step:

- `script -q /dev/null ...` — fails with `tcgetattr/ioctl: Operation not
  supported on socket` when stdout is a socket.
- `osascript -e 'tell application "Terminal" to do script ...'` — can return
  `AppleEvent timed out (-1712)` and leave nothing running.

What works is allocating the pty yourself:

```python
import os, pty, fcntl, termios, struct

pid, fd = pty.fork()
if pid == 0:
    os.environ["TERM"] = "xterm-256color"
    os.execv(tui_path, [tui_path, "--control-port", "8815", "--dev"])

# Size it, or cols/rows are 0 and every capture wraps wrongly.
fcntl.ioctl(fd, termios.TIOCSWINSZ, struct.pack("HHHH", 50, 160, 0, 0))
while True:                       # drain, or the child blocks on a full buffer
    if not os.read(fd, 65536):
        break
```

Call `resize` **first** in any drive script for the same reason.

### Colour

`GET /screen?format=ansi` and count `\x1b`: dozens on a styled frame, zero means
the colour profile degraded at launch. On Windows, launch through `wt.exe` — a
`cmd.exe` window spawned by `Start-Process` lands in legacy conhost, reports no
colour support, and the TUI then emits no escape sequences at all. It reads as
"syntax highlighting is broken" but nothing is broken.

## Capture mistakes that produce false bug reports

- **Always capture the whole screen.** A cropped capture once produced a
  fabricated "uninstall silently does nothing" — the status line is the
  second-to-last row.
- **Check which screen you are on** before sending keys. Keys sent to the wrong
  screen do nothing and read as "the binding is broken".
- **Grep for the right words.** The confirmation prompt's first line is a
  risk badge (`READ`, `WRITE`, `RUNS CODE`, `DESTRUCTIVE`, or `ACCESS` on a
  prompt to use a file or folder outside the chat's) and a question. A
  tool the TUI knows gets a plain question — a shell command reads
  `RUNS CODE Run this command?`, a file write `WRITE Write this file?` — and
  any other tool reads `Allow <tool>?`. There is no `Confirm: <tool>` line.
- **`format=plain` strips ANSI**, so it cannot answer a colour question.
- `screencapture` is blocked on some machines; use the control API text.

## Logs and traces

| What | Where |
|---|---|
| TUI control/state log | `$GAIA_TUI_HOME/gaia-tui.log` |
| Agent debug log | `~/.gaia/logs/gaia-agent.log` (`gaia-agent` only; `gaiacpp` writes its log lines to stderr, which the TUI shows if the process exits with an error) |
| Lemonade (embedded) | `~/.gaia/lemonade/lemond.log` |
| Event trace | `~/.gaia/traces/<ts>-<agent>.jsonl` via `--trace` |

The agent log is where tool calls live, with arguments and results:

```bash
grep -E "Executing tool|Tool execution result" ~/.gaia/logs/gaia-agent.log
```

The `TOOL_LOADER` lines record which tools were selected for each turn — the
first thing to check when the agent claims a capability "isn't available".

<Warning>
A trace holds whatever the agent read — file contents, shell output, email.
Review before sharing. The control log omits input contents and masks pasted
credentials by design.
</Warning>

## Running a local model on a dev box

The embedded Lemonade is self-contained and does not need a system install:

```bash
gaia lemonade embedded install     # downloads the platform artifact
gaia lemonade embedded start       # prints its port and writes env.sh
source ~/.gaia/lemonade/env.sh     # LEMONADE_BASE_URL + LEMONADE_API_KEY
gaia lemonade embedded status
```

It is private: its URL and key are its own, and other configured servers never
inherit them.

`gaia init --check` is the exact gate the preflight screen uses, and it names
the missing model id:

```
NOT READY: profile 'gaia' needs setup
  - Model 'user.embeddinggemma-300m-GGUF' is not downloaded
```

<Warning>
`user.`-prefixed models are **custom registrations**: pulling one requires
`checkpoint` + `recipe` (+ `embedding` for an embedder, and `mmproj` / `vision`
/ `reasoning` when the model needs them), unless Lemonade already lists it —
then it is pulled by name. Built-in models are the opposite —
pulling one *with* a recipe makes Lemonade treat it as a new registration and
400 (#1655). `gaia init` sends those fields, and `readiness.pull_model` and
the Agent UI Download button share one body (`pull_request_body`). A gateway
model is refused before any request: there are no weights to fetch.
</Warning>
