<Note>
This is the page to start from if you want to **use** GAIA. GAIA runs AI agents locally on your machine, and you can use them two ways: the **desktop app** (a window with chat, your documents and files) or the **terminal** (`gaia-tui`). Building agents or working on GAIA itself? Skip to [For developers](#for-developers).
</Note>

## What you'll need

- A computer running **Windows 10/11**, **macOS 14+** (Apple Silicon), or **Linux** with glibc 2.38 or newer (Ubuntu 24.04+, Fedora 39 to 44, or a current Arch). Ubuntu 22.04, Debian 12 and RHEL 9 are too old for GAIA's AI engine
- About **1 GB** of free disk space for the app. A model that runs on this PC needs more: about 6 GB for Gemma 4 E4B, or about 30 GB on PCs that get Qwen3.6. A cloud model (Fireworks AI or the AMD LLM Gateway) downloads under 1 GB
- **16 GB** of RAM or more to run a model on this PC. On a 16 GB PC, close other large apps first: the model needs about 8 GB free (see [Not enough free memory](/reference/troubleshooting#not-enough-free-memory))
- An **internet connection** for setup, which downloads GAIA's model server, the GAIA agent, and the model you pick

### Silent install on Windows (IT and scripted deployment)

The Windows installer is an NSIS package, so it takes the usual `/S`, plus `/COMPONENTS=` to choose what to install:

```powershell
gaia-<version>-win-x64-setup.exe /S /COMPONENTS=ui,tui
```

| Option | Meaning |
|---|---|
| `/S` | No windows, no prompts. |
| `/COMPONENTS=ui,tui` | `ui` is the desktop app, `tui` the terminal; name one or both, no spaces. Without it, `/S` updates whatever is already installed, and installs both on a machine that has neither. |
| `/D=<folder>` | The terminal's install folder. Must come last. The desktop app always uses its own folder. |

| Exit code | Meaning |
|---|---|
| `0` | Installed what was asked. |
| `2` | A GAIA program it would replace is running. Nothing was changed. |
| `3` | `/COMPONENTS=` named something unknown, or nothing. Nothing was changed. |
| `4` | A conflicting install: a GAIA developer build, or the desktop app installed for all users. Nothing was changed. |
| `5` | A chosen component failed. Any other component you chose was installed. |

`/S` installs for the account that runs it. Deployment tools that run as SYSTEM (the SCCM and Intune default) install into SYSTEM's profile, not a user's — run it in the user's context.

To uninstall silently, run each component's `QuietUninstallString` from `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall`. Both keep `~/.gaia` when silent.

## First-launch setup (desktop app)

The desktop app ships its backend: a `gaia` executable inside the app, so it installs no Python and downloads no package on your PC. The first launch goes straight to the setup screen, where you pick and download a model.

An app update carries a new backend with it. After one, the app updates the GAIA agent on its first launch, with a **Try again** button if that fails. Your models stay as they are. If the agent update fails, **Try again** picks it up, and the next launch does too.

Before an update replaces the app, its installer stops GAIA's background service (the GAIA daemon) and the agents it runs, because Windows can't replace files a running program holds.

### Choose where chat runs

The app then opens on its setup screen, which asks where chat should run:

- **Fireworks AI** or **AMD LLM Gateway** (cloud): installs GAIA's local model
  server and its small document-search model (under 1 GB), then asks for your
  key and lets you pick the cloud model. Nothing large downloads.
- **On this PC** (local): starts GAIA's local model server first, then names the
  chat model that fits this PC and the whole download size before anything
  large downloads. The pick follows the memory that is **free right now**, not
  just the memory the PC has: Gemma-4-E4B-it-GGUF (~6 GB) on most PCs, or
  Qwen3.6-35B-A3B-GGUF (~23 GB, about 30 GB in all) where the GPU holds it and
  enough memory is free. When a larger model is passed over, the screen says
  why, for example how much memory it needs and how much is free. You can pick
  another model that fits. If the download won't fit the disk, the screen says
  how much space is needed and doesn't start it. While it downloads, the screen
  shows which model, how much is done, the speed and the time left.

If a step fails, the screen shows the error `gaia init` reported, with a **Try
again** button and the command to run in a terminal instead.

### What if the app can't start its backend?

If the app's `gaia` is missing, the window says so; reinstall GAIA. See the [installation troubleshooting guide](/reference/install-troubleshooting) for common failure modes.

## Use a Lemonade you already run

GAIA normally runs its own private Lemonade Server. If you already run Lemonade,
point GAIA at yours instead: the PC then runs one server and keeps one copy of each
model, and your own launch flags and backend stay in charge. On a 16 GB machine,
two servers side by side can run it out of memory.

GAIA asks the first time it finds one, and remembers the answer:

- **Desktop app and `npx @amd-gaia/agent-ui`:** the Agent UI's setup screen asks
  before it installs a server or downloads anything.
- **Terminal UI:** the first-run checks offer it.
- **Command line:** `gaia init` asks; `gaia init --yes` never switches on its own and
  prints the command to run instead.

To switch at any time:

<CodeGroup>
```bash Use yours
gaia lemonade connect http://localhost:13305
```

```bash Back to GAIA's own
gaia config set lemonade_mode gaia
```

```bash Which one is in use
gaia lemonade status
```
</CodeGroup>

In the Agent UI, use **Settings → Advanced → Model server**. `gaia lemonade connect`
with no address uses the one `gaia lemonade detect` finds on this PC.

- **Version:** your Lemonade must be v2026.44.1 or newer. An older one is refused,
  and the message names both versions, as is one that reports no version GAIA can
  read. GAIA's own Lemonade Server is upgraded the next time GAIA's daemon starts it;
  `gaia daemon restart` does that now.
- **API key:** if your server was started with `LEMONADE_API_KEY`, GAIA asks for it
  (`--api-key-stdin` reads it from a pipe). It's kept in the OS credential store,
  never in GAIA's config file.
- **Down:** if your server isn't answering, GAIA says so and how to start it. It
  never starts its own instead.
- **What GAIA does on your server:** registers its embedding model
  (`user.embeddinggemma-300m-GGUF`), downloads the models it needs and loads them.
  Its chat model loads with GAIA's context size for that load.
- **What GAIA never does there:** change your server's setup. It doesn't register
  cloud providers or hand your server keys, install backends, save load options
  into its config, or unload or delete your models.
- **Cloud providers:** to chat through Fireworks AI or the AMD LLM Gateway, set
  the provider up on your server yourself, with its key in your server's
  environment. GAIA then uses it as it is. If it isn't set up, connecting says so
  instead of changing your server.
- **Long documents:** if answers about long documents time out, raise your server's
  request timeout (`global_timeout` in its config).

`LEMONADE_BASE_URL` (and `LEMONADE_API_KEY`) still work and win over this setting.
Choosing GAIA's own in first-run setup (when that server isn't answering) or in
**Settings › Advanced** sets GAIA's own up and ignores that value from then on. Both
name the address before you switch, and Settings says it is ignored while it is still
set. Set it to a different address and it applies again.
The choice is stored as `lemonade_mode` and `lemonade_base_url` in
`~/.gaia/config.json`. Switching tells a running GAIA daemon right away. It stops
GAIA's own server when you switch to yours, and starts it again when you switch back.
Switching back needs GAIA's own server installed, and waits until it answers: if it
isn't installed or won't start, the switch is refused or undone and nothing changes. Run `gaia init --gaia-lemonade` to install it and switch in one
step.

### A Lemonade on another computer

GAIA can use a Lemonade Server on another computer on your network, such as a
desktop with a bigger GPU. Lemonade only answers its own computer at first, so set
up that computer before you connect:

1. **Let other computers reach it.** On the server computer, run
   `lemonade config set host=0.0.0.0`. The setting is saved and applies right away.
2. **Lock it with a key.** Set `LEMONADE_API_KEY` in the server's environment.
   Without a key, anyone on your network can use the server and change its models.
3. **Open the port.** Allow incoming connections to port 13305, Lemonade's default,
   in the server computer's firewall.

Then, on the GAIA computer, open **Settings → Advanced → Model server**, enter the
server's address (for example `http://192.168.1.100:13305`) and its key, and choose
**Use this server**. GAIA checks that the server answers before it saves the address.
If it doesn't answer, check the three steps above.

## Updating GAIA

GAIA checks for new releases and tells you when one is out, then waits for you to
install it. **Auto-update is off by default** while GAIA is still changing quickly;
turn it on when you'd rather not be asked.

Updates stay out of your way: they download in the background, usually only the
parts that changed, and installing shows no setup wizard. A restart brings the app
back by itself. GAIA restarts its own Lemonade Server only when a release changes
the version it needs. If an install doesn't finish, GAIA says so the next time it
opens, and the next try shows the installer's window.

An update doesn't lose your work. The desktop app asks first if an answer or an
indexing job is still running, keeps any message you were typing, and reopens the
chat you were in. The Terminal UI won't install while it is answering or running
setup, saves the conversation first, and shows it again when you reopen it. The agent starts a fresh session after an update, so mention
anything from earlier that it still needs.

**Desktop app (Agent UI).** It checks 10 seconds after launch and every 4 hours. A
found release shows as a chip in the corner with **Update now**; once it has
downloaded, the chip offers the restart, whenever suits you. Quitting GAIA also
installs it. If the update then fails to finish setting up or start, GAIA offers **Go back** in that error box or on the chip, for the first three launches after an update. The update carries the new version's backend, so the first launch after the restart downloads nothing for it. A failed background check stays quiet and tries again later. Going back keeps your chats, memory and goals: an earlier version opens the data a newer one saved. **Settings → General → Updates** has:

- **Install updates automatically** — off by default. On, releases download in the
  background and you're asked only to restart.
- **Include release candidates** — off by default. On, GAIA also offers test builds
  (`vX.Y.Z-rcN`) before their final release; they install only when you ask, unless
  auto-update is on. A release candidate build is offered newer candidates either
  way, and moves to the final release once it ships.
- **Check for updates**, and **Update to vX** when one is waiting.
- **Go back to GAIA vX** after an update, if it causes problems. GAIA installs the version you had before and pauses updates, so the bad one doesn't come back; **Unpin** resumes them. It downloads that version, so it needs an internet connection.
- **Install a specific version…** — a recent release, newer or older. GAIA then
  stays on that version (pinned) until you click **Unpin**.

**Terminal UI.** It checks once at launch and prints a line when a release is out.

| Command | What it does |
|---|---|
| `/update` | Show the running version, the newest release, and the settings |
| `/update now` | Install the newest release |
| `/update v0.25.0` | Install that exact release and pin to it |
| `/update back` | Go back to the version before the last update, and pin to it |
| `/update list` | List recent releases |
| `/update auto on` / `off` | Install new releases automatically when you quit (off by default) |
| `/update rc on` / `off` | Offer release candidates too (off by default; they still wait for `/update now` unless auto-update is on) |
| `/update unpin` | Offer new releases again after a pinned install (`/update now` also replaces the pin) |
| `/update cancel` | Don't install the release queued for quit |

If something stops the Terminal UI from starting, its startup screen offers the same two ways out: `u` installs a newer
release, and `b` goes back to the version before the last update.

Installing closes the Terminal UI and runs the installer in the same terminal; open
GAIA again when it finishes. It uses the installer GAIA came from: the one-line
script for `~/.gaia/bin`, or the release's Windows setup, macOS `.pkg`, or Linux
`.deb`/`.rpm` (checked against the release's `gaia-installers-SHA256SUMS.txt` first).
Releases older than the combined Windows setup can't be installed that way from the
Terminal UI; use the one-line installer with `GAIA_RELEASE_TAG` set instead. The
Windows setup and macOS package finish in their own window, so an exact version installed
through them is pinned, and remembered for `/update back`, the next time GAIA opens on it.
A setup or package install can't go back to v0.25.3 or older, which predate those
installers; `/update back` says so. The launch check and `/update now` offer only
the newest release that has an installer for your machine's OS and architecture; when a newer
one has none, `/update` says so and points to the releases page.

Both apps keep the auto-update and release-candidate choices in
`~/.gaia/update-config.json`, so turning one on in either app turns it on in the
other. Pins stay separate. If the file can't be read, neither app overwrites it: saving a
setting fails with a message saying to fix or delete the file, and the desktop app pauses
its update checks until it is fixed. Both check the
[GitHub releases](https://github.com/amd/gaia/releases). The desktop app installs only releases that publish its update for your
platform.

**On a Mac the desktop app can't install updates itself yet** ([#7061](https://github.com/amd/gaia/issues/7061)):
its builds aren't signed with an Apple Developer ID, and macOS rejects an unsigned
update. A new release still shows on the corner chip and in **Settings → General →
Updates**, with a **Download** link to its release page; install the `.dmg` from there
over the app you have. **Install updates automatically** isn't shown, and **Install a
specific version…** opens the chosen release's page instead of installing it.

To turn update checks off entirely, set `GAIA_DISABLE_UPDATE=1` before launching.

## Uninstalling

GAIA follows the platform convention: removing the app leaves your user data (chats, documents, downloaded models) behind by default. To remove the data too, run the `gaia uninstall` CLI from a terminal — it has tiered flags so you can decide exactly what to keep.

The Windows uninstaller and `apt remove` also stop GAIA's background service (the GAIA daemon) and the agents it runs. macOS and AppImage have no uninstall step, so the daemon watches for it instead: within a few seconds of the app going to the Trash or the `.AppImage` being deleted, it shuts down and stops its agents. A daemon you started from a terminal is not tied to the app and keeps running; stop it with `gaia daemon stop`.

### Windows

The Windows uninstallers keep data by default. Choosing Yes to the additional
cleanup prompt deletes **every file in `~/.gaia`**, including custom agents,
connector sign-ins and permissions, memory, and shared runtimes. Other GAIA
installations using that folder will stop working. Silent uninstalls keep it.

Each part you installed has its own entry in **Settings → Apps → Installed apps**, so you can remove one and keep the other. To remove GAIA completely, uninstall both:

- **GAIA** — the desktop app. Removes the app, its Start Menu / Desktop shortcuts, and the autostart registry entry.
- **GAIA Terminal UI** — the terminal. Stops GAIA's background service, then removes `gaia-tui`, `gaia-agent`, `gaia`, the PATH entry, the Windows Terminal profile, the font if the installer added it, and its shortcuts.

Each uninstaller shows the cleanup prompt above; decline it and `~/.gaia/` is left alone. For tiered cleanup instead of deleting the whole shared folder, open PowerShell before you uninstall and run the `gaia` inside the desktop app (with the terminal installed, plain `gaia uninstall --purge` does the same):
```powershell
& "$env:LOCALAPPDATA\Programs\gaia-desktop\resources\core\gaia.exe" uninstall --purge
```

### macOS
Drag the **GAIA** app from Applications to the Trash. Empty the Trash.

To also remove your data, run this from a terminal first, while the app is still in Applications:
```bash
/Applications/GAIA.app/Contents/Resources/core/gaia uninstall --purge
```

### Linux (Debian/Ubuntu)
```bash
sudo apt remove gaia-desktop
```

Both `apt remove` and `apt purge` preserve your personal data in `~/.gaia`.
To also remove your data, run this as your own user before you remove the package:
```bash
/opt/GAIA/resources/core/gaia uninstall --purge
```

### Linux (AppImage)
Delete the `.AppImage` file. Its app-grid entry hides itself once the file is gone; to remove it too, delete `~/.local/share/applications/gaia-desktop.desktop` and `~/.local/share/icons/hicolor/256x256/apps/gaia-desktop.png`. To also remove your data, delete `~/.gaia/`.

### Tiered cleanup with `gaia uninstall`

The CLI lets you escalate cleanup as far as you want — useful for reclaiming disk or fully resetting:
```bash
gaia uninstall --purge --dry-run            # Preview the purge tier without deleting
gaia uninstall --venv                       # Just the Python env
gaia uninstall --purge                      # Venv + chats, documents, memory, sessions, undo snapshots, config, agents, saved keys + installer leftovers
gaia uninstall --purge --purge-lemonade     # Also remove a system-wide Lemonade Server
gaia uninstall --purge --purge-models       # Also remove downloaded Lemonade models
gaia uninstall --purge --purge-hf-cache     # Also remove ~/.cache/huggingface/
```

## Where things live

| What | Location |
|---|---|
| Electron app | Platform-specific (Program Files / /Applications / /opt/GAIA) |
| Backend (`gaia`) | Inside the app, in `resources/core/` |
| Chat database | `~/.gaia/chat/gaia_chat.db` |
| Document Library uploads | `~/.gaia/documents/` |
| Chat file attachments | `~/.gaia/chat/uploads/` |
| Configuration | `~/.gaia/electron-config.json` |
| Logs | `~/.gaia/gaia.log` (`$GAIA_HOME/gaia.log` when `GAIA_HOME` is set), or the path in `GAIA_LOG_FILE` (capped at 10 MB; older logs rotate to `gaia.log.1`–`gaia.log.3`), `~/.gaia/electron-install.log` |
| Terminal UI and agent binaries (one-line installer), plus the agent's install record (`gaia-agent.install.json`, its version and SHA-256, which GAIA checks before starting it). It also holds the `gaia`, `gaia-cli` and `gaia-mcp` commands (links to `~/.gaia/core` on Linux and macOS; on Windows the frozen `gaia` itself), and is the only GAIA directory the installer puts on your PATH | `~/.gaia/bin/` |
| The frozen `gaia` the one-line installer runs (Linux and macOS) | `~/.gaia/core/` |
| The copy of its `gaia` an AppImage runs, which outlives the AppImage's mount | `~/.gaia/app-core/` |
| Agent run traces | `~/.gaia/traces/` |
| Daemon state (token, custody database, logs) | `~/.gaia/host/` (`$GAIA_HOME/host/` when `GAIA_HOME` is set) |
| Models (managed by Lemonade) | `~/.cache/lemonade/models/` |

Setting `GAIA_HOME` moves Document Library uploads and chat file attachments to `$GAIA_HOME/documents/` and `$GAIA_HOME/chat/uploads/`, the MCP server list to `$GAIA_HOME/mcp_servers.json`, and installed agents to `$GAIA_HOME/agents/`. It must not be your home directory or one of its parents.

## Privacy

GAIA runs entirely on your machine. **No data is sent externally** beyond the package downloads during install. There is no telemetry, no crash reporting, no usage analytics. See the [FAQ](/reference/faq) for more.

## For developers

The installer above is for using GAIA. To build agents, work on GAIA itself, or put one front end on a machine from a script, use one of these instead. Each installs one thing directly; the script, `pip`/`uv` and npm routes add no desktop shortcuts or Installed-apps entries:

| You want | Use |
|---|---|
| The `gaia` CLI, plus the terminal UI, in one command, with no Python needed | Windows: `irm https://amd-gaia.ai/install.ps1 \| iex` · Linux/macOS: `curl -fsSL https://amd-gaia.ai/install.sh \| sh` |
| The Python package only | `uv pip install amd-gaia` — see [Setup](/setup) and the [Quickstart](/quickstart) |
| The desktop app from npm | `npm install -g @amd-gaia/agent-ui`, then `gaia-ui` — see [Agent UI](/guides/agent-ui) |
| The desktop app's own installer | `gaia-agent-ui-<version>-<arch>` files on [GitHub Releases](https://github.com/amd/gaia/releases/latest) |
| Either front end from source | [Development guide](/reference/dev); the terminal builds with `cd tui && make build`, the desktop installers as in [Packaging & Distribution](/deployment/ui) |
| A Windows build of your own branch to hand to someone | [Shareable build](/deployment/shareable-build). Uninstall it before running the GAIA installer, which refuses to install beside it. |
