## What Is Agent Eval?

The Agent Eval framework validates your GAIA agent's quality by running realistic, multi-turn conversations against the live Agent UI. It uses **Claude Code** as both user simulator and judge -- driving conversations through MCP, scoring every response across 7 dimensions, and producing a machine-readable scorecard.

Unlike unit tests that check individual functions, Agent Eval tests the **full system end-to-end**: RAG indexing, tool dispatch, context retention, hallucination resistance, and personality compliance -- through the same interface real users interact with.

**What you get:**
- Automated multi-turn conversation testing with persona-driven user messages
- 7-dimension scoring rubric (correctness, tool selection, context retention, completeness, efficiency, personality, error recovery)
- Deterministic pass/fail with weighted scoring
- Regression detection via baseline comparison
- Auto-fix mode that invokes Claude Code to repair failures

## Prerequisites

<Steps>
  <Step title="Install eval dependencies">
    ```bash
    uv pip install -e ".[eval]"
    ```
  </Step>

  <Step title="Authenticate Claude">
    The benchmark uses Claude to drive and judge each scenario. A Claude Code login
    (`claude`, then `/login`) is enough, and it wins over any API key. Without one,
    export an API key in the shell:

    ```bash
    export ANTHROPIC_API_KEY=sk-ant-...
    ```

    A key in a `.env` file is used only when there is no login and no exported key.
    The run prints which credential it uses, for example
    `Claude eval driver: using the Claude Code CLI login`.
  </Step>

  <Step title="Install Claude Code CLI">
    The runner invokes scenarios via `claude -p` subprocess. Verify it's installed:

    ```bash
    claude --version
    ```

    If not installed, see [Claude Code installation](https://code.claude.com/docs/en/quickstart).
  </Step>

  <Step title="Install the local LLM backend">
    The benchmark runs against a local model, so Lemonade and the model have to be on
    the machine. `gaia init` installs both — you don't have to start anything, the
    daemon does that:

    ```bash
    gaia init
    ```
  </Step>

  <Step title="Start the Agent UI backend">
    Start the backend from the repository root with the eval switches set. The
    pre-flight check refuses to run memory, email and scripted-user scenarios
    without them, and a full benchmark always includes all three:

    <Tabs>
      <Tab title="CLI">
        ```bash
        GAIA_MEMORY_ADMIN=1 GAIA_EVAL_SCRIPTED_USER=1 \
        GAIA_EVAL_MAILBOX=$PWD/tests/fixtures/gaia/email/eval_inbox.mbox \
        gaia chat --ui
        ```
      </Tab>
      <Tab title="Direct">
        ```bash
        GAIA_MEMORY_ADMIN=1 GAIA_EVAL_SCRIPTED_USER=1 \
        GAIA_EVAL_MAILBOX=$PWD/tests/fixtures/gaia/email/eval_inbox.mbox \
        python -m gaia.ui.server
        ```
      </Tab>
      <Tab title="PowerShell">
        ```powershell
        $env:GAIA_MEMORY_ADMIN="1"; $env:GAIA_EVAL_SCRIPTED_USER="1"
        $env:GAIA_EVAL_MAILBOX="$PWD\tests\fixtures\gaia\email\eval_inbox.mbox"
        gaia chat --ui
        ```
      </Tab>
    </Tabs>

    | Variable | Why the eval needs it |
    |---|---|
    | `GAIA_MEMORY_ADMIN=1` | Unlocks the memory admin endpoints (`/api/memory/admin/*`) that reset and seed memory between scenarios. Without it, pre-flight stops with a 403 from `/api/memory/admin/seed`. |
    | `GAIA_EVAL_SCRIPTED_USER=1` | Lets a scenario script a user who declines commands (`setup.decline_commands`). Without it, pre-flight stops with a 403 from `/api/eval/scripted-user`. |
    | `GAIA_EVAL_MAILBOX` | Points the mail tools at the offline fixture mailbox the `gaia_email` scenarios read. |

    Memory scenarios also need long-term memory switched on. It is on by
    default; if you turned it off, switch it back on in the Memory dashboard,
    or with:

    ```bash
    curl -X PUT http://localhost:4200/api/memory/settings \
      -H 'X-Gaia-UI: 1' -H 'Content-Type: application/json' \
      -d '{"memory_enabled": true}'
    ```

    The Agent UI backend must be running on `http://localhost:4200` (default).
    A scenario that touches neither memory nor email and sets no
    `decline_commands` runs against a plain `gaia chat --ui`. The eval's own MCP
    server already gets `GAIA_MEMORY_MCP_ALWAYS=1` from `eval/mcp-config.json`, so
    the backend does not need it.
  </Step>
</Steps>

## Quick Start

Run your first eval in under 5 minutes:

### 1. Run a Single Scenario

Start with a simple RAG factual lookup test:

```bash
gaia eval agent --scenario simple_factual_rag
```

This will:
1. Create a new Agent UI session via MCP
2. Index the `acme_q3_report.md` document
3. Ask about Q3 revenue (simulating a `power_user` persona)
4. Judge the response against the ground truth (`$14.2 million`)
5. Output a scored result

### 2. Run a Category

Test all RAG quality scenarios:

```bash
gaia eval agent --category rag_quality
```

### 3. Run the Full Benchmark

Run all scenarios across every category (91 scenarios in 12 categories at the time of writing):

```bash
gaia eval agent
```

<Note>
  The full benchmark includes memory, `gaia_email` and scripted-user scenarios, so it
  needs a backend started with the eval switches from
  [Start the Agent UI backend](#prerequisites). Against a plain `gaia chat --ui` it
  stops at pre-flight before running any scenario. Passing pre-flight does not make
  a local run match CI: the `gaia_*` categories also rely on a fixture hub, a fixture
  web server and auto-approved tools that pre-flight does not check. To reproduce a
  CI lane's scores, run `python util/run_eval_lane.py --lane <lane>`, which sets the
  backend up the way CI does.
</Note>

Every scenario scores the flagship `gaia` agent. That is the `--agent-type`
default and no scenario pins its own, so a scorecard names one agent and two
scorecards are comparable. Pass `--agent-type` to measure a different agent, but
never compare that result to a scorecard captured under another one —
`--compare` matches on scenario ID alone and cannot tell two agents apart.

The local model is different: a scorecard records it, and `--compare` refuses
(exit 3) a baseline captured on another model or under another eval model. To
score a specific model, set it as `default_model` in the backend's GAIA home and
pass `--agent-model` so every scenario is checked against it.

### 4. Architecture Audit (Free)

Check for structural limitations without making any LLM calls:

```bash
gaia eval agent --audit-only
```

## Reading the Scorecard

After each run, results are written to `eval/results/<run_id>/`:

| File | Description |
|------|-------------|
| `scorecard.json` | Machine-readable results with per-scenario scores and cost |
| `summary.md` | Human-readable pass/fail report |
| `traces/<scenario_id>.json` | Full per-scenario trace with turn-level scores and reasoning |

### Understanding Pass / Fail

A scenario **passes** when both conditions are met:
- Overall score is **6.0 or higher** (out of 10)
- **No turn** has a correctness score below 4

A scenario **fails** if either:
- Overall score is below 6.0, OR
- Any single turn has correctness below 4 (hard fail on hallucination or wrong answer)

### The 7 Scoring Dimensions

Each turn is scored across 7 dimensions. The overall score is a weighted sum:

| Dimension | Weight | What It Measures |
|-----------|:------:|-----------------|
| **Correctness** | 25% | Factual accuracy against ground truth. Wrong numbers, wrong names, or hallucinated facts score 0 |
| **Tool Selection** | 20% | Used the right tools in the right order. Skipping tools or over-calling scores low |
| **Context Retention** | 20% | Remembered prior turns, resolved pronouns, didn't re-ask established information |
| **Completeness** | 15% | Answered all parts of the question |
| **Efficiency** | 10% | Took the optimal path without redundant tool calls |
| **Personality** | 5% | Concise, direct tone. No sycophancy or generic AI hedging |
| **Error Recovery** | 5% | Gracefully handled missing files, empty results, or ambiguous queries |

### Status Codes

| Status | Meaning |
|--------|---------|
| `PASS` | All criteria met |
| `FAIL` | Score too low or critical failure (hallucination, wrong answer) |
| `BLOCKED_BY_ARCHITECTURE` | Agent UI architecture prevents success (e.g., history window too small) |
| `TIMEOUT` | Scenario exceeded time limit. The runner stops the scenario's running turn before the next scenario starts, and records the turns that finished (unjudged) in `turns` |
| `BUDGET_EXCEEDED` | Claude API budget cap hit |
| `INFRA_ERROR` | Agent UI backend unreachable, MCP failure, or a permission prompt the runner could not answer |
| `SETUP_ERROR` | Document indexing failed (0 chunks) |
| `SKIPPED_NO_DOCUMENT` | Corpus file not present on disk |
| `SKIPPED_NO_MODEL` | A model a `requires_asr` / `requires_vlm` tag names is not downloaded (or ffmpeg is missing for ASR) |
| `ERRORED` | Eval agent crashed or returned invalid output |

<Note>
  Only `PASS`, `FAIL`, and `BLOCKED_BY_ARCHITECTURE` count toward the average score and judged pass rate. Infrastructure statuses are excluded from quality metrics.
</Note>

## Scenario Categories

The benchmark includes 91 scenarios across 12 categories (counts as of this writing — the runner discovers scenarios dynamically, so totals grow as new YAML is added):

| Category | Count | What It Tests |
|----------|:-----:|---------------|
| `memory` | 25 | Cross-session persistence, fact accumulation, conflict resolution, temporal recall |
| `real_world` | 19 | Real PDFs, XLSX, 10-K filings, RFC specs, datasheets |
| `mcp_reliability` | 10 | Tool-call reliability: parameter passing, conditional tool use, multi-step chains |
| `rag_quality` | 8 | Factual extraction, hallucination resistance, negation handling, CSV/table data |
| `web_system` | 6 | Clipboard, desktop notifications, webpage fetching, system info |
| `tool_selection` | 5 | Correct tool usage, smart discovery, multi-step planning |
| `context_retention` | 4 | Cross-turn recall, pronoun resolution, multi-document context |
| `adversarial` | 3 | Empty files, large documents (>100k tokens), topic switching |
| `personality` | 3 | Concise responses, no sycophancy, honest limitations |
| `vision` | 3 | Screenshot capture, VLM integration |
| `error_recovery` | 3 | Graceful handling of missing files, empty results, vague requests |
| `captured` | 2 | Golden-path replays from real user sessions |

CI runs all of these except `vision` and `web_system`, which read the runner's
own screen, windows and clipboard into a scorecard that uploads as a public
artifact. Run those two locally.

## Common Workflows

### Regression Testing

Save a baseline after a known-good run, then compare future runs. A baseline is
only valid against runs of the **same agent** under the **same judge model** —
`--model` drives each scenario as well as scoring it, so changing either makes
the diff meaningless rather than merely noisy:

```bash
# Save current results as baseline
gaia eval agent --save-baseline

# Later, compare a new run against the baseline
gaia eval agent --compare eval/results/eval-20261021-141300/scorecard.json

# Explicit two-file comparison
gaia eval agent --compare eval/results/run_A/scorecard.json eval/results/run_B/scorecard.json
```

The comparison shows per-scenario deltas, regressions (PASS to FAIL), and improvements (FAIL to PASS).

### Auto-Fix Mode

Let Claude Code automatically diagnose and repair failures:

```bash
# Fix all failures, up to 3 iterations
gaia eval agent --fix

# Fix a specific category with custom targets
gaia eval agent --category rag_quality --fix --max-fix-iterations 5 --target-pass-rate 0.95
```

Fix mode runs in a loop:
1. Evaluate all scenarios
2. Diagnose failures and patch source code
3. Re-run only the failed scenarios
4. Compare results -- stop when `--target-pass-rate` is reached

<Warning>
  Fix mode patches `src/gaia/` source files directly, so it refuses to start while tracked files have uncommitted changes — commit your work or run it from a separate worktree. A fixer iteration that times out or fails stops the loop; check `git diff` for partial edits. Always review diffs before committing. Run `python util/lint.py --all --fix` after fix iterations.
</Warning>

### Capturing Real Sessions

Convert a live Agent UI conversation into a replayable scenario:

```bash
gaia eval agent --capture-session 29c211c7-31b5-4084-bb3f-1825c0210942
```

This reads the session from the Agent UI database, extracts turns and indexed documents, and writes a scenario YAML to `eval/scenarios/captured/`. You must then edit the file to add proper `ground_truth` and `success_criteria` fields.

### Filtering by Tags

Run only scenarios with specific tags:

```bash
# Run scenarios tagged with "security" OR "t4_adversarial"
gaia eval agent --tag security --tag t4_adversarial
```

A scenario matches when its `tags:` field contains at least one of the given tags. The shipped scenarios use the difficulty tiers `t1_basic`, `t2_compound`, `t3_stress` and `t4_adversarial`, plus `security`, `usability` and `tui`; scenarios you author can carry any tags you like. `--exclude-tag` drops scenarios carrying a tag, after the include filters are applied. Shipped scenarios that need a particular environment are tagged for this: for a run without Lemonade, use `--exclude-tag local_blocked_no_embedder --exclude-tag live`.

### Output Formats

```bash
# JUnit XML for CI integration
gaia eval agent --output-format junit

# Markdown summary
gaia eval agent --output-format markdown
```

## Cost Control

| Control | Flag | Default |
|---------|------|---------|
| Budget per scenario | `--budget` | `$2.00` |
| Timeout per scenario | `--timeout` | `900` seconds |
| Run specific scenario | `--scenario` | all |
| Run specific category | `--category` | all |

**Typical costs:**
- Single scenario: $0.02 -- $0.10
- Full benchmark (all scenarios): $1.00 -- $5.00 (scenarios whose corpus files aren't on disk are skipped)
- Architecture audit: $0.00 (no LLM calls)

<Tip>
  Start with `--audit-only` (free) to understand expected failures, then run individual categories to control costs during development.
</Tip>

### Which Claude account pays

Every eval that calls Claude (`gaia eval agent`, `gaia eval tasks`, email drafting, action items, briefings, `gaia eval sessions`, retrieval) and PDF corpus generation uses the first of these, and prints which one, never any part of the key or token:

1. **Your Claude Code subscription**, through `claude -p`: `CLAUDE_CODE_OAUTH_TOKEN`, or the CLI's own login (checked with `claude auth status`). Where no interactive login is possible (CI), set `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`. A subscription token is not an API key, so never export it as `ANTHROPIC_API_KEY`.
2. **`ANTHROPIC_API_KEY` from the environment:** the Messages API, billed per token to that console account.
3. **`ANTHROPIC_API_KEY` from a `.env` file**, the same way.

With none of them, the run stops with an error naming all three. It never falls back to a weaker scorer.

On the subscription path, token counts and `total_cost_usd` come from the CLI's JSON output. The cost is the list price of those tokens, not money spent. Token counting (`count_tokens`) and inline PDF analysis exist only on the API path.
