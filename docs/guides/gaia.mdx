# GAIA — the flagship agent

GAIA is the agent a new user meets first. One agent handles the everyday work you'd otherwise spread across four: talking things through, answering questions about your own documents, poking at a spreadsheet, and reading the web. It remembers across sessions, and inference runs **locally** on your machine through Lemonade by default.

<Note>
  GAIA is built on top of the [Chat agent](/guides/chat) — same document Q&A prompt, same
  RAG discovery, same session persistence. What it adds is *breadth*: the data, web, and
  filesystem capabilities Chat leaves off by default, plus a home for add-on skills.
</Note>

## What it does

- **Conversation with memory** — facts you tell it persist to an on-device store and come back in later sessions. It can also search your own past conversations.
- **Document Q&A over your files** — index a file or a whole folder, then ask questions. PDF, Word, PowerPoint, and plain text; the prompt tells the agent to name which document each fact came from rather than blending sources.
- **Data exploration** — load a CSV or Excel file into a local SQL scratchpad table and query it, so "which region grew fastest" becomes a real query rather than a guess from a truncated preview.
- **Web research** — search the web, fetch and read pages, download files.
- **Files** — read, search by name or content, and walk directory trees inside your allowed scope. Writing and editing are available too, behind an explicit confirmation (see [Tools that need your approval](#tools-that-need-your-approval)).
- **Images** — describe a local image or answer a question about it, using the local vision model. It can also *generate* one from a description with local Stable Diffusion; that swaps the resident model, so the reply after an image takes an extra moment while the chat model reloads.
- **Skills** — short playbooks loaded into the agent's own prompt. One ships always-on; the rest are opt-in. See [Skills](#skills) below for what this release ships.

## Requirements

| | |
|---|---|
| Local model server | Lemonade **10.2.0** or newer, running |
| Model | `Gemma-4-E4B-it-GGUF` (downloaded) |
| RAM | 8 GB minimum |
| Platforms | Windows x64, Linux x64, macOS Apple Silicon |

Install Lemonade, download the model, and start the server:

```bash
gaia init
```

Inference runs locally by default. The sidecar's `/query` endpoint accepts `provider: "lemonade"` (the default) or `provider: "claude"`, which sends the conversation to Anthropic's API. Any other provider is rejected with **HTTP 400**, as is naming a `provider` together with a `model` that belongs to the other one. Omit `provider` and the `model` decides: a `claude-*` id goes to Anthropic, anything else runs locally.

### Check it's ready before you ask it anything

`GET /v1/gaia/init` is a read-only preflight: it probes Lemonade, compares its version against the 10.2.0 floor, and confirms the model is downloaded. It never pulls or loads a model.

```bash
curl -s http://127.0.0.1:8141/v1/gaia/init
```

It answers **200** when ready and **503** when not, with a `hint` naming the fix — Lemonade unreachable, Lemonade too old, or model not downloaded. Liveness alone is `GET /health`, which never touches the model server.

<Note>
  A **401** here means the sidecar wants a caller token — `/v1/gaia/*` requires one, while
  `/health` and `/version` don't. That's the normal state for the sidecar the daemon
  spawns. See [Authenticating your requests](#authenticating-your-requests).
</Note>

## Tool surface

Some register conditionally: `search_documentation` needs `npx` on your PATH, and the browser tools need the `browser` extra (`pip install "amd-gaia[browser]"`). Grouped by what they're for:

| CLI setup | `check_cli_setup`, `install_cli`, `sign_in_cli` |
| Skills | `list_skills`, `search_skill_hub`, `install_skill`, `capture_skill`, `remove_skill`, `load_skill`, `unload_skill`, `skill_status`, `remember_skill_lesson` |
| Code search | `index_codebase`, `search_code_index`, `get_index_status`, `clear_code_index` |
| Run control | `request_user_input`, `set_loop_state`, `sleep`, `load_tools`, `read_tool_output` |

That count is what the agent *can* do, not what it sees at once: per-turn tool selection sends the model a subset of the registry on any one call, and `load_tools` is the escape hatch it calls mid-turn to pull in a bundle the selector missed. No capability is lost either way.

`run_shell_command` is rate-limited and needs your approval like the other gated tools. Anything off its read-only no-prompt list (`ls`, `cat`, `grep`, `find`, `stat`, `df`, `uname`, and similar) — `git commit`, `npm test`, `rm notes.txt` — is shown to you and runs once you approve it, rather than being refused. A few invocations a yes/no cannot describe honestly, like `gh auth token` or an encoded PowerShell command, are always refused. A run pre-approved with `GAIA_AUTO_APPROVE_TOOLS` gets the read-only list and refuses the rest; only full access, which a person turns on and can see on screen, runs the rest unasked. Installing the specific CLIs a skill needs goes through [its own tools](#setting-up-a-cli-a-skill-needs) instead. Commands can be chained on one line (`cd src && ls | grep agent`) so looking something up and checking it is a single step — every command on the line is checked against the same allowlist before any of it runs, and one approval covers the line. A leading `VAR=value` (`PYTHONPATH=. pytest -q`) sets that one command's environment and nothing else's; the variables that decide which binary runs or what code it loads — `PATH`, `LD_PRELOAD`, `GIT_SSH_COMMAND` and their families — stay refused. A `cd` that actually ran carries to the *next* separate call, so `cd build` in one turn is still in effect on the next — `get_shell_state` reads the session's current directory, and `reset_shell_session` returns it to where the task started; an explicit `working_directory` is a one-shot override that never moves the session. `run_python` runs a Python snippet from the project root and returns its output, so the agent can compute or check something without leaving a script in your project. `sleep` waits up to five minutes per call, so the agent can wait out a rate limit before retrying; pressing Stop ends the wait within a second.

How long a command may run depends on what it is — a test run gets 15 minutes, a build or install 30, a network call 5, and everything else the usual 30 seconds. `wait_for_condition` covers the other half of waiting: give it a command that succeeds once the thing you are waiting for is ready (a file written, a server answering) and the agent waits in one step instead of re-checking in a loop.

**Mail is treated as data, never as instructions.** Every message body the email tools return arrives fenced between `<<<UNTRUSTED_EMAIL_BODY_START>>>` and `<<<UNTRUSTED_EMAIL_BODY_END>>>`, and a message showing phishing signals comes back flagged with the reason it was flagged. A flagged message is never reported as something that needs action, however urgent it sounds, and the agent will not repeat its call to action as advice — it says what the message claims, that it looks like a lure, and to leave it alone.

**Image *generation* costs you a model reload.** Drawing a picture pulls Stable Diffusion into Lemonade and evicts the resident chat model, so the first reply after an image waits for the chat model to load again. The trade is worth it on the flagship, which is general-purpose; the Chat agent's doc and file profiles leave the [`sd` tool mixin](/sdk/mixins/tool-mixins#95-stable-diffusion-mixin) off for exactly that reason.

### Setting up a CLI a skill needs

Some skills run a command-line tool rather than calling an API — [`github-triage`](/guides/starter-skills#github-triage) needs the GitHub CLI, which owns its own login. When that tool is missing or logged out, the agent sets it up for you instead of handing you instructions and stopping.

Ask for it in plain words — *"set up the GitHub CLI"* — and three tools do the work:

| Tool | What it does |
|---|---|
| `check_cli_setup` | Reads the CLI's own status. Changes nothing and never prompts. |
| `install_cli` | Installs it with your package manager, after you approve the exact command. |
| `sign_in_cli` | Starts the browser sign-in, after you approve the exact command. |

The check reports one of five states, and only one of them means "sign in":

| State | What it means | What fixes it |
|---|---|---|
| `ready` | Installed, signed in, permissions present. | Nothing. |
| `missing` | Not on `PATH`. | Install it. |
| `unauthenticated` | Installed, no working credential. | Sign in. |
| `insufficient_scopes` | Signed in, but the token lacks a permission the skill needs. | Sign in again — the flow re-requests it. |
| `env_token` | The credential comes from a `GH_TOKEN` / `GITHUB_TOKEN` environment variable — normally working, and reported here even when that token has expired. | Nothing while it works. If it has expired, replace the variable's value — signing in cannot fix it, because `gh` refuses to store its own credential while the variable is set. Clear the variable to switch to a browser login. |

**You approve every install and every sign-in, one at a time.** Both are in the confirmation set below, and neither offers an "always" — there is no way to pre-authorize them, and loading a skill does not exempt them.

**Signing in is a handoff, not automation.** GAIA starts `gh auth login --web`, shows you the one-time code and the device URL, and waits. You enter the code in your browser; the agent cannot type it for you. Afterwards it re-checks and confirms the permissions actually arrived, rather than trusting the exit code. GAIA requests exactly the scopes the skill's commands can reach — `repo` and `read:org` for GitHub — and never sees the token.

If any step can't finish — no code appears, the code expires, the browser sign-in fails — it says so and gives you the command to run by hand. It never reports a setup that didn't happen.

<Note>
  **Linux has no automated install, on purpose.** The GitHub CLI is not in the stock Debian or Fedora repositories, and the real install adds GitHub's apt/dnf repository — a root-level trust decision that is yours, not an agent's. On Linux you get [cli.github.com](https://cli.github.com) instead. Windows uses `winget`, macOS uses `brew`.
</Note>

### Fast mode — for a session that's only conversation

Breadth is not free. The tool descriptions and capability instructions are re-read by the model on **every** call of a turn, and a turn is two to five calls — so a session spent entirely on conversation pays for documents, files, and the web without ever using them.

Fast mode drops the agent to a plain conversational surface for the whole session: **3,110 tokens of fixed prompt instead of 17,942** — under a fifth. The personality and honesty rules stay; nothing else does. It keeps the three CLI-setup tools above, which are conversational by design, so "set up the GitHub CLI" still works in a fast session.

```bash
GAIA_FAST=1               # environment
```

```python
GaiaAgentConfig(fast=True)   # GAIA_FAST still overrides this, in both directions
```

<Warning>
  **It's session-scoped and one-way.** A fast session has no documents, no files, no web,
  no images, and no skill library, and it cannot pick them up mid-conversation — the tools
  were never registered. Start an ordinary session when you need them.
</Warning>

Use it when you know the session is chat: a voice front-end, a quick question, a kiosk. Leave it off otherwise — the default agent already trims what the model sees per turn, and keeps every capability available.

### Tools that need your approval

Thirteen tools mutate your machine or your accounts and are gated behind an explicit confirmation: **`write_file`**, **`edit_file`**, **`run_shell_command`**, **`wait_for_condition`** (it re-runs a shell command until it succeeds), **`execute_python_file`**, **`run_python`**, **`notify_desktop`** (on Windows it spawns a PowerShell child to draw the notification), **`install_cli`** and **`sign_in_cli`** (they install software and sign you in to an account), **`browser_login`** (it opens a window and persists a signed-in session), and — because installing or capturing a skill writes third-party code under `~/.gaia/skills` and removing one deletes it — **`install_skill`**, **`capture_skill`**, and **`remove_skill`**. Everything else — reading, indexing, querying, web fetching, memory, and `check_cli_setup` — runs without asking.

The browser's acting tools are gated by *situation* rather than by name: clicking and typing on the open web is ungated, the same as fetching a page, but the same click **inside a session you signed in to** asks first, as does anything whose label reads irreversible. See [Driving a browser](/guides/browser-use).

<Warning>
  **Over the sidecar's `/query` stream, a gated tool asks only if you can answer.** Pass a
  `session_id` and the stream stays open on the confirmation so your client can approve it;
  a one-shot request that cannot be asked stops with a message saying which action it
  declined, rather than running it.
</Warning>

### The agent reads a file before it changes it

`edit_file`, and `write_file` on a file that already exists, refuse a file the agent hasn't read with `read_file` in this session, or one that changed on disk since it did. That stops edits patched together from a search snippet or a guess. The check runs before any approval prompt, so you aren't asked to approve an edit that is going to be refused, and it still applies with confirmations bypassed. A partial read counts, and creating a new file needs no read. See [Read before edit](/spec/file-io-tools-mixin#read-before-edit) for the exact rule.

## File access scope

The agent's file, document, and data tools are confined to a set of allowed paths. **By default that set is your home directory.**

That's the honest scope for a personal document agent — "ask questions about my files" means your files — and it is still a real boundary: system directories, program files, and other users' home directories fall outside it and are refused. The check runs against the *resolved* path, so a symlink pointing out of the allowed set doesn't get around it; you get an explicit `Access denied to path:` error naming both the requested and the resolved path.

**The allowed set is not the whole story, and shouldn't be treated as one.** Two denylists apply *inside* it, because "in scope" and "safe" are different questions:

- **Secrets are never read back.** `.env`, `id_rsa`, `credentials.json`, `.netrc`, any `.pem`/`.key`, and everything under `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.kube` are refused on read even when they sit in an allowed directory — otherwise "summarise this folder" is a credential exfiltration primitive.
- **Files that run on their own are never written.** Shell startup files (`.bashrc`, `.zshrc`, `.profile`), PowerShell profiles, `~/.config/autostart/*`, systemd user units, `LaunchAgents`, and anything inside a repo's `.git/` — hooks and config alike. Writing to one of those isn't editing a document, it's arranging for the agent's output to execute at your next login.

Both are refused with a message naming the file and why. Edit such a file yourself if that's genuinely what you wanted.

**Reaching outside the scope asks first.** When a tool needs a file or folder outside the allowed set, the TUI and Agent UI show the same approval dialog as a write, naming the path. Approving grants that one file, or that folder and everything inside it (reads and changes), until the chat's agent restarts — never saved, never "always", and each new path is asked about on its own. Paths that stay off limits whatever you answer are refused without a prompt: secrets, system and program directories, the system temp folder, a whole drive, your entire home folder, and any folder that contains one of those. Pre-approved tools (`GAIA_AUTO_APPROVE_TOOLS`) never answer this prompt; only full access does. The Agent UI scopes a chat to its attached documents, so this is how it reads a file you name in your own folders — indexing it for document Q&A still needs it attached.

To narrow the scope, construct the agent with an explicit list:

```python
from gaia_agent.agent import GaiaAgent, GaiaAgentConfig

agent = GaiaAgent(config=GaiaAgentConfig(
    allowed_paths=["/home/me/Documents", "/home/me/projects"],
))
```

<Note>
  In v0.1.1 this is a **construction-time** setting only — the packaged sidecar exposes no
  flag or environment variable for it, so narrowing the scope means embedding the agent in
  your own Python process.
</Note>

## Memory

Memory is on by default and lives on-device. The agent writes facts you ask it to remember, recalls them in later sessions, and can search prior conversations. `forget` and `update_memory` let you correct or drop what it holds.

The mechanism, storage location, and how to disable it are covered in the [Memory guide](/guides/memory).

## Skills

[Agent Skills](/guides/composing-skills) are short playbooks an agent loads into its own prompt, grouped into named **skill sets** — exactly one set is active per launch. GAIA is built to host them: its own bundled skill directory is the highest-precedence discovery root, so a skill shipped with the agent wins over a same-named user copy.

**One skill ships enabled: `gaia-voice`.** It is declared in the manifest's always-on `skills:` list, so it is in the prompt on every call — 702 tokens of it, and it registers no tools. It isn't a task recipe but the agent's honesty floor: don't claim work you didn't do, don't present empty output as a result, don't substitute a near-miss and report success. Those failures spoil an answer whatever the task is, which is why it can't sit in a bundle you have to opt into.

**No skill *set* loads by default, and v0.1.1 declares none.** Loading several skill bodies into every prompt costs tokens and shrinks the room left for an answer, and no eval has measured that trade for this agent yet. The manifest's skill-set declarations ship commented out; enabling them is uncommenting two blocks, with no code change.

Once a release declares sets, you select one at launch:

```bash
GAIA_SKILL_SET=research   # environment
```

or in Python, which takes precedence over the environment:

```python
GaiaAgentConfig(skill_set="research")
```

A name that isn't a declared set **fails at startup** naming the valid sets — it never silently falls back to a default. Today, with no sets declared, any value fails; leave it unset.

## Driving it over HTTP

The agent runs as a **sidecar** — a self-contained HTTP service the GAIA daemon spawns, health-checks, and tree-kills. It binds `127.0.0.1:8141` by default and is never exposed on a LAN interface: it speaks for your documents and your memory.

| Endpoint | Purpose |
|---|---|
| `GET /health` | Liveness. Never touches the model server. |
| `GET /version` | The daemon's contract probe → `{apiVersion, agentVersion}`. |
| `GET /v1/gaia/version` | The terminal UI's negotiation probe. |
| `GET /v1/gaia/init` | Readiness preflight (see [above](#check-its-ready-before-you-ask-it-anything)). |
| `POST /v1/gaia/query` | Run one turn. Streams Server-Sent Events. |
| `POST /v1/gaia/query/{run_id}/cancel` | Cooperatively cancel a live run. |
| `POST /v1/gaia/query/{run_id}/respond` | Answer a mid-run `needs_input` question. |
| `POST /v1/gaia/query/{run_id}/followup` | Add to a turn already running, without interrupting it. |

`/query` implements the shared canonical SSE contract (API version **2.15**), so every stream is terminated by **exactly one** `final` or `error` event — the guarantee that lets the daemon relay and the terminal UI treat every GAIA agent identically. A few details worth knowing when you write a client:

- **You mint the `run_id`**, not the server. Cancellation keys off it, so it has to exist before the request rather than arrive in the stream.
- **Conversation context is pushed in the body**, never pulled. Pass `session_id` too — the agent persists its indexed-document set per session, and without it the agent forgets a document between the turn that indexed it and the next question.
- **Set `can_answer_questions: false` for one-shot runs.** With nobody there to answer, the agent resolves ambiguity itself instead of parking on a question that reads as a hang.
- **Idle streams emit `: keepalive` comments** every 10 seconds so a long tool call doesn't look like a dead connection.
- **A user who says something mid-turn doesn't have to wait for it.** `POST /v1/gaia/query/{run_id}/followup` with `{"text": "…"}` hands the running turn their words; the agent folds them in at its next step and answers them alongside the work in progress. Nothing is interrupted and no second turn starts. Because context is pushed rather than pulled, record a delivered follow-up in the `context` you send next turn — between that turn's question and its answer.
- **Confirmation-gated tools end the run with a refusal** — see [Tools that need your approval](#tools-that-need-your-approval).

### Authenticating your requests

Binding to loopback is not access control — this agent has shell and file tools, so an open port would let any page you visit drive it. Three checks guard the sidecar:

- **A per-session bearer token.** Every `/v1/gaia/*` request must carry `Authorization: Bearer <token>`; without it you get **401**. The process that spawned the sidecar supplies the token, either as `GAIA_GAIA_SIDECAR_TOKEN_FILE` — a path to a `0600`, owner-only file, so the secret never sits in the environment — or directly as `GAIA_GAIA_SIDECAR_TOKEN`. When the GAIA daemon runs the agent, it mints the token and uses the file channel.
- **A loopback `Host` allowlist.** A `Host` header that isn't `127.0.0.1`, `localhost`, or `::1` is **400** — this is what defeats DNS rebinding.
- **Origin rejection.** A request carrying a non-loopback browser `Origin` is **403**. Non-browser clients send no `Origin` and are unaffected.

`GET /health`, `GET /version`, and `GET /v1/gaia/version` skip the token — they're the probes a host polls before any token is in play, and none of them exposes your data. `Host` and `Origin` still apply to them.

If neither token variable is set, the sidecar starts with the token check off and says so loudly in its log; `Host` and `Origin` stay enforced. That's a **local development** convenience — a sidecar you started by hand — not something to build on. Full details, including how to supply a token when you spawn the sidecar yourself, are in the package's [SPEC.md §5.4](https://github.com/amd/gaia/blob/main/hub/agents/gaia/npm/SPEC.md).

## Troubleshooting

### "Local Lemonade Server is not reachable"

The model server isn't running. Run `gaia init` to install and start it, or point the agent at one you already have with `LEMONADE_BASE_URL`. `GET /v1/gaia/init` tells you which of the three preconditions failed (reachable / version / model present) rather than making you guess.

### "The model … is not downloaded"

```bash
gaia init
```

The hint `GET /v1/gaia/init` returns also names the pull command for whichever Lemonade client this machine has, if you'd rather pull just that one model. Then re-run the readiness check.

### "Access denied to path"

The file resolves outside the allowed paths — by default, outside your home directory — and either you denied the approval prompt or the path is one that is never granted (see [File access scope](#file-access-scope)). Approve the prompt when it appears, move the file inside the scope, or construct the agent with an `allowed_paths` list that covers it.

### The sidecar won't start

The daemon redirects the sidecar's output to `~/.gaia/agents/gaia/logs/sidecar-<port>.log`. Check that file first; a failed start also surfaces the log tail in the error. `gaia daemon agents` shows id, mode, pid, port, and contract version for everything currently running.

## Limitations (v0.1.1)

- **No skill sets declared** — the skill machinery is wired and tested, and `gaia-voice` ships always-on, but no *set* does; see [Skills](#skills).
- **Narrowing file scope requires embedding the agent** — no sidecar flag for `allowed_paths` yet.
- **No server-side confirmation flow** — over `/query`, every [confirmation-gated tool](#tools-that-need-your-approval) ends the run with a refusal instead of prompting over the stream.
- **Image generation evicts the chat model** — the SD model has to be resident to draw, so the first reply after an image waits for the chat model to reload. Ask for pictures at a natural pause, not mid-thread.
