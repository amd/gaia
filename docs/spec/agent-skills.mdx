A skill packages instructions, optional Python tools, and supporting resources for
an agent. It has no agent loop of its own. GAIA adopts the Agent Skills
`SKILL.md` structure and adds typed capabilities under `metadata.gaia`.
This reference describes the implemented Python runtime; the authoring walkthrough
is [Composing skills](/guides/composing-skills).

## Anatomy of a skill

```text
incident-review/
├── SKILL.md          # Required: YAML frontmatter followed by Markdown
├── tools.py          # Optional: declared @tool implementations
├── scripts/          # Optional supporting scripts
└── references/       # Optional documents loaded when needed
```

The minimum file is an instruction-only skill:

```yaml
---
name: incident-review
description: Review an incident timeline and draft postmortem actions after an outage.
---

Establish the timeline, separate causes from contributing factors, and draft
follow-up actions with owners.
```

Files referenced by the body are not automatically read or executed. A host must
supply any tools needed to access them.

## Field reference

| Field | Contract |
|---|---|
| `name` | Required string, at most 64 characters: lowercase alphanumeric segments separated by single hyphens. Must match the directory name when loaded from disk. |
| `description` | Required nonempty string, at most 1,024 characters. Describe requests the skill handles; this is used for relevance matching. |
| `license` | Optional string. Repository-authored skills use MIT. |
| `version` | Optional top-level SemVer string, such as `"1.0.0"`. Invalid versions fail validation. Omission means unversioned; publishing requires a version other than the reserved `0.0.0`. |
| `metadata` | Optional mapping, including arbitrary vendor namespaces. |

Unknown top-level fields, other vendor namespaces, and unknown `metadata.gaia`
fields are preserved by the parser/writer. `compatibility`, `allowed-tools`, and
`disallowed-tools` are preserved but **ignored**: they do not grant permissions or
restrict tool execution in GAIA.

### The metadata.gaia namespace

| Field | Type and default | Meaning |
|---|---|---|
| `security_tier` | String; `experimental` | `verified`, `community`, or `experimental`. A declaration is not a verified attestation. |
| `permissions` | List of strings; empty | Capability declarations using the grammar below. |
| `requirements` | Mapping; empty | Advisory model, context, runtime, dependency, environment, and hardware requirements. |
| `tools` | List of mappings; empty | Functions the skill **provides** in `tools.py`. |
| `tools_required` | List of strings; empty | Existing registry tools the instructions **consume**. Does not implement or install those tools. |

`requirements` recognizes `model`, `context`, and `python`; lists
`dependencies`, `node_dependencies`, and `env_vars`; and a `hardware` mapping.
These fields are advisory metadata, not automatic dependency installation or a
resource-enforcement contract. Binary-grant availability checks are separate.

Each `tools` entry contains a required `name`, optional `description`, a
`parameters` mapping keyed by argument name, optional `returns` mapping, and
`atomic` boolean (default `false`). Parameter mappings describe `type`,
`required`, and optionally `default`. For example:

```yaml
metadata:
  gaia:
    security_tier: experimental
    tools:
      - name: example_tool
        description: Echo the provided text
        parameters:
          text: {type: string, required: true}
        returns: {type: object}
```

This is a frontmatter fragment, not a complete skill. Its implementation must
match the declaration. See [Agent tools](/sdk/core/tools) for inferred parameter
types and decorator behavior.

## Permission model

Permissions use `<domain>:<level>[:scope]`. The grammar accepts:

| Domain | Levels | Current load behavior |
|---|---|---|
| `network` | `read`, `write`, `none` | Converted to a connector requirement; raw network scope is declarative, not an enforced egress boundary. |
| `mcp` | `connect`, `none` | Bridged to connector requirements; use a connector ID as scope. |
| `shell` | `execute`, `none` | Only a scoped binary with an implemented command policy can load. |
| `filesystem` | `read`, `write`, `none` | Non-`none` grants are refused. |
| `database` | `read`, `write`, `none` | Non-`none` grants are refused. |
| `desktop` | `control`, `none` | Non-`none` grants are refused. |
| `env` | `read`, `none` | Non-`none` grants are refused. |

`<domain>:none` grants nothing. Unsupported domain/level combinations fail
validation. Scope narrows the declaration; it is not universally an enforced
path or hostname allowlist.

For example, `shell:execute:gh` names one executable. A path, flags, or an entire
command line is invalid binary scope. An unscoped `shell:execute` is refused,
and an unknown binary policy is refused. The implemented policies live in
[`binaries.py`](https://github.com/amd/gaia/blob/main/src/gaia/skills/binaries.py).
They distinguish allowed reads, writes requiring confirmation, and refused calls.
Declaring a binary grant does not authorize every command accepted by that CLI.

`Agent.load_skill()` checks permission bridges and required binary availability
before importing tools. Connector requirements are attached to the agent instance,
and binary grants are tracked per skill. `network` scopes that do not name an
actual connector are recorded under the reserved `network` requirement; this
does **not** constrain arbitrary HTTP requests made by Python code.

<Warning>
Skill Python modules execute in the host process. GAIA does not provide a general
filesystem, process, or network sandbox for them. Declared permissions, tool
confirmation, and package signatures do not make untrusted Python safe to run.
A locally copied skill has not passed marketplace installation checks.
</Warning>

## Security tiers

Marketplace installation verifies bundle signatures and uses the lower of the
claimed tier and the signature's attested tier. Permission ceilings are then
checked before installation:

| Effective tier | Installation behavior |
|---|---|
| `experimental` | Requires `--allow-experimental`; only `network:read` and inert `none` grants fit the ceiling. |
| `community` | Publisher-signed trust; supports bridged network, MCP, and scoped shell permissions. Dangerous grants, including network writes and shell execution, require installation approval. |
| `verified` | AMD-attested trust; no additional tier ceiling, but unsupported permission bridges are still refused. |

A higher tier does not create missing enforcement capabilities. These ceilings
are enforced at **install**, not by `Agent.load_skill()` for arbitrary directories.
Local creation, import, and migration are separate from signed installation.

`gaia skill audit` produces a verdict for publishing. The publish gate binds the
verdict to the skill name, version, tier, and audited bytes. A successful audit is
not a runtime sandbox. See [Hub publishing](/guides/hub-publishing).

## Discovery and loading

`SkillManager` scans these roots in order; the first valid copy of a name wins:

| Order | Root |
|---|---|
| 1 | Agent-bundled skill directories, including explicit `Agent.SKILL_DIRS` and package-adjacent roots. |
| 2 | `~/.gaia/skills/`, honoring `GAIA_CONFIG_DIR`. |
| 3 | Project `./.claude/skills/`, then `~/.claude/skills/`, as read-only import roots. |

There is no default project-local `./.gaia/skills/` discovery root.
`skill-lock.json` records installation provenance; it is not another discovery
root. `SkillManager.shadowed()` exposes lower-precedence copies and
`discovery_errors` records invalid skill directories. `discover()` caches metadata;
`reload()` or `discover(force=True)` rescans.

```python
from gaia.skills import SkillManager

manager = SkillManager()
for skill in manager.list_skills():
    print(skill.name, "-", skill.description)
```

`manager.load(name)` reads the body and validates the skill. To activate it on an
agent, use `agent.load_skill(name, manager=manager)`. Activation registers tools,
adds requirements/grants, records the skill in `loaded_skills`, and rebuilds the
prompt. Loading an already-loaded name reactivates its body rather than importing
it twice. `agent.unload_skill(name)` removes its tools/body and revokes its binary
grants, returning whether it was loaded.

### Tool registration

The loader imports `tools.py` and registers functions under `<skill-name>/<tool>`.
Declared names, parameter names, requiredness, and inferred types must match the
`@tool` functions. Missing or undeclared tools and incompatible signatures fail
loading. On import/validation failure the loader restores the previous tool
registry; this rollback cannot undo arbitrary side effects of imported Python.

`tools_required` names existing capabilities. Direct skill loading logs inactive
consumed tools; it does not manufacture them. Declarative composition also uses
these relationships to order providers before consumers.

### Progressive disclosure

Discovery reads metadata first. Agents with proactive discovery configured score
requests against skill names/descriptions outside the prompt. A strong match can
load a skill; ambiguous candidates become a shortlist. Read-only imported skills
are not automatically proposed by that discovery path.

Loaded bodies can be selected per turn and otherwise reduced to menu entries.
Explicit activation can keep a body available for follow-up turns. Selection is
prompt management, not a permission boundary; resources remain on demand.
The base harness supplies hooks, while concrete agents configure their discovery
and body-selection policies.

## Skill sets

An agent's `gaia-agent.yaml` composes skills using:

```yaml
skills:
  - incident-review
  - name: release-checklist
    version: ">=1.0.0"
    required: false
skill_sets:
  personal: [inbox-triage]
  work: [inbox-triage, meeting-scheduling]
default_skill_set: personal
```

`skills` is always included; exactly one declared set is selected. References are
strings or mappings with `name`, optional `version`, and `required` (default
`true`). Nonempty `skill_sets` requires a valid `default_skill_set`. Selection
precedence is the constructor's `skill_set` request, the agent's
`select_skill_set()` hook, then the manifest default. Unknown names fail instead
of silently selecting another set.

Resolution checks installed versions locally and orders dependencies. Missing or
incompatible required skills and dependency cycles fail; optional unavailable
skills are logged and skipped. Startup does not download missing code. An agent
with no declarations loads no declared skills automatically.
