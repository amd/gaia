# Release Notes

Browse the full release history for GAIA below, or on [GitHub Releases](https://github.com/amd/gaia/releases). Each release includes a summary of new features, improvements, bug fixes, and upgrade instructions.

---

## Release Process

GAIA follows a **release-notes-first** workflow. All release artifacts are prepared and reviewed in a PR before the tag is pushed.

### Files to update

`main` already declares the next version: after each final, a bot PR moves
`src/gaia/version.py` to the next minor, stamps every version field that follows
it (the Agent UI package, the Terminal UI manifest, the flagship agent, which
ships at GAIA's version), and opens a notes stub. So a release PR touches three
things. Using `v0.17.0` as an example:

#### 1. `docs/releases/v0.17.0.mdx` — write the release notes

Replace the stub with the notes. The stub carries a `release-notes-stub` comment
that fails validation until it's gone.

```mdx
---
title: "v0.17.0"
description: "Short one-line summary of this release"
---

# GAIA v0.17.0 Release Notes

Summary paragraph describing the release.

## What's New

### Feature Name
Description of the feature.

## Bug Fixes

- **Description**: What was fixed

## Full Changelog

Full Changelog: [v0.16.1...v0.17.0](https://github.com/amd/gaia/compare/v0.16.1...v0.17.0)
```

**Required sections:** `## What's New` (or `## Key Changes`) and `## Full Changelog`, plus a `github.com/amd/gaia/compare/` link.

#### 2. `docs/docs.json` — list the release

Add `"releases/v0.17.0"` to the **Releases tab** pages array, after
`"releases/index"` and before the previous release:

```json
{
  "tab": "Releases",
  "groups": [{
    "group": "Release Notes",
    "pages": [
      "releases/index",
      "releases/v0.17.0",
      "releases/v0.16.1"
    ]
  }]
}
```

#### 3. Stamp the version fields

```bash
python util/release_versions.py --stamp
python util/release_versions.py --check
```

The navbar label (`v0.17.0 · Lemonade <version>`) names the newest release the
Releases tab lists, so listing the page in step 2 is what moves it. If a
squash-merge reverted `__version__` in `src/gaia/version.py`, set it back to
`0.17.0` before stamping.

### Merge, tag, push

After the PR is merged:

```bash
git tag v0.17.0
git push origin v0.17.0
```

### CI validation

The `Publish GAIA Release` workflow runs a `validate-release` job that **blocks the release** if any check fails:

| Check | What it validates |
|-------|-------------------|
| Release notes exist | `docs/releases/v0.17.0.mdx` is present |
| Version consistency | `__version__` in `src/gaia/version.py` equals `0.17.0` |
| docs.json release entry | `releases/v0.17.0` is in the Releases tab pages array |
| docs.json navbar | Navbar label contains `v0.17.0` |
| Release notes structure | Has frontmatter (`title`, `description`), required sections, and changelog link, and is no longer the stub |

If all checks pass:
- The release notes content is published to [GitHub Releases](https://github.com/amd/gaia/releases)
- The package is published to [PyPI](https://pypi.org/project/amd-gaia/)

After a final publishes, the **Next Version PR** workflow opens the PR that moves `main` to the next minor and opens its notes stub. Merge it to start the next release.
