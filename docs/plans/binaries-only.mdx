# Binaries-Only Apps

<Note>
**Status:** Plan, audited against `main` at `adcd189f2` (2026-11-02).
**Decision being planned:** the Agent UI and the TUI never install a PyPI package on a
user's PC. Everything they run is a shipped binary: the GAIA agent from
`hub.amd-gaia.ai`, and the app's own Python core, frozen.
**Related:** [Desktop Installer Plan](/plans/desktop-installer),
[Flagship Installer Plan](/plans/flagship-installer),
[Daemon Convergence](/plans/daemon-convergence), [#2014](https://github.com/amd/gaia/issues/2014),
[#5840](https://github.com/amd/gaia/issues/5840).
</Note>

## §0 Summary

Every desktop install still builds a Python environment from PyPI, and several features
still try to import the GAIA agent's Python package, which a normal install never has.

- **Installs.** The Agent UI downloads Python 3.12 and `amd-gaia[ui]` into `~/.gaia/venv`
  on first run and again on every update, then `gaia init` pip-installs the same extras a
  second time. The TUI's installers ship no `gaia` CLI at all, so its setup, daemon start,
  model links and Slack setup tell the user to run the install script, which also installs
  from PyPI.
- **In-process agent.** Chat already relays to the hub binary. `gaia -p`, background goals,
  skill preferences and the "agent not installed" message still look for the `gaia_agent`
  package and fail, or show a `pip install git+…` command, on every packaged install.
- **Why tests missed it.** A developer's `~/.gaia/venv` is an editable install of a
  checkout, so `gaia_agent` imports fine there. On the machine this audit ran on,
  `~/.gaia/venv` resolves `gaia_agent` from a worktree. Every check below must run on a
  machine with no checkout and no `~/.gaia/venv`.

The fix is a frozen `gaia` core shipped inside the Agent UI and TUI installers, every agent
turn relayed to the hub binary, and no pip remedy anywhere a user can see it. §6 orders it
into reviewable PRs.

**The goal is speed.** §5 records today's numbers as the baseline, and every conversion PR
reports its before and after against it.

**PyPI is for third-party developers building on GAIA, and only for them.** The Agent UI
and the TUI never install a PyPI package on a user's PC: not on first run, not on update,
not to repair, and not as text telling the user to.

## §4 Freezing the app

### §4.1 What has to be frozen

Both apps depend on the Python core today, not just on the agent:

- **Agent UI backend.** Electron spawns `gaia chat --ui` from the venv (`main.cjs:372`,
  located by `findGaiaBin`, `backend-installer.cjs:568`). That FastAPI server does RAG
  indexing in-process (`faiss`, `pypdf`, `pypdfium2`, office formats), so those stay in
  the core.
- **The `gaia` CLI the backend shells out to.** `gaia init` (setup and its `--check`), the
  daemon, `gaia diagnostics`, and the Agent UI MCP server. These launch as
  `sys.executable -m …`, which a frozen build can't do (D1–D3 below).
- **The TUI.** Its installers ship `gaia-tui` and `gaia-agent` only. Setup, daemon start,
  model links and Slack all call `exec.LookPath("gaia")` (D7) and fail on a TUI-only
  install.

Code that assumes an interpreter:

| # | Where | Assumption |
|---|---|---|
| D1 | `src/gaia/ui/setup_runner.py:137` | `[sys.executable, "-m", "gaia.cli", …]` |
| D2 | `src/gaia/daemon/client.py:659`; launcher identity check in `daemon/instance.py:164` | `[sys.executable, "-m", "gaia.daemon"]` |
| D3 | `src/gaia/ui/routers/mcp.py:270` | `-m gaia.mcp.servers.agent_ui_mcp` |
| D4 | `src/gaia/daemon/sidecars/manager.py:421` | `-m uvicorn` (sidecar dev mode only) |
| D5 | `init_command.py:1333` | pip extras step (A5) |
| D6 | `main.cjs:372`, `backend-installer.cjs:568` | `gaia` lives in `~/.gaia/venv`, else PATH |
| D7 | `tui/internal/daemon/client.go:365`, `gaiainit/gaiainit.go:78`, `gaiamodel/gaiamodel.go:32`, `gaiaslack/gaiaslack.go:41`, `ui/preflight/autostart.go:135` | `gaia` on PATH |

### §4.2 Reuse, don't rebuild

The flagship freeze already solves most of this, and the core freeze should copy it.

- **`hub/agents/gaia/python/packaging/freeze.py`:** PyInstaller with the ML stack excluded
  (~170 MB instead of ~2 GB), `faiss`/`keyring`/`uvicorn`/`pydantic` collected, the
  tiktoken bundle, the Linux CA runtime hook, a preflight that fails the build when a
  collect target is missing, GPL excludes, and the license and glibc checks beside it.
- **`smoke_test.py`:** boots the frozen binary and checks it answers.
- **`release_agent_gaia.yml` and `build_flagship_sidecar.yml`:** a per-platform freeze
  matrix and an approval-gated publish.
- **`hub.amd-gaia.ai` (`POST /publish`, immutable per filename) and
  `src/gaia/daemon/sidecars/fetch.py`:** the SHA-256-verified fetch, with no unverified
  fallback.

### §4.3 Recommended shape

- **One frozen `gaia` core, one-dir, shipped inside the app installers.** The entry is
  `gaia.cli:main`, so `gaia chat --ui`, `gaia daemon`, `gaia init` and `gaia diagnostics`
  are the same executable. One-dir because the CLI and daemon start often: one-file
  unpacks the whole bundle to a temp folder on every launch, and antivirus scans it each
  time.
- **Ship it inside the installers, not from the hub.** The backend is already pinned 1:1 to
  the app version (`amd-gaia[ui]==<app version>`). Bundling it makes an update one atomic
  electron-updater step, works offline, and removes A1–A4, the uv bundle and its checksums.
- **The agent stays a separate hub binary.** It updates on its own cadence, the daemon
  already supervises it, and the TUI already spawns it.
- **A frozen core never imports `gaia_agent`.** Exclude `gaia_agent`, `gaia.eval` and the
  ML stack, and add a test that the frozen build can't import them. That turns B4 and B5
  into dead code on shipped builds instead of a silent second path.
- **One self-launch helper.** It returns `[sys.executable, <subcommand>…]` when frozen and
  `[sys.executable, "-m", "gaia.cli", …]` from source. D1–D3 use it.

### §4.4 Build, release, update, size

- **Build.** A new `installer/core/freeze.py` modelled on the agent's, plus a matrix job
  (win-x64, darwin-arm64, darwin-x64, linux-x64) that the Electron and TUI installer jobs
  consume as an artifact. Smoke test: `gaia --version`,
  `gaia init --check --profile gaia --json`, `gaia daemon start` then `status`, and
  `gaia chat --ui` answering `/api/health`.
- **Release.** Built on every RC and final, like the installers. It needs no hub publish
  of its own.
- **Update.** The Agent UI updates through electron-updater alone, with no prefetch, and
  restarts the daemon when its host API changed. The TUI updates through its installers.
  The agent updates through the hub install route the Agent UI already has
  (`flagshipInstall.ts`). Today the TUI runs the `gaia-agent` it ships on PATH while the
  daemon runs `~/.gaia/agents/gaia/gaia-agent.exe`. They should resolve to one copy, or
  they drift apart on update.
- **Size.**
  - Measured here: `~/.gaia/venv` is 342 MB without GAIA's own source (editable install),
    and the one-file agent is 173 MB.
  - Expect a one-dir core of 250–350 MB on disk and roughly a third of that compressed in
    the installer. Measure it in step 7 before committing to a number.
  - The installer grows. First run no longer downloads Python, uv and the venv.
  - The core and the agent each carry a Python runtime, `faiss` and the shared deps. One
    binary that also serves the agent would save ~150 MB but tie agent updates to app
    releases. Revisit once [#5982](https://github.com/amd/gaia/pull/5982) (C++ agent)
    settles the agent's size.

### §4.5 What breaks

- **Editable dev installs keep working.** `uv pip install -e .`, `npm run dev`, and
  `start-agent-ui` still run from source. An unpackaged Electron app (`!app.isPackaged`)
  must keep using the PATH or venv `gaia`, and a `GAIA_CORE_BIN` override should point a
  packaged app at a local build.
- **`gaia eval agent` stays source-only.** It runs the agent in-process on purpose (B5,
  B10). The frozen core leaves it out. The gap: eval scores the in-process agent while
  users run the frozen binary, which differs in bundled dependencies. A later PR can add
  an option to score the sidecar binary. Until then, the agent's own smoke and judged eval
  in `release_agent_gaia.yml` are the only checks on the binary.
- **Optional extras can't be added later:** talk, browser, mcp, slack, telegram, diarize.
  Each one is either bundled and tested, or hidden in the frozen core. Per the
  "only expose what's proven" rule, nothing is offered with a pip hint.
- **Wheel-kind hub agents and custom Python agents** (`~/.gaia/agents/`, `gaia agent init`)
  have no interpreter to install into. A frozen core must refuse a wheel artifact with a
  plain message (A8, B9), never attempt `uv pip install --target`.
- **`gaia api` model `gaia`** (B8) must relay to the sidecar or be removed from the frozen
  core.
- **Upgrading from a venv install.**
  - A running `gaia chat --ui` or daemon from `~/.gaia/venv` must be stopped first. The
    existing kill-before-install logic (`main.cjs:1268`) carries over.
  - A daemon from the old venv speaks an older host API, so restart it.
  - Delete `~/.gaia/venv` only after the frozen core starts.
  - The `.deb` `postrm` message (`installer/debian/postrm:35`) names
    `~/.gaia/venv/bin/gaia` and has to change.
- **Signing and antivirus.** PyInstaller executables draw SmartScreen and antivirus false
  positives. The core needs the same signing the agent still lacks
  ([Flagship Installer Plan §9.2](/plans/flagship-installer)).

## §5 Speed baseline

Speed is why the apps go binaries-only, so the conversion is judged on measured time
from a clean machine. Six metrics, each measured the same way before and after every
conversion PR:

| # | Metric | Starts | Ends |
|---|---|---|---|
| M1 | Installer to setup screen | Installer launched | Setup screen shown (today: the backend answers `GET /api/health`) |
| M2 | Venv build | Backend install starts | `amd-gaia[ui]` installed and verified, split into uv and Python download, `uv venv`, `uv pip install`, and verify |
| M3 | `gaia init`, per step | `gaia init --profile gaia --yes --progress-json` starts | Each step's last event: Lemonade, each model download, the agent download, verify |
| M4 | Backend cold start | App launched with the backend already installed | `GET /api/health` answers |
| M5 | Agent cold start | The daemon is asked for the `gaia` sidecar | The sidecar answers its health route |
| M6 | First-chat latency | First chat message sent after setup | First token, and the finished answer, each recorded |

### §5.1 Where each number comes from

- **Clean GitHub runners (M1 proxy, M2 total, M5 proxy).** The installer journeys
  (`test_installers_headless.yml`) install each release on a fresh runner and time every
  phase. The raw samples for v0.25.4-rc3 (7 runs, 21 rows) are committed in
  [`installer/headless/baselines/binaries-only-v0.25.4-rc3.json`](https://github.com/amd/gaia/blob/main/installer/headless/baselines/binaries-only-v0.25.4-rc3.json).
  Reproduce the medians with
  `python installer/headless/propose_thresholds.py --runs 7 --release v0.25.4-rc3`.
- **A clean AMD PC (M2 split, M3, M4, M5, M6).** These need Lemonade, models and a GPU or
  NPU, which runners don't have. The PC has no GAIA, no `~/.gaia`, no uv or Python cache,
  no Hugging Face cache and no checkout, and it is idle: no eval or other model load
  running. Run each metric three times from that state and record the median and every
  sample.

### §5.4 How each conversion PR reports

- Every PR in §6 states which metrics it should move and gives before/after medians for
  those metrics, measured the same way. Use the same runner rows for CI metrics, or the
  same clean PC for hardware metrics.
- "Before" is the committed baseline, or the previous conversion PR's "after" if one
  merged since.
- A PR that makes a metric slower says so and why.
- A change that improves a metric by less than the spread of its samples doesn't count as
  a speedup.

## §7 Risks

- **Every check needs a clean machine.** Each in-process path passes on a developer box,
  because the editable venv makes `gaia_agent` importable. Steps 2–10 need a test-plan
  item on a machine or VM with no checkout and no `~/.gaia/venv`. The headless installer
  journeys (`installer/headless/`, `test_installers_headless.yml`) are the place to add it.
- **Installer size and download time grow.** Measure in step 7. If the compressed core is
  too large, split it into a hub-fetched component with the same checksum rules as
  `fetch.py` rather than keep PyPI.
- **Frozen builds can silently lose a capability.** PyInstaller turns a missing collect
  target into a warning. The agent freeze already fails the build on a missing target; the
  core freeze must too, plus a smoke test per surface (RAG indexing, connectors keyring,
  scheduler, MCP server).
- **Two Python runtimes on disk.** The core and the agent each carry one. Accepted for now
  (§4.4).
- **Migration from venv installs** can strand a running process or a stale daemon (§4.5).
  Step 8 needs an upgrade test from the last venv-based release.
- **Eval no longer measures what ships** while it stays in-process (§4.5). Name it in
  release notes until step 11 lands.
- **The baseline is half-filled.** Until step 0 runs on a clean AMD PC, only the
  clean-runner metrics have numbers. Runners have no GPU or NPU and a datacenter network,
  so their install times run faster than a user's. Compare runner numbers only with
  runner numbers.
- **Unsigned binaries** will draw antivirus and SmartScreen warnings until signing lands.
