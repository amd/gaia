## Part A — amendments to filed issues (post as comments; do not re-file)

### #2677 — tiered delta store + tier classifier · **largest amendment**

Three changes, all reductions:

1. **Drop the tier classifier from scope.** Tier is *declared at the write site*:
   a preference-tool call is tier 0 by construction, a recipe outcome is tier 1 by
   construction, everything else is tier 3. The classifier was the second-highest
   risk item in the milestone and it buys nothing that declaration does not.
2. **Defer tier 2 (typed parameters) past v1.** Ship tiers 0, 1, 3. Tiers 0 and 1
   are *already-shipped mechanisms* needing a wire-up, not new machinery — so
   cutting them saves nothing; tier 2 is the only genuinely new one. Stated
   hypothesis to test rather than assume: *if a learned value can be read by a
   tool it is tier 0; if it cannot, prose is the only thing that can carry it —
   so tier 2 is tier 0 with an unwired tool.* A threshold as one tier-3 sentence
   costs ~20 tokens; that is not worth a grammar, a validator, and an anchoring
   dependency before a single user has taught an agent anything.
3. **Correct the acceptance criterion "tier 0 and tier 1 deltas add zero tokens."**
   Tier 0: true. Tier 1: **false** — admitting a tool renders its schema
   (`tool_loader.py:326-337`); below `DEFAULT_MAX_TOOLS = 14` that is real added
   text, net-zero only at the cap. Restate as *"tier 1 adds no prose and is
   hard-bounded by `max_tools` however much is learned."*
   Corollary worth keeping: because the loader drops registry-absent names
   (`tool_loader.py:316-323`) and never touches `_TOOL_REGISTRY`, a tier-1 delta is
   *structurally* incapable of adding a tool — the "may never add tools" invariant
   is enforced by construction.

Also: **"extend the `procedures` table" is not implementable as written.**
`when_to_use` and `markdown_body` are `NOT NULL` (`memory_store.py:286-287`,
enforced `:2580-2583`); `_nearest_enabled_procedure` would treat a delta as a
supersede target (`skill_synthesis.py:620-625`); `_rebuild_proc_faiss_index` would
inject a fragment as a complete procedure (`procedural_memory.py:80-82`). One
database, one migration chain, one lineage idiom — sibling `skill_deltas` table.
And add a `scope` column: `procedures` has none, so today scope is decided by
which DB file the host opens (email passes its own `db_path`, ChatAgent does not).

### #2678 — effective-skill resolution, prefix stability, off-states

- **"Deltas apply at session boundaries only" is necessary and insufficient.** The
  same premise is *already violated* by shipped code — #2686. Add the second rule:
  **position**, not only timing. Mixin fragments compose first (`agent.py:617-618`)
  while the volatile tools block was deliberately moved last (`:625-651`); any
  learned fragment that can change must render in that tail.
- Add an off-state row: **embedder unavailable / embeddings cleared**
  (`clear_all_embeddings`, `memory_store.py:1487`) → tier-3 retrieval dark, tiers
  0–2 unaffected. Pushing learning down the stack buys robustness, not just
  tokens.
- Note the eval-isolation item is a *pre-existing* gap, not a new requirement:
  there is no `GAIA_MEMORY_DISABLED` handling in `src/gaia/eval/` today, so a
  machine's synthesized corpus can already contaminate a baseline.

### #2679 — staged write path, trust classes, consent gate

- **"Promotion gates on empirical track record" is currently unimplementable.**
  `success_count`/`attempt_count` are written once at insert from the *cluster*
  and never incremented — `reconcile_and_store` always inserts with
  `skill_id=None` (`skill_synthesis.py:693-704`), so `put_skill`'s update branch
  (`memory_store.py:2613`, the only `UPDATE … success_count`) is unreachable.
  Add a dependency on the new outcome-attribution issue (Part B).
- **What the counters measure is not what the issue assumes.** `iter_sessions`
  increments on any tool call that did not raise (`memory_store.py:2855-2858`), so
  `MIN_SUCCESS_RATE = 0.80` reads *"80% of tool calls returned without raising"*,
  not *"the user got what they wanted."*
- Add the hard invariant that "never widen permissions" misses: **a delta may not
  introduce a new destructive action class inside an already-granted permission.**
  Operationally, deltas inherit the confirmation gate (`agent.py:152` ∪
  `hub/.../gaia_agent_email/agent.py:453`) and never bypass it.
- Trust class = `min(provenance trust, skill-capability trust)`. A delta on a skill
  carrying any local-capability permission is untrusted regardless of author.

### #2680 — rebase when the base updates · **scope reduction, accepted plainly**

**v1 should not build selective re-anchoring.** On any base content-digest change,
orphan **all** deltas for that skill, retain them, surface them once with a bulk
re-approve action. Both safety properties survive (never silently dropped, never
silently re-applied); what is given up is the *convenience* of no-user-action
re-attachment.

Reasoning is timing, not difficulty: at launch the hub has ~0 authored skills with
version history, so a re-anchor path would be built, shipped, and never exercised
— untested code guarding a rare event, which is how a silent-reapplication bug
reaches production a year later. Also: a base with no headings anchors whole-body,
so v2's worst case equals v1's normal case.

Keep in v1: **record** a full anchor (slug + digest) on every delta so it stays
rebaseable later, and prefer the anchored section when rendering. Recording is one
function; matching is the research. Move the three "genuinely unsolved" questions
to a v2 issue.

### #2681 — legibility · **one addition, and it is the important one**

Add an acceptance criterion: **a tier-0 fact with zero declared consumers is
reported as inert.** The email agent registers 59 tools and exactly one module
consumes a learned preference (`read_tools.py`), so a user can mark a sender
important and 57 tools will not care. The write succeeds, the confirmation says
"saved", and nothing changes — a silent no-op that *looks* like successful
learning. Legibility that shows a count without showing which tools honor it
displays a number that does not mean what a user reads it to mean.

### #2682 — budget, consolidation, decay

- **The budget must cover authored + learned resident content, not learned alone.**
  `Agent.get_skills_system_prompt` (PR #2669) renders every loaded skill's *full*
  body with no cap — correct for atomicity, but it means authored skills have no
  runtime ceiling at all. A well-behaved overlay can still be blamed for an
  overflow caused by the authored half.
- `last_used_at` has exactly one consumer today: a `MAX(last_used_at)` readout for
  `gaia memory status` (`memory_store.py:2017`). Decay is a scoping decision, not
  a schema change.

### #2683 — email as the reference agent · **narrow the blast radius, keep the agent**

Switching to a lower-stakes agent is the wrong fix: neither analyst nor browser
ships a tier-0 store or an outcome ledger, so proving the mechanism there means
building both from scratch; low-stakes agents have low-value learning, so the eval
delta would be unmeasurable; and nothing transfers to the agent that needs it.

Instead: **in v1, deltas may affect only read-path/classification tools**
(`triage_inbox`, `pre_scan_inbox`, `summarize_thread`) and never the write path
(`send_draft`, `send_now`, `schedule_send`, `forward_message`, `accept_invite`,
`decline_invite`, `create_event_from_email`, `trash_message`, `archive_message`).
That set is the agent's existing `CONFIRMATION_REQUIRED_TOOLS`
(`hub/.../gaia_agent_email/agent.py:453`) plus the organizing tools. So a wrong
delta mis-*ranks* rather than mis-*sends*: bad, visible, recoverable. The write
path opens in v2 gated on the correction-non-recurrence KPI holding for a release.

Also: tier 2 is deferred, so the "worked example per tier" criterion becomes three
tiers, not four.

## Part B — scopes no filed issue covers (file these three)

### B1. The learning trigger — when is a delta proposed at all? · `p1`

**Why this matters.** #2679 owns *how* a delta is written and approved; nothing
owns *when* one is proposed. "Explicit user correction only" is a policy, and a
policy with no detector never fires. The answer is not a new correction detector —
it is three signals the codebase already produces, two of which are shipped.

**Dependencies:** peer of #2679; signals 1–2 can land with the store (#2677),
signal 3 is the only piece with design risk.

**Acceptance criteria:**
- [ ] Signal 1 — a preference-setting tool call (`set_priority_sender` et al,
      `preference_tools.py:355`) writes a delta alongside the store write. The call
      *is* the correction; nothing is detected.
- [ ] Signal 2 — a recorded negative outcome (`TrustLedger.record_outcome(...,
      positive=False)`, `trust.py:358`) produces a delta *candidate* linked to its
      scope.
- [ ] Signal 3 — an explicit "remember this" affordance (a `remember_correction`
      tool the model may call only on corrective language, or a user-invoked
      command). Model-proposed, human-confirmed, so a misread costs a declined
      prompt.
- [ ] Inference from repeated behavior is **absent**, and its absence is
      documented rather than stubbed.
- [ ] Documented: GAIA does **not** adopt Hermes' "5+ tool calls" heuristic,
      because the synthesized corpus already has a stricter trigger —
      `MIN_OCCURRENCES = 3` at `MIN_SUCCESS_RATE = 0.80`
      (`skill_synthesis.py:52-55`) requires repetition *and* success, not merely
      complexity.

### B2. Outcome attribution — make the empirical gate actually count · `p1`, **blocker**

**Why this matters.** The milestone's central safety claim is "promote on measured
track record, never on model judgment." No code increments a procedure's or
delta's counters after it is stored: `reconcile_and_store` always inserts with
`skill_id=None` (`skill_synthesis.py:693-704`), making the only
`UPDATE … success_count` (`memory_store.py:2613`) unreachable. The counters
describe the sessions that *produced* the artifact, not its performance after
adoption — so a recalled procedure that fails twenty times carries the counters it
was born with. Without this, #2679's promotion gate cannot be implemented and
#2682's "consolidation gates on track record" has nothing to read.

**Dependencies:** blocks the promotion half of #2679 and #2682. Independent of the
store schema, so it can start immediately — it is a defect in shipped code as much
as a v2 prerequisite.

**Acceptance criteria:**
- [ ] A recall/resolution turn records which procedures and deltas were in context.
- [ ] A user-observable outcome (correction, undo, accepted suggestion) increments
      the right row's counters. **Not** tool-call non-error — that is available and
      nearly worthless as a quality signal (`memory_store.py:2855-2858`).
- [ ] The chosen signal is documented as *the* definition of "empirical" for the
      milestone.
- [ ] A procedure that repeatedly fails after adoption becomes eligible to be
      superseded or disabled — the property `superseded_by` was built for and that
      nothing currently exercises.
- [ ] Backward-compatible: existing rows keep their at-insert counters; no
      migration rewrites them.

### B3. Privacy, retention, and deletion of learned data · `p1`

**Why this matters.** Deltas derive from real mail. #2671 covers graduation
(private → shareable) and nothing covers the rest: where learned data lives, what
it may contain, whether it is exportable, and whether there is a
delete-everything-learned-about-me path. There is also a real conflict to settle —
archive-never-delete is right for *learning* and wrong for *erasure*.

**Dependencies:** #2677 (the store it governs), #2681 (export shares the
legibility surface).

**Acceptance criteria:**
- [ ] **A delta payload stores the lesson, never the evidence.** Provenance
      references session/turn ids (the `from_sessions` precedent,
      `skill_synthesis.py:690`), never message bodies. Cheapest and most important
      control; enforced with a test.
- [ ] Incognito (`memory.py:421-423`) suppresses delta writes, and the write path
      reports session-only honestly — the pattern `set_priority_sender`'s
      `persisted` flag already sets.
- [ ] `gaia skill deltas <name> --json` exports what is stored.
- [ ] A hard-delete path (`gaia memory forget --learned [--agent] [--skill]`)
      removes rows **and** embeddings **and** purges the FAISS index — not just the
      row, or the vector keeps answering.
- [ ] Documented split: learning retirement (supersede/revert/consolidate/decay) →
      archive, never deletes; **user-initiated erasure → genuinely deletes.**
      `gaia skill reset` is the former, so nobody discovers that "reset" left the
      content on disk.
- [ ] Documented as an open gap, not implied to be handled: **learned data is not
      encrypted at rest, and neither is today's `memory.db`.** Deltas add no new
      exposure but make the existing gap more acute, because prose can quote where a
      knowledge row paraphrases.

## Part C — milestone-level items for #2674 itself

- **Success metrics.** The umbrella has none. Three, with measurement: *correction
  non-recurrence* (≥70% of corrections stated once, from the trigger's log — the
  only claim falsifiable without a benchmark); *measured eval delta with a provably
  inert off-state* (deltas-off must equal the committed baseline exactly, deltas-on
  ≥ +5 points, 0 regressions); *cost of learning* (p100 resident tokens ≤ ceiling,
  ≤2% TTFT regression at the ceiling). Named anti-KPI: **number of things learned**
  — a system optimized for delta count manufactures deltas, and count is exactly
  what the budget exists to bound. Hermes' "20+ skills → 40% faster" is
  vendor-adjacent; directional only.
- **Define the entry gate.** "Don't start until milestone 60 ships and is
  validated" is unenforceable. Seven criteria in the spec; the real one is
  **the `SKILL.md` frontmatter and discovery roots have gone one full release cycle
  without a breaking change** — deltas anchor to the base's shape, so the shape has
  to have stopped moving. Runner-up: **≥1 skill authored by someone who did not
  write the format spec** (proves the docs, not the code).
- **Sequencing against #2672.** Adaptive skills must not ship deltas on
  capability-bearing skills before the sandbox exists. Costs nothing today — PR
  #2669's loader already refuses skills declaring local-capability permissions
  rather than loading them unenforced — and becomes a real gate the moment those
  skills become loadable.
- **Add #2676 and #2686 as explicit blockers.** Both are defects in the recall path
  every v2 tier inherits.
