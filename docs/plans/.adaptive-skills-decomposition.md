## 0b. Learned prompt content must stop rebuilding the KV-cache prefix mid-session

**Why this matters.** `_refresh_recalled_skills` runs every user turn
(`memory.py:2053`) and calls `rebuild_system_prompt()` whenever the recalled set
changes (`procedural_memory.py:418-425`). Because mixin fragments compose *first*
(`agent.py:617-618`) — while the deliberately volatile tools block was moved
*last* to protect the prefix (`agent.py:625-651`) — that invalidates the entire
KV prefix, in the most expensive position, on an NPU where re-prefill hurts most.
The docstring two lines above the refresh call even promises the prompt is "left
frozen so the LLM inference engine can reuse its KV cache" (`memory.py:2038-2039`).
Every adaptive-skills tier that renders text inherits this bug unless it is fixed
first.

**Dependencies:** none. Fixes shipped code; should land before Phase 1 of v2.

**Acceptance criteria:**
- [ ] Either (a) the recalled-procedure fragment is resolved once per session and
      not per turn, or (b) it renders in the volatile tail alongside the tools
      block — decision recorded in the issue with a measured TTFT comparison.
- [ ] A session where the recalled set changes on turn N shows no change to the
      system-prompt bytes *before* the volatile tail (asserted by test).
- [ ] A session where the recalled set does **not** change produces
      byte-identical prompts across turns (regression guard for today's
      behavior).
- [ ] `gaia eval agent` on the rag_quality / email categories shows no regression
      vs. the committed baseline.

## 1. Delta store: `skill_deltas` at schema v4 + the typed delta grammar

**Why this matters.** Everything else depends on a place to put a learned change
and a bounded vocabulary for expressing one. The review found that the existing
`procedures` table **cannot** hold delta rows: `when_to_use` and `markdown_body`
are `NOT NULL` (`memory_store.py:286-287`, enforced at `:2580-2583`) so a typed
parameter has to invent both; `_nearest_enabled_procedure` would treat a delta as
a supersede target (`skill_synthesis.py:620-625`); and `_rebuild_proc_faiss_index`
would surface a fragment as a complete proven procedure
(`procedural_memory.py:80-82`). One database, one migration chain, one lineage
idiom — two tables.

**Dependencies:** #888 (the authored base a delta attaches to). Blocks 2–7.

**Acceptance criteria:**
- [ ] `skill_deltas` created via `CREATE TABLE IF NOT EXISTS` in `_SCHEMA_SQL`
      with a v3→v4 marker bump only — the exact v2→v3 pattern
      (`memory_store.py:457-470`). No `ALTER TABLE`, no row rewrite.
- [ ] A v1, v2, and v3 database each migrate to v4 with zero rows in
      `procedures` / `knowledge` / `tool_history` modified (asserted by test).
- [ ] Store accessors `put_delta`, `search_deltas`, `supersede_delta`,
      `approve_delta`, `touch_deltas`; **no `DELETE` path anywhere**.
- [ ] Every existing `procedures` read path returns byte-identical results with
      deltas present in the DB.
- [ ] The five `kind`s (`tool-hint`, `parameter`, `exception`, `preference`,
      `example`) validate their payload shapes; an unknown `kind` or malformed
      payload is refused loudly at write time.
- [ ] `kind: fact` is **rejected** with an actionable error pointing at the
      agent's tier-0 store.
- [ ] `clear_all_embeddings` (`memory_store.py:1487`) also nulls
      `skill_deltas.embedding`.

## 2. Section anchorer: deterministic named-section addressing for `SKILL.md`

**Why this matters.** A delta anchored to a line offset is unmergeable and a
delta anchored to prose is unfindable. Anchoring needs `(section slug, section
digest)` — and nothing in the codebase splits a `SKILL.md` body into sections
today: the in-flight loader keeps it as one opaque string (`Skill.body: str`, PR
#2669 `src/gaia/skills/format.py:341`). This is new machinery and it must be
deterministic, or every delta re-anchors on a whitespace change.

**Dependencies:** #888 / PR #2669 (the `Skill` body it parses). Blocks 3, 6.

**Acceptance criteria:**
- [ ] Given a `SKILL.md` body, returns an ordered list of
      `(slug, heading, text, digest)` for every ATX heading level.
- [ ] Idempotent and whitespace-stable: reflowing a paragraph, changing trailing
      whitespace, or normalizing line endings does not change any slug.
- [ ] Duplicate headings disambiguate deterministically (e.g. `escalation-2`),
      stable across runs.
- [ ] A body with **no headings** yields a single whole-body anchor, and the
      write path warns that deltas on it are fragile.
- [ ] Round-trip fuzz test over the `tests/fixtures/skills/` corpus PR #2669
      adds.

## 3. Effective-skill resolution + off-states + `--no-learned-skills`

**Why this matters.** This is where the overlay becomes observable behavior:
`base ⊕ deltas` composed at **session start only**, rendered in a deterministic
order, with every degraded condition landing on a conservative floor. The
non-negotiable property is that the off-state is *byte-identical* to a no-delta
build — without it, per-user divergence makes behavior unreproducible and bug
reports uninterpretable.

**Dependencies:** 1, 2, 0b. Blocks 4, 5, 7, 8.

**Acceptance criteria:**
- [ ] `EffectiveSkill` composes base + active in-scope deltas with precedence
      base < `parameter` < `exception` < `preference`/`example`, and a stable
      `(tier, kind, created_at, id)` render order.
- [ ] Resolution happens once per session; a delta approved mid-session takes
      effect next session and the UI says so.
- [ ] `--no-learned-skills` (and `skills.learned_enabled = false`) short-circuits
      before any store read; the composed system prompt and the loader's
      `skill_tools` list hash-match a no-delta build.
- [ ] Tier-1 `tool-hint` deltas feed the **existing** `ToolLoader.select(skill_tools=…)`
      path (`tool_loader.py:224`, `:310`) with no loader change.
- [ ] Every row of the spec's [Off-states table](adaptive-skills.mdx) has a test:
      memory disabled, embedder down, embeddings cleared, base missing, anchor
      vanished, digest changed, payload unparseable, provenance absent, budget
      exceeded. No row produces a more-permissive result than the base.
- [ ] `gaia eval agent` forces the off-state deterministically (closes the
      pre-existing gap: no `GAIA_MEMORY_DISABLED` handling exists in
      `src/gaia/eval/` today).

## 4. Write path: tier classifier + staged proposals + consent gate

**Why this matters.** Today a prompt injection lasts one turn; a persisted delta
lasts forever. Hermes independently arrived at the same control — staged writes
with reviewable diffs behind `skills.write_approval` — which is strong evidence
the gate is the minimum viable safety control, not over-engineering. The tier
classifier is the other half: a lesson recorded as prose when a row would do is a
permanent context tax, and a lesson buried in a representation too weak to hold
it is knowledge lost.

**Dependencies:** 1, 2, 3, and **#2468** (body-injection analyzer — required
before any `observed_content` provenance is accepted). Blocks 6, 7, 8.

**Acceptance criteria:**
- [ ] Default trigger is **explicit user correction only**; inference from
      observed behavior is behind an off-by-default setting.
- [ ] The classifier routes a `fact`-shaped lesson to the agent's tier-0 store
      and writes **no** delta; an unclassifiable lesson surfaces to the user
      rather than defaulting to prose.
- [ ] Every delta lands `status = 'staged'` and is invisible to resolution until
      approved; nothing staged reaches the model.
- [ ] `observed_content` provenance lands `quarantined`, is scanned by #2468
      before display, and is **not** auto-approvable at any setting.
- [ ] A delta that would widen a permission, change `security_tier`, or introduce
      a tool name is **refused at write time** with an actionable error.
- [ ] Promotion to `active` gates on measured evidence (the
      `TrustLedger(min_samples=5, threshold=0.85)` shape,
      `hub/agents/email/python/gaia_agent_email/trust.py:345`, or the
      `success_count` dominance rule, `skill_synthesis.py:713`) — **never** on
      model judgment.
- [ ] Retirement archives (`status`/`superseded_by`); no code path deletes a
      delta row.

## 5. Inspection + control surface: `gaia skill deltas` + Agent UI panel

**Why this matters.** Reviewers of Hermes consistently single out that its
learning is *legible* — a file you can open and diff — as what makes the feature
feel real rather than claimed. Legibility is product surface, not tooling polish,
and it is also the only way a user can tell that their agent is no longer running
the shipped skill. Prioritized early, deliberately.

**Dependencies:** 3 (something to inspect), 4 (something to approve). Nice to
land alongside 4 rather than after.

**Acceptance criteria:**
- [ ] `gaia skill deltas <name>` lists active deltas with tier, kind, anchor,
      evidence, and last-used.
- [ ] `--pending` shows staged + quarantined with a **reviewable diff** of the
      effective skill with and without each delta; `--diff` shows effective vs.
      authored base; `--orphaned` lists orphans with their old anchor text.
- [ ] `gaia skill approve <id>`, `revert <id>` (archives one), `reset <name>`
      (archives all → pure base).
- [ ] The Agent UI skills panel shows a per-skill delta count, the diff view,
      approve/revert, and a visible badge when a skill runs with an overlay.
- [ ] Extends the `gaia skill` subcommand from PR #2669; no new top-level
      command.

## 6. Rebase on base update — re-anchor, visible orphaning, conflict reporting

**Why this matters.** The highest-risk item in the milestone and the one with
**no prior art anywhere**: Hermes has no authored base to update against, and
`git`'s three-way merge does not apply because a delta is typed structured data,
not a text hunk. Get this wrong and an upstream skill update either silently
discards personal learning or silently re-applies it to text that no longer means
the same thing.

**Dependencies:** 1, 2, 3, 4. Highest risk — prototype the conflict half before
committing to it.

**Acceptance criteria:**
- [ ] Base change detected by **content digest**, not by `version` (top-level
      `version` is optional in the format, so it cannot be relied on).
- [ ] Slug present + digest unchanged → silent re-anchor, `base_version`
      refreshed.
- [ ] Slug present + digest changed → re-anchored and marked `stale`, surfaced in
      inspection.
- [ ] Slug absent → `status = 'orphaned'`, **never applied, never re-anchored by
      similarity**, surfaced with the old anchor text for re-point or discard.
- [ ] Structural conflicts (same key, different value) reported for tier 1–2; for
      tier 3 report *possible* conflict without asserting a verdict.
- [ ] A base update that **narrows** a permission a delta depended on orphans
      that delta with a recorded reason — the base always wins restrictively.
- [ ] Zero deltas silently dropped and zero silently re-anchored across the test
      corpus of synthetic base updates.

## 7. Learning budget + consolidation (umbrella merge) + decay policy

**Why this matters.** `reconcile_and_store` matches one nearest neighbour and
supersedes it (`skill_synthesis.py:691-726`) — it never merges several related
items into one, so a long-lived agent accumulates near-duplicates that each
individually clear τ against a different neighbour. Hermes solves this with an
umbrella merge. Separately, `last_used_at` has been stamped on every recall since
#887 but has exactly **one** consumer: a `MAX(last_used_at)` readout for
`gaia memory status` (`memory_store.py:2017`) — so decay is a scoping decision,
not a schema change. Unbounded accumulation is untidy on a 64K window and fatal
on 32K.

**Dependencies:** 1, 3, 4 (consolidation proposals go through the same staged
gate).

**Acceptance criteria:**
- [ ] A hard resident-token ceiling for tier-2/3 deltas per agent, configurable
      in `memory_settings.json` alongside the existing `skill_synthesis` section
      (`skill_synthesis.py:107-150`).
- [ ] At the ceiling: consolidate → demote to retrieval-only → archive, in that
      order. **Never truncate a delta or a procedure body mid-step** (the #2676
      rule applies to learned content identically).
- [ ] Consolidation proposes **one** replacement for N near-identical deltas on
      the same base+anchor (and, optionally, for tightly clustered procedures)
      through the staged-diff gate — never an automatic rewrite.
- [ ] `last_used_at` becomes a ranking input for budget eviction and a surfacing
      input for consolidation; it never deactivates a user-approved delta on age
      alone.
- [ ] Tiers 0 and 1 are exempt from the budget (tier 0 never enters the prompt;
      tier 1 is already capped by `DEFAULT_MAX_TOOLS = 14`, `tool_loader.py:72`).
- [ ] A synthetic 200-delta corpus stays under the ceiling with nothing cut
      mid-step.

## 8. Email reference agent + tiered eval (the milestone-60 pattern, applied)

**Why this matters.** #2466 played this role for milestone 60 and it is what
turns an architecture into something a user can feel. The email agent is also the
only agent that already ships **both** a tier-0 store
(`preference_tools.py:63`, `:355` — sender priorities the triage tools query with
zero prompt cost) and an empirical evidence ledger (`trust.py:336`). v2's job is
to generalize those, not rebuild them. And a learning feature whose value cannot
be measured against its own off-state is not shippable.

**Dependencies:** 3, 4, 5 (and 7 for the budget assertion). Last.

**Acceptance criteria:**
- [ ] One worked delta per tier on the email agent, matching the spec's examples:
      tier 0 (priority sender → `state.db`), tier 1 (inbox-cleanup recipe →
      `skill_tools`), tier 2 (per-sender follow-up window), tier 3 (recruiter
      decline style).
- [ ] The tier-0 pattern is generalized: any agent can declare a tier-0 store and
      the classifier routes fact-shaped lessons to it.
- [ ] Two eval runs on the email category — deltas **off** (the baseline) and
      deltas **on** with a fixture set in `tests/fixtures/skill_deltas/` — with
      the difference attributable to named deltas.
- [ ] The off run's scorecard matches the committed baseline (proves the off-state
      really is inert).
- [ ] ≥70% of the fixture lessons land at tier ≤ 2 (the tier-discipline KPI).
- [ ] `README` / `SPEC` / `SKILL` / `CHANGELOG` for the email package updated
      together — a behavior change described in three docs must be corrected in
      three docs.

## Notes on issues the spec found but that are not sub-issues

- **Delta scope default (per-agent vs per-user)** is an open question, not a task.
  Today it is answered inconsistently in shipped code: tier-0 preferences are
  per-agent (`state.db`), `procedures` has no scope column
  (`memory_store.py:283-299`), the email agent passes its own `db_path`
  (`hub/agents/email/python/gaia_agent_email/agent.py:637-639`) and ChatAgent
  does not. The `scope` column in item 1 makes the choice explicit; **which
  default** needs a maintainer decision.
- **The `Skill` → `DistilledProcedure` rename** (part of #2671) is a naming
  dependency, not a sub-issue. The spec is written against the new name.
- **`gaia eval agent` memory isolation** is folded into item 3 rather than filed
  separately, because the off-state test is meaningless without it — but it is a
  *pre-existing* gap (a machine's synthesized corpus can already contaminate a
  baseline today), so it could also be filed against milestone 60.
