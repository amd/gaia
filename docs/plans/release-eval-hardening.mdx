# Release eval hardening: stress and adversarial testing

> **Status:** Proposed
>
> **Priority:** P1
>
> **Related:** [Eval design and hillclimbing](/plans/eval-hillclimbing) (judge calibration and noise, #4473–#4477),
> [Nightly benchmarks](/plans/nightly-benchmarks), [#5169](https://github.com/amd/gaia/issues/5169) (where escapes were caught),
> [#5197](https://github.com/amd/gaia/issues/5197) (release eval never compares), [#2983](https://github.com/amd/gaia/issues/2983) (no flagship release gate),
> [#883](https://github.com/amd/gaia/issues/883) (Playwright E2E)

---

## 1. The finding

**GAIA's release evals check whether a healthy model on a healthy machine gives good answers. Most of the bugs that reached users this cycle needed something unhealthy to happen first.** Examples are a second GAIA process, a dead child process, a laptop going to sleep, a busy or failing model server, or a new major version of a dependency. No release-time tier causes any of these on purpose. And no eval result can stop a release: `publish.yml` says so directly ("No eval gates this workflow").

What the last two tags show:

- **v0.25.0 shipped with 14 of 27 baselined categories flagged as regressed** against the flagship baseline (a worse status or score, or more than twice the time). The baseline is one run, so some flags may be noise, but nobody re-ran them to find out. The run passed 221 of 343 scenarios. Because the eval runs in report mode, those flags were only warnings, the run was green, and its "file an issue" job was skipped. `gaia_git` and `gaia_resilience` have no baseline, so they were never compared.
- **The RAG retrieval benchmark had been failing since 2026-10-12** ([#5490](https://github.com/amd/gaia/pull/5490)). Three RCs tagged `[skip eval]` (v0.25.0-rc17 to rc19) recorded "success" without running it. v0.25.0 then shipped with it red, and both v0.25.1 RCs published with it red.
- **The task suites' gate has nothing to compare against.** `eval/tasks/expectations/` was never committed, so every tag run prints "Not gated yet", including for the adversarial traps.
- **Automated tests found 8% of the 523 bugs that reached main** between Sep 15 and Oct 16 ([#5169](https://github.com/amd/gaia/issues/5169)). Unit tests cover 81% of lines, but they run that code against fakes. A bug that needs two processes, a second OS or a fresh machine never shows up in them.

The fix is mostly cheap. Build the fault injectors once: a fake model server you can script to fail, a harness that kills processes, a clock that can simulate sleep, and a nightly install with unpinned dependencies. Run them on hosted runners on every PR or every night. Keep the Strix Halo pool for the few checks that need a real model, and turn the final-tag eval into a verdict instead of a report.

## 5. Recommendations, by bugs caught per unit of cost

Each item names its tier and trigger. "Hosted" means GitHub-hosted runners. Strix Halo time goes only to items 8 and 9.

### 1. A fault-injecting fake model server: per PR, seconds

Promote `FakeServer` from `tests/unit/test_lemonade_retry_fake_server.py` into `gaia.testing.fault_server`: an OpenAI- and Lemonade-compatible server driven by a script. It **validates** requests against recorded real payloads, so a request the real server would reject fails here too (#5169 item 3). Faults to support: any status code, a stall before the first token or mid-stream, a dropped connection, malformed or never-ending tool calls, parallel batches, "model not loaded", context-size errors, and text claiming tests passed. Point the agent loop, the Agent UI backend, the TUI (through the sidecar) and the messaging bridges at it.

- The stream stalls after the first tool call. The turn ends **failed**, lists what ran, the UI's run status is `failed`, and the TUI exits non-zero.
- A 401 arrives after `write_file` succeeded. Each surface names its own fix (Settings > Model, `/provider`, both in the CLI) and lists the saved file.
- The model sends four parallel out-of-range `read_file` calls, then corrects them. The turn finishes with an answer.

Would have caught #5432, #5440, #5413 and #5101, and the open #5061 and #5064.

### 2. A multi-process and `kill -9` chaos suite: nightly on hosted Linux, macOS and Windows; seeded short run on PRs that touch those paths

Start a real daemon, Agent UI backend, headless TUI and sidecar on a temp `GAIA_HOME`, backed by the fault server. Kill a random process at a random, seeded point, restart, and check invariants: no reply lost without an "interrupted" notice, no orphan processes, no corrupted file in `~/.gaia`, locks released, connectors kept, port reacquired.

- Four processes run `config set`, connector refreshes and index writes for 60 s, including a folder this user can't write to on Windows. The final state matches a serial replay, and no "credentials are no longer valid" appears.
- SIGKILL the UI backend at a random point in the stream, then restart. The reply shows the interrupted notice, and a document caught mid-index shows Failed.
- Kill a sidecar between health pings. The desktop app stays up, and quitting leaves zero descendant processes.

Would have caught #5469, #5467, #5472, #5438, #5386, #5282, #5378 and #5377. About 15 minutes per OS per night.

### 3. Make the final-tag eval a verdict: config plus a little code

- Fix #5197. Commit `gaia_git` and `gaia_resilience` baselines and the task expectations from a real run. Remove the #3016 exception (that issue is closed).
- Add a `release-verdict` job that `approve-publish` waits on **for final tags only**. It fails on missing or unmeasured scenarios, and on **confirmed** regressions in a short must-not-regress set: `gaia_honesty`, `gaia_resilience`, `adversarial`, `error_recovery`, and the security and injection scenarios. Anything else that regresses needs a waiver naming the approver in the tag annotation.
- **Confirm before failing:** re-run only the scenarios that flipped from PASS to FAIL, two more times, and count a regression only if most runs fail (#4473). Compare scores against a measured noise floor: re-grade the same transcripts twice and ignore differences smaller than that spread.
- **Retry rule**: re-run a scenario that produced no work (an infra error) up to twice and record every attempt. Never re-run one that produced work.
- A final tag can't inherit a `[skip eval]` pass. It needs a measured run on its own commit, or on an RC whose diff touches no LLM-affecting path.
- Make the benchmarks self-contained: vendor the code-retrieval repositories as cached archives, so a red result means the product broke, not someone else's network.

Would have stopped v0.25.0's 14 unexamined regression flags and the three-RC retrieval hole (#5490).

### 4. Clock, standby and network shims: nightly, hosted

Replace the awake clock with a fake that can jump forward (suspend) or freeze the process for N seconds with a display-off event. Put a TCP fault proxy between GAIA and the fault server that adds latency, resets connections and black-holes traffic.

- Freeze the process for 10 minutes mid-stream with the display off. On wake, no stall error appears and the turn finishes.
- Black-hole the connection for 30 s mid-turn. The UI shows "reconnecting", then either completes or fails with a cause. It never hangs.
- A sleep that crosses a schedule window shows the missed run once.

Targets #5387, #5464, #5316, #5384 and #5391.

### 5. A dependency-drift canary: nightly, hosted, about 8 runners for 10 minutes

Matrix: Linux x64, Windows x64, macOS arm64 and **macOS x64 (Intel)** × the oldest and newest supported Python. Install from source with no lock: `--pre --upgrade`, latest of everything. Then import every module, run the `gaia init --profile chat` offline journey and a unit smoke subset. On the first failure, file an issue that diffs resolved versions against the last green night. This catches the next pymupdf, httpx or APScheduler days before an RC, not at publish.

### 6. Clean-state install and N-1 upgrade journeys: reduced at merge, full on RC (#5169 top-five item 2)

Start from an empty `GAIA_HOME` and a clean image. Install the wheel and the frozen binary on each OS, run the daemon with the fault server (or a tiny CPU model where a real one matters), and walk the TUI control API and the Agent UI MCP. For upgrades, install the last release, create sessions, memory, connectors and schedules, upgrade to the candidate, and assert everything survives and no stale sidecar keeps running.

### 7. A soak suite: nightly, hosted

Run a 200-turn tool-heavy session against the fault server, and an 8-hour daemon with schedules firing. Sample RSS, handles, threads, open files and DB size every 30 s, and fail on growth that doesn't level off.

- 200 turns with 3 MB tool results stay under the context window, and memory levels off.
- A daemon that has run for 8 hours answers `/health` within its SLO, and its log and DB rotate.

### 8. A `gaia_chaos` scenario category on Strix Halo: release tags, one lane, about 45 minutes

Only for faults that need a real model's behavior under them. A scenario-level `setup.faults` block points the agent at a fault proxy in front of the real Lemonade.

- Unload the model mid-turn. The turn recovers or fails honestly, and no deliverable is claimed that doesn't exist.
- A second front-end opens the same session mid-stream. Both show one consistent transcript.
- Overflow the context with a VLM loaded alongside. The trim-and-retry path answers from the evidence.

Add two checks to every scenario: compare the workspace before and after, and fail on unrequested writes or deletes; and search deliverables for planted secret markers. Also validate every deterministic success criterion: it must pass a known-good reference transcript and fail an untouched one and a plausible wrong one.

### 9. A hardware chaos lane: release tags, one Strix Halo machine

Wire the existing hand-run pieces into one job: `util/lemonade_restart_harness.py repro` and `stress --sessions 16`, the allowlisted live Lemonade contract tests (`test_lemonade_predownload_checks`, `test_lemonade_tokenize`, `test_lemonade_model_residency`, `test_daemon_broker_lemonade`, `test_gateway_lemonade`), and the Linux Strix Halo user-issue suite. Add a 1-hour real-model soak. All of this code already exists; it just never runs.

### 10. Housekeeping

- Port `tests/stress/test_agent_ui_stress.py` into item 2's suite as pytest, or delete it. A hand-run script nobody runs gives a false sense of coverage.
- Add hosted, fault-server-backed Playwright journeys for #883 (reload mid-stream, two tabs, backend killed, Esc versus Stop). They don't need Strix Halo.
- Give Slack and Telegram adapters a fake platform API that rate-limits and drops the socket.
- Add the #5169 test-value rule to `REVIEW.md`: a fix's test covers the *class* of bug at the layer where it lived.

### Strix Halo budget

Today a tag costs about 26 machine-hours of scenario lanes, plus ~1.5 h of task outcomes, plus code retrieval and Linux Halo. Twelve machines sit busy for 3.3 h. The proposal keeps the **full** flagship run for the first RC of a cycle and the final tag. Later RCs run only the categories mapped to changed paths, plus the must-not-regress set, plus the `gaia_chaos` lane. Items 1, 2, 4, 5, 6, 7 and 10 run on hosted runners at no Strix Halo cost. The net effect is fewer Strix Halo hours per cycle than today, with more failure modes covered.

## 6. The bulletproof bar for a final tag

A final `vX.Y.Z` tag publishes only when all of these hold on its commit:

1. **CI is green on the tag commit:** lint, unit, offline integration and CLI (already enforced).
2. **The fault-server suite (item 1) passes on all three OSes.**
3. **The chaos suite (item 2) passes on all three OSes**, plus the clock and network shims (item 4).
4. **The drift canary (item 5) passed within 24 hours on every OS and arch, Intel Mac included**, or the failing dependency is capped.
5. **Clean-state install and N-1 upgrade pass** for the wheel and the frozen binary on Windows, macOS arm64, macOS x64 and Linux (item 6).
6. **The flagship eval measured this commit,** with no missing or unmeasured scenarios and no confirmed regression in the must-not-regress set. Every other confirmed regression is waived by name.
7. **The retrieval and code-retrieval benchmarks are green or waived by name**, and none is red for a harness reason.
8. **The hardware chaos lane is green:** Lemonade restart harness, live contract tests and Linux Strix Halo user issues (item 9).

## 7. Open questions

- Should the must-not-regress set block RCs too, or only finals? Blocking RCs finds problems earlier, but costs more RC re-tags.
- Can a CPU-only tiny model on hosted runners stand in for the real model in the clean-state journeys, or does that path need Strix Point?
- Who approves a waiver, and does it belong in the tag annotation or in a committed file the gate reads?
