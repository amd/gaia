## Overview

The Agent UI SDK is the Python backend that powers the GAIA Agent UI. It provides:

- **FastAPI REST server** with session, chat, document, and memory endpoints
- **SQLite database** for persistent sessions, messages, and document metadata
- **SSE streaming** for real-time chat responses
- **RAG integration** for document Q&A
- **Memory dashboard** with knowledge browser, tool stats, and observability ([Memory SDK](/sdk/sdks/memory))
- **Pydantic models** for request/response validation

The backend runs on port `4200` by default and serves both the Electron desktop app and browser-based clients.

<Tip>
End users don't need to interact with this SDK directly — prebuilt `.exe` /
`.deb` desktop installers are on the
[GitHub Releases page](https://github.com/amd/gaia/releases), and
`npm install -g @amd-gaia/agent-ui` gives the same app on any Node-capable
platform. This page is for developers embedding or extending the backend.
See the [Agent UI guide](/guides/agent-ui#install-and-launch) for install
options.
</Tip>

## Quick Start

### Start the Server

```python
from gaia.ui.server import create_app

# Create with default database (~/.gaia/chat/gaia_chat.db)
app = create_app()

# Create with custom database path
app = create_app(db_path="/path/to/my/chat.db")

# Create with in-memory database (for testing)
app = create_app(db_path=":memory:")
```

Run with uvicorn:

```python
import uvicorn
from gaia.ui.server import create_app

app = create_app()
uvicorn.run(app, host="localhost", port=4200)
```

Or from the command line:

```bash
python -m gaia.ui.server --port 4200
```

### Use the Database Directly

```python
from gaia.ui.database import ChatDatabase

db = ChatDatabase()  # Uses default path ~/.gaia/chat/gaia_chat.db

# Create a session
session = db.create_session(title="My Chat", model="Qwen3.5-35B-A3B-GGUF")
print(f"Session ID: {session['id']}")

# Add messages
db.add_message(session["id"], "user", "Hello!")
db.add_message(session["id"], "assistant", "Hi there! How can I help?")

# Retrieve messages
messages = db.get_messages(session["id"])
for msg in messages:
    print(f"{msg['role']}: {msg['content']}")

# Clean up
db.close()
```

## Core Classes

### ChatDatabase

The persistence layer for all Agent UI data. Uses SQLite with WAL mode for concurrent read access.

```python
from gaia.ui.database import ChatDatabase, DEFAULT_DB_PATH
```

**Constructor:**

```python
class ChatDatabase:
    def __init__(self, db_path: str = None):
        """Initialize database connection.

        Args:
            db_path: Path to SQLite database file.
                     Defaults to ~/.gaia/chat/gaia_chat.db.
                     Use ":memory:" for in-memory database (testing).
        """
```

#### Session Methods

| Method | Signature | Description |
|--------|-----------|-------------|
| `create_session` | `(title?, model?, system_prompt?, document_ids?) -> Dict` | Create a new chat session |
| `get_session` | `(session_id) -> Optional[Dict]` | Get session by ID with message count and document IDs |
| `list_sessions` | `(limit=50, offset=0) -> List[Dict]` | List sessions ordered by most recently updated |
| `count_sessions` | `() -> int` | Count total sessions |
| `update_session` | `(session_id, title?, system_prompt?) -> Optional[Dict]` | Update session title and/or system prompt |
| `delete_session` | `(session_id) -> bool` | Delete a session and its messages (cascading) |
| `touch_session` | `(session_id) -> None` | Update the session's `updated_at` timestamp |

**Example:**

```python
db = ChatDatabase()

# Create session with attached documents
session = db.create_session(
    title="Project Review",
    model="Qwen3.5-35B-A3B-GGUF",
    system_prompt="You are a code review assistant.",
    document_ids=["doc-abc123"],
)

# Update title
db.update_session(session["id"], title="Sprint 42 Review")

# List recent sessions
for s in db.list_sessions(limit=10):
    print(f"{s['title']} ({s['message_count']} messages)")
```

#### Message Methods

| Method | Signature | Description |
|--------|-----------|-------------|
| `add_message` | `(session_id, role, content, rag_sources?, tokens_prompt?, tokens_completion?, model_messages?) -> int` | Add a message, returns message ID |
| `get_messages` | `(session_id, limit=100, offset=0) -> List[Dict]` | Get messages oldest-first |
| `count_messages` | `(session_id) -> int` | Count messages in a session |
| `get_context_messages` | `(session_id) -> List[Dict]` | Read ordered model history, including tool evidence; separate from UI pagination |

In-process chat and autonomous turns save the agent's `model_messages` on the
assistant or autonomous row. These contain the current turn's user message,
assistant tool calls, tool results and final answer, without duplicating prior
history or the system prompt. The nullable JSON column is added automatically to
existing databases; legacy rows retain their original text-only context.

Restoration budgets complete turns against the resolved model/device window
(including `GAIA_CTX_SIZE` and the NPU ceiling), reserving the current prompt, native tool schemas, output allowance and
2K estimated tokens of headroom. History uses at most half the resolved window.
Counts use GAIA's shared token estimator, not a guarantee against the model's
exact tokenizer. On overflow, old turns are removed in a block toward half the
history budget; the newest turn is retained if it fits. The full stored trace
remains in SQLite, and exclusions produce a warning in the backend log. When a
streamed turn hides more turns than the session's last streamed turn did (a
longer chat, or a smaller model's budget), the stream sends one `status` event
with `status: "history_cut"`, `turns` and `tokens` (the turns no longer replayed
and their estimated size), which the chat shows as an inline note. A stable cut
is not reported again. A relayed sidecar agent receives only the last 5
exchanges; its stream sends the same event once, on the turn the sixth arrives.

`get_messages` and the ordinary transcript API do not expose the internal trace.
Deleting a transcript message also deletes its evidence.


**Example:**

```python
# Add a user message
db.add_message(session_id, "user", "What does this function do?")

# Add an assistant message with RAG sources
db.add_message(
    session_id,
    "assistant",
    "This function initializes the database connection...",
    rag_sources=[
        {"document_id": "doc-123", "filename": "main.py", "chunk": "def init_db()...", "score": 0.92}
    ],
    tokens_prompt=150,
    tokens_completion=87,
)

# Retrieve conversation
messages = db.get_messages(session_id)
for msg in messages:
    print(f"[{msg['role']}] {msg['content'][:80]}...")
```

#### Document Methods

| Method | Signature | Description |
|--------|-----------|-------------|
| `add_document` | `(filename, filepath, file_hash, file_size?, chunk_count?) -> Dict` | Add document to library (deduplicates by hash) |
| `get_document` | `(doc_id) -> Optional[Dict]` | Get document by ID |
| `list_documents` | `() -> List[Dict]` | List all documents |
| `delete_document` | `(doc_id) -> bool` | Delete a document |
| `attach_document` | `(session_id, document_id) -> bool` | Attach document to session |
| `detach_document` | `(session_id, document_id) -> bool` | Detach document from session |
| `get_session_documents` | `(session_id) -> List[Dict]` | Get all documents for a session |

**Example:**

```python
import hashlib

# Add a document
doc = db.add_document(
    filename="manual.pdf",
    filepath="/home/user/docs/manual.pdf",
    file_hash=hashlib.sha256(open("manual.pdf", "rb").read()).hexdigest(),
    file_size=1_234_567,
    chunk_count=45,
)

# Attach to a session
db.attach_document(session_id, doc["id"])

# Check which documents are in a session
docs = db.get_session_documents(session_id)
for d in docs:
    print(f"{d['filename']} ({d['chunk_count']} chunks)")
```

### create_app()

Factory function that creates and configures the FastAPI application with all endpoints.

```python
from gaia.ui.server import create_app

def create_app(db_path: str = None, webui_dist: str = None) -> FastAPI:
    """Create and configure the FastAPI application.

    Args:
        db_path: Path to SQLite database.
                 None for default (~/.gaia/chat/gaia_chat.db).
                 ":memory:" for testing.
        webui_dist: Path to a prebuilt Agent UI bundle to serve as static
                 files. None falls back to the bundle that ships with the
                 installed package (used by `gaia --ui-dist`).

    Returns:
        Configured FastAPI application with all routers (agents, chat,
        documents, files, mcp, sessions, system, tunnel) registered.
    """
```

Shared state is stored on `app.state` and is accessible in tests:

```python
app = create_app(db_path=":memory:")
db        = app.state.db               # ChatDatabase
registry  = app.state.agent_registry   # AgentRegistry (see /spec/plugin-registry)
dispatch  = app.state.dispatch_queue   # background job queue
monitor   = app.state.document_monitor # watches the library for new files
```

### System

```python
class SystemStatus(BaseModel):
    """System readiness status returned by GET /api/system/status."""
    lemonade_running: bool = False
    # Why Lemonade's state is unknown, when it is; None when the probe succeeded.
    lemonade_error: Optional[str] = None
    # How the Lemonade probe ended: "ok", "down" (nothing listening),
    # "timed_out" (busy, or out of the 20 s probe budget), or "error".
    lemonade_probe: Optional[Literal["ok", "down", "timed_out", "error"]] = None

    embedding_model_loaded: bool = False

    version: str = "0.1.0"
```

```python
    """Returned by session endpoints."""
    id: str
    title: str
    created_at: str

    # The model a turn runs: custom override, agent preference, device config
```

## REST API Endpoints

Every other path serves the Agent UI page, except paths under `/api`: an unknown one returns a JSON **404** (`{"detail": "Not Found"}`), and a known one called with the wrong method returns **405**.

### System

<AccordionGroup>
  <Accordion title="GET /api/system/status">
    Check system readiness for the agent UI.

    **Response:**
    ```json
    {
      "lemonade_running": true,
      "lemonade_error": null,
      "lemonade_probe": "ok",
      "model_loaded": "Qwen3.5-35B-A3B-GGUF",
      "embedding_model_loaded": false,
      "disk_space_gb": 128.5,
      "memory_available_gb": 12.3,
      "initialized": true,
      "version": "0.1.0"
    }
    ```

    `lemonade_probe` tells clients why Lemonade is or isn't reachable: `ok`, `down` (nothing listening, so it needs starting), `timed_out` (running but busy, or the probes ran past their 20-second budget), or `error` (Lemonade answered with an error, or the probe failed some other way; see `lemonade_error`).
  </Accordion>

  <Accordion title="GET /api/health">
    Health check with database statistics.

    **Response:**
    ```json
    {
      "status": "ok",
      "service": "gaia-agent-ui",
      "stats": {
        "sessions": 12,
        "messages": 245,
        "documents": 5,
        "total_chunks": 320,
        "total_size_bytes": 15234567
      }
    }
    ```
  </Accordion>

  <Accordion title="GET /api/system/model-server">
    Which Lemonade GAIA talks to and what it runs, read from Lemonade's `/health` and `/system-info`. Always `200`: an unreachable server comes back as `reachable: false` with a one-line `error`. A field Lemonade did not report is `null`.

    **Response:**
    ```json
    {
      "reachable": true,
      "error": null,
      "base_url": "http://localhost:13305/api/v1",
      "port": 13305,
      "owner": "gaia",
      "version": "2026.41.1",
      "chat_model": {
        "name": "Qwen3.6-35B-A3B-GGUF",
        "recipe": "llamacpp",
        "device": "gpu",
        "backend": "vulkan",
        "backend_source": "lemonade_default",
        "ctx_size": 65536
      },
      "embedding_model": { "name": "embeddinggemma-300m-GGUF", "backend": "vulkan", "...": "..." },
      "default_backend": "vulkan",
      "available_backends": [
        { "name": "vulkan", "state": "installed" },
        { "name": "rocm", "state": "installable" },
        { "name": "cpu", "state": "installed" }
      ],
      "preferred_backend": null,
      "system_info_error": null
    }
    ```

    | Field | Description |
    |-------|-------------|
    | `owner` | `gaia` (GAIA's own Lemonade), `user` (another Lemonade on this PC), or `remote` |
    | `backend` | `vulkan`, `rocm`, `metal`, `cpu`, `npu`, `remote` (a cloud model), or `null` when Lemonade did not say |
    | `backend_source` | `requested` (named by the load), `launch` (read from the llama-server path), or `lemonade_default` |
    | `available_backends` | llama.cpp backends Lemonade can run here; `unsupported` ones are never listed |
    | `preferred_backend` | The saved choice; `null` means Auto |
  </Accordion>

  <Accordion title="PUT /api/system/model-server/backend">
    Save the llama.cpp backend for chat models as `llamacpp_backend` in `~/.gaia/config.json`. It applies the next time a chat model loads; the embedding model keeps its own backend.

    **Request:**
    ```json
    { "backend": "rocm" }
    ```

    `backend` is `auto` or one of the names in `available_backends`. Returns the refreshed `GET /api/system/model-server` body. `400` when the backend is not available on this machine, `503` when Lemonade is not answering.
  </Accordion>

  <Accordion title="POST /api/system/load-model">
    Trigger loading a model on the Lemonade server. Returns `202` immediately; loading proceeds in the background. Poll `GET /api/system/status` to detect when loading completes.

    **Request:**
    ```json
    {
      "model_name": "Qwen3.5-35B-A3B-GGUF",
      "ctx_size": 32768
    }
    ```

    | Field | Type | Required | Description |
    |-------|------|----------|-------------|
    | `model_name` | string | Yes | Name of the model to load. |
    | `ctx_size` | number | No | Context window size in tokens. Defaults to `32768`. |
    | `force` | boolean | No | Load even while a chat is answering. Defaults to `false`. |

    When `llamacpp_backend` is set in `~/.gaia/config.json` and the model runs on llama.cpp, the load asks Lemonade for that backend.

    The load takes the same model-slot lease and load lock a chat turn does, so it waits for another app's load instead of racing it. While a chat is answering, the request returns `409` (loading another model could cut that answer off); send it again with `"force": true` to load anyway.

    **Response (202):**
    ```json
    {
      "status": "loading",
      "model": "Qwen3.5-35B-A3B-GGUF",
      "ctx_size": 32768
    }
    ```
  </Accordion>

  <Accordion title="POST /api/system/download-model">
    Trigger downloading a model via the Lemonade server. Returns `202` immediately; the download proceeds in the background. Poll `GET /api/system/status` to detect when the model becomes available. Set `force` to `true` to re-download even if the file already exists (repairs corrupted or incomplete downloads).

    **Request:**
    ```json
    {
      "model_name": "Qwen3.5-35B-A3B-GGUF",
      "force": false
    }
    ```

    | Field | Type | Required | Description |
    |-------|------|----------|-------------|
    | `model_name` | string | Yes | Name of the model to download. |
    | `force` | boolean | No | Re-download even if the model already exists. Defaults to `false`. |

    **Response (202):**
    ```json
    {
      "status": "downloading",
      "model": "Qwen3.5-35B-A3B-GGUF"
    }
    ```
  </Accordion>

  <Accordion title="GET /api/system/work-in-progress">
    Answers still being written and documents still being indexed. The desktop app reads it when you quit, to warn that the work would be lost; nothing polls it.

    **Response (200):**
    ```json
    {
      "answers": [{ "session_id": "3f2a…", "title": "Trip plan" }],
      "indexing": [{ "document_id": "9c1d…", "filename": "report.pdf" }]
    }
    ```

    `title` or `filename` is `null` when the chat or document was deleted while it ran. `indexing` covers background uploads and the document monitor's re-indexes.
  </Accordion>

  <Accordion title="POST /api/system/unload-model">
    Unload one model from the model server to free its memory; the embedding model and any other loaded model stay. The next message loads it again. Used by the desktop tray's **Free memory**.

    **Request:**
    ```json
    { "model_name": "Gemma-4-E4B-it-GGUF" }
    ```

    **Response (200):**
    ```json
    { "status": "unloaded" }
    ```

    `409` while an answer is running or a document is indexing in this app. `422` without a `model_name`. `502` with the model server's error when it refuses.
  </Accordion>

  <Accordion title="POST /api/system/warm-up">
    Read a new chat's system prompt and tool schemas into Lemonade's prompt cache, so the first message doesn't wait on them. The UI calls this when a new chat opens. Only one warm-up runs at a time, a repeat within 30 s of a finished one does nothing, and none starts while a streamed chat turn runs. Cloud models and models that aren't downloaded are skipped, so it never starts a download or a paid request. It is also skipped when the GAIA agent runs in its daemon sidecar (a Hub install), which warms its own prompt, on a PC with under 24 GB of RAM, where the model loads with the first message instead, and before first-run setup has finished, when it would load a model setup didn't pick. Returns the warm-up state, with the `model` it loads and its `device` (`npu`, `gpu` or `cpu`) once known. `GET /api/system/warm-up` returns the same state without starting one, and `GET /api/system/status` carries it as `warm_up`.

    **Response:**
    ```json
    {
      "state": "warming",
      "elapsed_seconds": 0.0,
      "prompt_tokens": null,
      "cached_tokens": null,
      "error": null
    }
    ```

    `state` is one of `idle`, `warming`, `ready`, `failed`, or `skipped`.
  </Accordion>

  <Accordion title="GET /api/settings">
    Get current user settings including the custom model override and its status on the Lemonade server.

    **Response:**
    ```json
    {
      "custom_model": "huihui-ai/Huihui-Qwen3.5-35B-A3B-abliterated",
      "model_status": {
        "found": true,
        "downloaded": true,
        "loaded": false
      }
    }
    ```

    | Field | Type | Description |
    |-------|------|-------------|
    | `custom_model` | string or null | HuggingFace model ID overriding the default, or `null` if using the default model. |
    | `model_status` | object or null | Status of the custom model on Lemonade. `null` when no custom model is set. Contains `found` (in catalog), `downloaded` (on disk), and `loaded` (currently active). |
  </Accordion>

  <Accordion title="PUT /api/settings">
    Update user settings. Set `custom_model` to a model ID to override the default, or to an empty string / `null` to clear the override and revert to the default model.

    **Request:**

    | Field | Type | Required | Description |
    |-------|------|----------|-------------|
    | `custom_model` | string or null | No | HuggingFace model ID to use instead of the default. Empty string or `null` clears the override. |

  </Accordion>
</AccordionGroup>

  </Accordion>

### Undo a turn's file changes

Before an agent tool writes, edits, creates or deletes a file, GAIA saves the
file as it was under `<GAIA home>/snapshots/<session_id>/<turn_id>/`. The copies
live with the agent, not the UI, so any client can list and undo them.
Deleting a chat deletes its copies.

<AccordionGroup>
  <Accordion title="GET /api/sessions/{session_id}/changes">
    Every turn in the session that changed files, oldest first.

    **Response:**
    ```json
    {
      "turns": [
        {
          "turn_id": "20261016153012-1a2b3c4d",
          "message_id": 42,
          "finished_at": "2026-10-16T15:30:40+00:00",
          "restored_at": null,
          "files": [{"path": "C:\\notes\\todo.md", "change": "edited", "tool": "edit_file"}],
          "untracked": [{"kind": "shell", "detail": "npm run build", "paths": []}],
          "incomplete": true
        }
      ]
    }
    ```

    `message_id` is the assistant message that answered the turn. `change` is
    `edited`, `created` or `deleted`. `incomplete` is true when the turn ran
    something GAIA can't copy ahead of time — a shell command outside the
    read-only tier, a Python snippet or script, or an MCP tool not marked
    read-only — and `untracked` lists each one. Undo does not cover what those
    changed.
  </Accordion>

  <Accordion title="GET /api/sessions/{session_id}/changes/{turn_id}/diff">
    What the turn did to each file, as a unified diff from the copy saved
    before the turn to the copy saved when it ended. Binary files carry
    `binary: true` with `before_size` and `after_size` instead of a diff; a diff
    over 200,000 characters is cut and carries `truncated: true`.
  </Accordion>

  <Accordion title="POST /api/sessions/{session_id}/changes/{turn_id}/undo">
    Put every file the turn changed back as it was before the turn: edited and
    deleted files get their old bytes, created files are removed, and folders
    the turn created are removed when empty.

    **Request:** `{"force": false}`

    It is all or nothing. Every file is checked first; a write that fails
    part-way puts back the files already restored. Returns **409** without
    changing anything when a file changed after the turn (`detail.conflicts`
    names each one; send `"force": true` to overwrite those changes), when the
    turn was already undone, when a saved copy is damaged, when the turn never
    finished, or while a turn is running in the chat. **404** means the copies
    are gone, usually removed by the retention limit.
  </Accordion>

  <Accordion title="GET /api/sessions/{session_id}/changes/total">
    Every file the chat changed, from its state before the chat's first turn to
    its state after the last. Undone turns are left out, and a turn still
    running sets `pending` without being counted.

    **Response:**
    ```json
    {
      "files": [
        {"path": "C:\\work\\app.py", "change": "edited", "unified": "...",
         "additions": 3, "deletions": 1, "binary": false, "too_large": false,
         "truncated": false, "message_ids": [42, 47], "changed_since": null}
      ],
      "totals": {"files": 1, "additions": 3, "deletions": 1, "uncounted": 0},
      "turns": 2, "pending": false, "untracked": [], "incomplete": false
    }
    ```

    A file put back by a later turn, or created and then deleted, is not
    listed. `additions` and `deletions` are null for a binary or too-large file,
    which `totals.uncounted` counts. `changed_since` says why the file on disk no
    longer matches what the chat left (`"changed after this turn"`), or is null.
  </Accordion>

  <Accordion title="POST /api/sessions/{session_id}/changes/undo">
    Undo all: put every file the chat changed back as it was before its first
    turn, then mark every turn undone.

    **Request:** `{"force": false}`

    All or nothing, like undoing one turn: saved copies are checked, a file
    changed since the chat last touched it is a **409** with
    `detail.conflicts` unless `force` is true, and a write that fails part-way
    puts every file back. Also **409** when nothing is left to undo, when a turn
    never finished, or while a turn is running.
  </Accordion>

  <Accordion title="GET /api/sessions/{session_id}/changes/git">
    The git repositories holding the chat's changed files:
    `{"available": true, "repos": [{"root", "branch", "remote", "default_branch",
    "gh", "files", "uncommitted", "ignored", "draft": {"title", "body"},
    "pr_blocked"}]}`. `ignored` lists the chat's files git ignores; they are
    left out of `files` and never committed. `draft` is drafted from the chat's requests for the turns that changed those
    files; `pr_blocked` says why a pull request can't be opened (no `gh`, no
    remote, or on the default branch), or is null.
  </Accordion>

  <Accordion title="POST /api/sessions/{session_id}/changes/git/commit">
    **Request:** `{"root": "...", "message": "...", "confirmed": true}`

    Stages only the files the chat changed in `root` (deletions included, names
    taken literally, never as patterns) and
    commits them with `message`; other staged or changed files are left alone
    and hooks run as usual. Files git ignores are left out and returned in
    `ignored`. Returns `{"root", "commit", "files", "ignored"}`. **400**
    without `"confirmed": true`, for an empty message, for a repository in a
    folder removed from the chat, when every changed file is ignored, or when
    git refuses; **409** while a turn is
    running.
  </Accordion>

  <Accordion title="POST /api/sessions/{session_id}/changes/git/pr">
    **Request:** `{"root": "...", "title": "...", "body": "...", "confirmed": true}`

    Pushes the current branch with `--set-upstream` (never forced), then runs
    `gh pr create`. Returns `{"root", "url"}`. **400** without confirmation,
    while the chat's internet is off, on the default branch, or without `gh` or
    a remote.
  </Accordion>

  <Accordion title="GET /api/settings/undo">
    The retention limits and current use:
    `{"retention_days": 7, "max_mb": 500, "used_bytes": 18233, "turns": 3, "path": "..."}`.
    Stored as `undo_retention_days` and `undo_max_mb` in `~/.gaia/config.json`.
  </Accordion>

  <Accordion title="PUT /api/settings/undo">
    Set `retention_days` (1–365) and `max_mb` (10–100000), then remove history
    past the new limits. Turns older than the time limit go first, then the
    oldest until the total fits. The size limit never removes the newest turn.
  </Accordion>
</AccordionGroup>

### Chat

<AccordionGroup>
  <Accordion title="POST /api/chat/send">
    Send a message and receive a response. Supports both streaming (SSE) and non-streaming modes.

    From the Agent UI (`X-Gaia-Client: agent-ui`) a non-`gaia` `agent_type` is
    a **422**, and sending into a chat stored under another agent is a **409**
    ("start a new chat"). See [Flagship only](#flagship-only).

    Turns run one at a time. A streamed turn sent while another chat is working
    starts at once and waits in line inside its run, sending
    `{"type": "status", "phase": "queued", "queue_position": 1,
    "queue_waited_s": 0, "message": "Waiting for the GPU — 1st in line"}`
    whenever its place changes and again every 10 s while it waits, so the
    stream is never silent. A non-streamed turn waits up to 60 s, then gets
    **429**.

    **Request:**
    ```json
    {
      "session_id": "abc-123",
      "message": "What does this code do?",
      "document_ids": ["doc-456"],
      "stream": true
    }
    ```

    **Streaming response** (SSE events):

    When `stream: true`, the server returns a `text/event-stream` response. Each line follows the SSE format `data: <JSON>`. The `SSEOutputHandler` ([`src/gaia/ui/sse_handler.py`](https://github.com/amd/gaia/blob/main/src/gaia/ui/sse_handler.py)) bridges agent console events to the following typed events:

    **Thinking and Progress**

    | Event type | Fields | Description |
    |------------|--------|-------------|
    | `thinking` | `content` (string) | Agent reasoning or progress message. Emitted when the agent starts processing, thinks through a problem, or begins a long-running operation. |
    | `step` | `step` (int), `total` (int), `status` (string) | Agent step progress. `step` is the current step number, `total` is the step limit, and `status` is `"started"`. |
    | `status` | `status` (string), `message` (string) | General status update. `status` is one of `"working"`, `"complete"`, `"warning"`, or `"info"`. May also include `steps` (int) and `elapsed` (number) when `status` is `"complete"`. |
    | `plan` | `steps` (string[]), `step_narrations` (string[]), `current_step` (int or null) | Agent execution plan, re-sent before each step it executes. `steps` names each planned tool call with its arguments; `step_narrations` is the same list as one plain line per step (e.g. `"Reading file: notes.txt"`). `current_step` is the zero-based index of the step being executed. |

    **Tool Execution**

    | Event type | Fields | Description |
    |------------|--------|-------------|
    | `tool_start` | `tool` (string), `detail` (string), `narration` (string) | Tool invocation started. `tool` is the tool function name (e.g., `"query_documents"`, `"search_file"`). `detail` is a human-readable description of the operation. `narration` is what the call does in plain words (`"Searching your documents"`). |
    | `tool_args` | `tool` (string), `args` (object), `detail` (string), `narration` (string) | Tool arguments. `args` is the raw arguments dict passed to the tool. `detail` is a formatted human-readable summary of the arguments, one `key: value` per line when there are more than two or a value holds a list. `narration` repeats the call's plain line with its main argument (`"Searching your documents: database init"`). |
    | `tool_end` | `success` (boolean) | Tool invocation completed. |
    | `tool_result` | `title` (string or null), `summary` (string), `success` (boolean), `result_data` (object or null), `command_output` (object or null) | Tool result with structured data. `summary` is a human-readable result. `result_data` contains typed results (see below). `command_output` contains shell command output (see below). |
    | `policy_alert` | `tool` (string), `decision` (`"BLOCK"`), `reason` (string), `rule_ids` (string[]), `policy_version` (string), `receipt_id` (string, optional) | Governance policy blocked a tool before execution. No user action is required; use this to show a visible policy refusal instead of treating the denial as a generic tool failure. |

    `result_data` variants in `tool_result`:
    - **File list:** `{"type": "file_list", "files": [...], "total": int}` -- up to 20 file entries
    - **Search results:** `{"type": "search_results", "count": int, "scores": float[], "previews": string[]}` -- top 5 chunk previews (200 chars each)

    `command_output` shape in `tool_result`:
    ```json
    {
      "command": "ls -la",
      "stdout": "total 42\n...",
      "stderr": "",
      "return_code": 0,
      "expected_exit": null,
      "cwd": "/home/user/project",
      "duration_seconds": 0.15,
      "truncated": false
    }
    ```

    `success` is `false` when the tool reports `status: "error"` or a non-zero
    `return_code`. The exception is an exit the tool names in `expected_exit`,
    such as grep's exit 1 for "no match": that result stays `success: true`.

    **Response Content**

    | Event type | Fields | Description |
    |------------|--------|-------------|
    | `chunk` | `content` (string) | Incremental text fragment of the response, streamed as the LLM generates tokens. Raw tool-call JSON is automatically filtered out. |
    | `answer` | `content` (string), `elapsed` (number), `steps` (int), `tools_used` (int), `tokens` (int, optional), `ttft` (number, optional) | Final complete answer from the agent. `elapsed` is wall-clock seconds. `steps` and `tools_used` are execution totals. `tokens` is the real output-token count and `ttft` the real time-to-first-token for the run, in seconds -- both omitted entirely (never a fake `0`) when no real value was recorded. Double-escaped newlines/tabs from LLM output are automatically corrected. |
    | `agent_error` | `content` (string) | Error message from the agent. |

    **Stream Termination**

    | Event type | Fields | Description |
    |------------|--------|-------------|
    | `done` | `message_id` (int), `content` (string), `turn_summary` (object, optional) | Signals the end of the stream. `message_id` is the database ID of the saved assistant message. `content` is the full response text. `turn_summary` is the turn's sources and data flow (below); it is also saved with the message and returned by the messages endpoint. |

    **Example stream** showing a typical multi-step interaction:
    ```
    data: {"type": "thinking", "content": "Sending to Qwen3.5-35B..."}
    data: {"type": "step", "step": 1, "total": 10, "status": "started"}
    data: {"type": "tool_start", "tool": "query_documents", "detail": "Searching indexed documents for relevant content", "narration": "Searching your documents"}
    data: {"type": "tool_args", "tool": "query_documents", "args": {"query": "database init"}, "detail": "query: database init", "narration": "Searching your documents: database init"}
    data: {"type": "tool_result", "title": "Result", "summary": "Found 3 relevant chunk(s) (best score: 0.87)", "success": true, "result_data": {"type": "search_results", "count": 3, "scores": [0.87, 0.72, 0.65], "previews": ["def init_db()..."]}}
    data: {"type": "tool_end", "success": true}
    data: {"type": "chunk", "content": "This function"}
    data: {"type": "chunk", "content": " initializes"}
    data: {"type": "chunk", "content": " the database..."}
    data: {"type": "answer", "content": "This function initializes the database...", "elapsed": 3.45, "steps": 1, "tools_used": 1, "tokens": 42, "ttft": 0.81}
    data: {"type": "status", "status": "complete", "message": "Completed in 1 steps", "steps": 1, "elapsed": 3.45}
    data: {"type": "done", "message_id": 42, "content": "This function initializes the database..."}
    ```

    **`turn_summary`** describes what the turn used and where its data went. It is built from the turn's tool calls and the location of the model that answered, never assumed:

    | Field | Description |
    |-------|-------------|
    | `pages` | Web pages the turn read (`url`, `title`, `kind: "page"`). When it only searched, the search hits (`kind: "search_result"`). |
    | `documents` | Documents it drew passages from: `name` (the name the file was attached under, not the upload copy's ID), `path`, `pages`, `passages`. |
    | `files` | Files it created or changed and that still exist: `path`, `name`, `openable` (false for scripts, programs and web pages), `mtime` (when the turn ended). |
    | `sites` | Hosts GAIA's web tools contacted. |
    | `outputs` | What it made besides files, for the session panel's Outputs: `kind` (`image`, `document` indexed, `memory` saved, `schedule` created), `name`, and `path`, `detail` or `ref` (a memory's id) where they apply. |
    | `live_data` | `attempted` and `failed` counts for the internet tools. All failed means the answer has no live data. |
    | `model` | `remote`, `provider`, `provider_name`, `name`. Absent when the location could not be determined. |
    | `cost` | `kind`: `local`, `estimate` (with `usd`, at list price), or `unknown`. |
    | `error` | Set, with the rest empty, when the summary could not be built. |

    **Non-streaming response:**
    ```json
    {
      "message_id": 42,
      "content": "This function initializes the database...",
      "sources": [],
      "tokens": null
    }
    ```
  </Accordion>

  <Accordion title="GET /api/chat/active">
    Chats with a turn in flight — a run continues server-side after the user
    navigates away, so this (not an open SSE connection) is the source of
    truth for the chat list.

    ```json
    {
      "session_ids": ["a", "b"],
      "queued": ["b"],
      "awaiting_user": {"a": "permission"}
    }
    ```

    `queued` lists chats waiting for the model, next to run first.
    `awaiting_user` maps a chat paused on the user to `permission` or
    `question`.
  </Accordion>

  <Accordion title="GET /api/chat/attach">
    Re-attach to an in-flight background run and stream its events over SSE
    (`?session_id=`). Read-only — replays every event emitted so far, then

  </Accordion>

  <Accordion title="POST /api/chat/cancel">
    Cancel an active streaming turn without tearing down the HTTP connection
    — sets the SSE handler's cancelled flag and, for an email-relay turn
    parked in a blocking socket read, forces it to error out. A turn still
    waiting in line is withdrawn and ends with a cancelled `done` event.
  </Accordion>

  <Accordion title="POST /api/chat/user-input">
    Answer a mid-run `needs_input` question from the agent. Tries an

    own query loop; a session with neither pending is a 404, never a silent
    no-op accept.
  </Accordion>

  <Accordion title="POST /api/chat/followup">
    Hand `{session_id, text}` to the session's running turn. The agent reads it
    at its next step without restarting. The stream then carries
    `followup_taken` (`text`) and the message is saved as a user message. A turn
    that ends first sends `followup_returned` (`texts`) before `done`. 404: no
    turn is running. 409: the running turn can't take it yet (it hasn't reached
    the model, or a relayed agent runs it). The Agent UI calls it only when the
    user picks **Add to this reply** on a queued message; otherwise a message
    typed mid-turn waits and is sent as its own turn.
  </Accordion>

  <Accordion title="GET /api/chat/followup/{session_id}">
    What the session's last finished turn did with the follow-ups handed to it:
    `{"taken": [...], "returned": [...]}`, as the user sent them. A chat that
    was not watching when the turn ended reads this to send the returned ones
    as their own turns without resending the taken ones. Each turn replaces the
    record, and deleting the session drops it. 409 while a turn still runs.
  </Accordion>

  <Accordion title="GET /api/chat/context/{session_id}">
    Tokens the chat's next message would carry, against the model's window:
    `system`, `tools`, `documents` (results of document-reading tools),
    `history`, `reply_reserve`, `used`, `window`, plus `turns_in_view`,
    `turns_hidden` and `at_risk`, the questions of the oldest turns that leave
    the model's view at the next overflow. `skills` and `memory` are the parts
    of `system` those prompt sections take, and `tool_definitions` the part of
    `tools` the tool schemas take. `categories` lists system prompt, tool
    definitions, skills, memory, documents and messages; their `tokens` add up
    to `used`. `tool_loading` names the tools sent now (`loaded`) and the ones
    loaded only when a turn needs them (`on_demand`). `context_state` is what
    the agent moved out of the window, from its optional `context_state()`
    method: `put_away` (`results`, `tokens`: tool results swapped for a re-read
    handle) and `summarized` (`turns`, `tokens`, `summary_tokens`: older turns
    folded into a rolling summary). No agent folds turns yet, so `summarized`
    is `null` today. `context_state` is `null` when the agent doesn't report
    one; a malformed report is a 500, never a guess.

    Counts come from the loaded model's own tokenizer (Lemonade's `/tokenize`)
    when the chat's model is the one loaded: `tokenizer` is
    `{"exact": true, "model"}`. Otherwise (a cloud model, another model
    loaded, or the model server not answering) they are estimates and
    `tokenizer` is `{"exact": false, "reason"}`. Asking never loads or swaps a
    model. `{"available": false, "reason"}` until an agent has answered in the
    chat. A streaming turn sends estimates of the same numbers as a
    `context_usage` event.
  </Accordion>

  <Accordion title="GET /api/chat/performance/{session_id}">
    Where each answered turn's time went. `turns` lists each turn, oldest
    first, with `time`: `wall_seconds` (message received to answer saved),
    `model_seconds` (every model request plus any model load before the turn)
    and `gaia_seconds`, which add up to `wall_seconds`. `gaia_seconds` splits
    into `tool_seconds`, `waiting_seconds` (approving a tool) and
    `own_seconds`. Each turn also has `first_token_seconds`,
    `prefill_tokens_per_second`, `generation_tokens_per_second`, `tokens_in`,
    `tokens_new`, `tokens_cached` (reused from the server's prompt cache),
    `tokens_out`, `tool_calls`, `loads` and `cost` (`local` at $0, a cloud
    `estimate` at list price, or `unknown`). `totals` sums the chat. `now` is
    the model as Lemonade reports it: `provider` (`local`, a cloud provider,
    or `unknown`), `device`, `backend`, `ctx_size`, `weights_gb`,
    `kv_cache_gb` and `free_gb`. `latest_message_id` is the newest answer, so
    a client can tell when it has no record. A value nobody measured is
    `null`, never 0: token totals are `null` unless every model call reported
    them. Turns answered before
    this existed have no entry.
  </Accordion>

  <Accordion title="POST /api/chat/retry-with">
    Answer the chat's latest question again on another local model:
    `{session_id, message_id, model}`. Tools aren't run again; the other model
    gets the turn's recorded tool calls and results as text. Returns
    `{content, stats}`, where `stats` holds `seconds`, `load_seconds`,
    `tokens_per_second` and token counts. Nothing is saved until
    `/api/chat/retry-with/choose`. 409: the message isn't the latest answer, or
    GAIA is answering in any chat (loading another model would unload the one
    it uses). 400: a cloud model. 413: the turn doesn't fit the model's window.
    503: the model couldn't be loaded or didn't answer.
  </Accordion>

  <Accordion title="POST /api/chat/retry-with/choose">
    Keep one answer from a comparison: `{session_id, message_id, keep}`, where
    `keep` is `original` or `retry`. `retry` replaces the answer in place,
    keeping the turn's tool evidence, so the next message continues from it.
    Its stats become the retry's, keeping the turn's step count and where it
    ran. Deleting the session drops an open comparison. 404: no open
    comparison for that message.
  </Accordion>
</AccordionGroup>

### Session environment and outputs

What one chat may reach and what it produced, behind the session panel's
Environment and Outputs sections. Folder and internet changes are stored with
the chat, applied to its agent before every turn, and applied to a running
agent at once, so they take effect on its next step.

<AccordionGroup>
  <Accordion title="GET /api/sessions/{session_id}/environment">
    ```json
    {
      "session_id": "...",
      "folders": [{"path": "C:\\work", "kind": "folder", "source": "added", "removable": true}],
      "removed": ["C:\\work\\private"],
      "internet": true,
      "enforced": true
    }
    ```

    `folders` is every folder and file the agent may read and write;
    `source` is `added`, `gaia_documents`, `scratch`, `document`,
    `working_folder` or `approved` (granted during the chat). `removable` is
    false for an attached document, which leaves through the chat's document
    list. `enforced` is false for an agent that runs as its own process (a
    relayed sidecar); the folder and internet endpoints then refuse changes
    with **409** (**400** for adding a folder).
  </Accordion>

  <Accordion title="POST /api/sessions/{session_id}/environment/folders">
    **Request:** `{"path": "C:\\work\\project"}`. Let the chat read and
    write the folder. **400** for a path that isn't a folder, for a filesystem
    root, the home folder or a protected folder, and for a folder inside one
    the user removed.
  </Accordion>

  <Accordion title="POST /api/sessions/{session_id}/environment/folders/remove">
    **Request:** `{"path": "..."}`. Take a folder or file away from the chat.
    The agent's path validator then refuses everything under it, even inside a
    wider grant and under full access, and never offers it as an approval,
    until it is added back.
  </Accordion>

  <Accordion title="PUT /api/sessions/{session_id}/environment/internet">
    **Request:** `{"on": false}`. With the internet off, the agent refuses
    web tools, the in-app browser, connector (MCP) tools, and any call whose
    arguments or shell command reach a host other than this PC (for example
    `curl https://…`, `git push`, `pip install`, `npx`), before asking for
    confirmation. A web or browser call whose URL is on this PC still runs,
    as does a plain `curl`/`wget`/`Invoke-WebRequest` whose every destination
    is: `localhost` exactly or a loopback IP (`127.0.0.0/8`, `::1`). Each
    command in a chained shell line is checked on its own. The refusal tells the model the
    internet is off for this chat.
  </Accordion>

  <Accordion title="GET /api/sessions/{session_id}/outputs">
    Everything the chat produced, newest first:

    ```json
    {
      "session_id": "...",
      "items": [
        {"id": "export:47:c:\\work\\totals.csv", "kind": "export", "name": "totals.csv",
         "path": "C:\\work\\totals.csv", "detail": null, "message_id": 47,
         "created_at": "2026-10-16 20:01:12", "change": "created", "state": "present",
         "openable": true, "revealable": true}
      ]
    }
    ```

    `kind` is `file`, `export`, `image`, `document`, `memory` or `schedule`.
    A file appears once, at the latest turn that changed it. `state` is
    `undone` when Undo restored its turn and `gone` when it is no longer on
    disk. `openable` is false for scripts, programs and web pages, which only
    show in their folder. `created_at` is UTC. Built from each answer's turn
    summary (`turn_summary.outputs`) and the undo snapshots, so it survives a
    restart.
  </Accordion>
</AccordionGroup>

### Chat (advanced)

<AccordionGroup>
  <Accordion title="POST /api/chat/confirm-tool">
    Tool-confirmation handshake. When a tool in the agent's
    `confirmation_required_tools()` set (the generic base set merged with the
    agent's own `CONFIRMATION_REQUIRED_TOOLS`) makes the agent pause, the
    stream emits a `permission_request` event carrying `confirm_id` and, when
    "always allow" can be offered, `always_scope` (what the grant would cover,
    e.g. `gh issue list`). The UI answers here with allow once, always allow,
    or deny. An unanswered prompt is denied after 600 seconds.

    **Request:**
    ```json
    {
      "session_id": "abc-123",
      "approved": true,
      "always": false,
      "confirm_id": "6f1c…"
    }
    ```

    `always` (with `approved: true`) grants this exact invocation for the rest
    of the chat — see `gaia.agents.base.tool_grants`. `confirm_id` echoes the
    prompt being answered.

    **Response:** `{"status": "ok", "approved": true, "granted": "gh issue list"}`
    — `granted` is the new grant's label, or `null`.

    **Errors:** **404** when the chat has no running turn; **409** when
    `confirm_id` no longer matches the live prompt, or `always` was requested
    for a call with no scope narrow enough to grant.
  </Accordion>

  <Accordion title="GET /api/chat/permissions">
    Every chat in this backend run that has full access on or at least one
    "always allow" grant, for the Settings → Permissions pane.

    **Response:** `{"default_mode", "sessions": [{"session_id", "mode", "grants": [{"key", "label"}]}]}`
    — `default_mode` is the mode a new chat starts in: `full_access` when it is
    set in `~/.gaia/config.json`, otherwise `ask`.
  </Accordion>

  <Accordion title="GET /api/chat/permissions/{session_id}">
    One chat's permission mode (`ask` or `full_access`) and its grants. A chat
    created in this backend run starts in `ask` unless `full_access` is set in
    `~/.gaia/config.json`; a chat from an earlier run reopens in `ask`.
    Permission state lives in memory: it ends when the chat is deleted or the
    backend restarts. **404** when no such chat exists (also for `PUT` and
    `DELETE` below).
  </Accordion>

  <Accordion title="PUT /api/chat/permissions/{session_id}">
    Switch the chat between `ask` (every gated tool prompts) and `full_access`
    (gated tools run unasked and shell guardrails are lifted, as the TUI's
    `/full-access`). Takes effect on the next gated tool, including mid-turn.

    **Request:** `{"mode": "full_access"}` — any value other than `ask` or
    `full_access` is a **422**.
  </Accordion>

  <Accordion title="DELETE /api/chat/permissions/{session_id}/grants">
    Revoke one "always allow" grant (`?key=<grant key>`) or, without `key`,
    all of them. Applies to a running turn too. **404** when `key` names no
    grant in the chat. Returns the chat's permission view.
  </Accordion>

  <Accordion title="POST /api/eval/scripted-user">
    **Eval-only**, gated by `GAIA_EVAL_SCRIPTED_USER=1` (403 otherwise).
    Scripts a user who declines the shell commands in `decline_commands` and
    answers no questions, so `gaia eval agent` can score what the agent does
    after a "no". An empty list turns it off. The runner sets it from a
    scenario's `setup.decline_commands` and clears it afterwards.
  </Accordion>
</AccordionGroup>

    server runs the hardware can't be read, so `decided_after_server` is true

  <Accordion title="GET /api/setup/status">

### Lemonade server

Which Lemonade Server GAIA uses: its own, or one the user already runs. Same
choice and checks as `gaia lemonade connect` and `gaia config set lemonade_mode`.
All three routes need the `X-Gaia-UI: 1` header (**403** without it).

<AccordionGroup>
  <Accordion title="GET /api/lemonade/target">
    The server GAIA uses now and who chose it: `mode` (`gaia` or `external`),
    `saved_mode` (`null` until someone chooses), `source`, `base_url`,
    `saved_base_url`, `api_key_stored`, `env_override` (a warning when
    `LEMONADE_BASE_URL` overrides the setting), `gaia_installed`, `offer` (no
    choice saved and the environment isn't choosing, so the UI should offer the
    switch), and `what_gaia_does`. **409** when the config is unreadable or the
    saved choice is unusable; `detail` names the fix.
  </Accordion>

  <Accordion title="GET /api/lemonade/detect">
    A Lemonade the user already runs on this PC's default ports:
    `{"found": {"url", "status", "version", "minimum", "message"}}`, or
    `{"found": null}` when none answers. `status` is `ok`, `needs_key`,
    `bad_key`, `too_old`, `not_lemonade`, or `unreachable`. `unchecked` lists
    the URLs where something accepted the connection but didn't answer within
    10 s, such as a busy server. Then "none found" isn't known, and the setup
    screen offers to check again.
  </Accordion>

  <Accordion title="POST /api/lemonade/target">
    Switch servers. Body: `{"mode": "gaia" | "external", "base_url": "...",
    "api_key": "..."}`; the URL and key are only for `external`. Nothing is
    saved unless the user's server checks out. A running daemon is told to
    stop (or start) GAIA's own server, and cached agents are dropped. Returns
    the `GET` shape plus `daemon`. **422** when the server can't be used
    (`detail.message`, `detail.status`), including `status: "not_installed"`
    when switching from the user's server to GAIA's own before it is
    installed; nothing is saved. **409** for an unreadable config, **403** over
    mobile access, **502** when the daemon did not switch. A failed switch to
    GAIA's own puts the previous mode back; a failed switch to the user's
    server stays saved.
  </Accordion>
</AccordionGroup>

### Providers

Where the chat model runs: **Local**, **Fireworks AI**, or the **AMD LLM
Gateway**, all served through the local Lemonade — the TUI's `/provider`.
Keys go to the local Lemonade only and, once they discover models, into the OS
credential store (the slot the TUI uses). A key is never echoed back or logged.

<AccordionGroup>
  <Accordion title="GET /api/providers">
    Every provider with its state — `registered`, `key_source` (`environment`,
    `lemonade`, `stored`, or `null`), `models_discovered` — and the active
    model. A stored key is handed back to a Lemonade that lost it.
    `lemonade_error` is set when Lemonade could not be reached. Requires
    `X-Gaia-UI: 1` (**403** without it).
  </Accordion>

  <Accordion title="GET /api/providers/active">
    The model new turns run — the one a new chat starts on: the picked model,
    else `default_model` from `~/.gaia/config.json`, else Gemma. Carries
    `display_name`, `downloaded` for a local model (`null` for a cloud
    model or while the server starts), and `inference_remote` /
    `inference_description`: where a new chat would be answered, by the rule
    session locations use (`null` when it can't tell). With an unreadable config, `model` is
    `null` and `config_error` says why. On the first call of a backend run it also
    restores `last_model` from `~/.gaia/config.json`; `restore.status` is
    `restored`, `failed` (with the reason — another model is never switched in
    quietly), `none`, or `pending` while the local model server is still
    starting (not cached; ask again). A saved key is never sent to a Lemonade
    that is not on this PC. Requires `X-Gaia-UI: 1` (**403** without it).
  </Accordion>

  <Accordion title="POST /api/providers/{provider}/connect">
    Register a cloud provider (`fireworks` or `amd`) in Lemonade and give it
    the key. Body: `{"api_key", "base_url", "auth_header_name",
    "auth_header_prefix"}`; the last three apply to `amd` only. A blank
    `api_key` keeps the current key.

    While GAIA uses the user's own Lemonade (`lemonade_mode` `external`) it
    sends that server nothing: it succeeds only when the server already has
    the provider working, and a pasted key is not sent anywhere.

    **Errors:** **401** when the provider rejects the key or discovers no
    models (a key that discovers nothing is removed from Lemonade again);
    **403** when a key is sent through the mobile tunnel; **409** when an
    environment key takes precedence, Lemonade is not on this PC, or the
    user's own server has no working provider.
  </Accordion>

  <Accordion title="DELETE /api/providers/{provider}/key">
    Clear the key from Lemonade and from the OS credential store. Returns
    `{"removed": bool}`. On the user's own Lemonade only GAIA's stored copy is
    removed; the server keeps its key.
  </Accordion>

  <Accordion title="GET /api/providers/{provider}/models">
    Chat models for a provider (embedding, reranker, speech, and image models
    are left out). `local` lists downloaded models plus the default models
    (`Qwen3.6-35B-A3B-GGUF`, `Gemma-4-E4B-it-GGUF` and the configured default);
    cloud providers list their own. Recommended models come first with a
    `rank`, `note`, and the measured `evidence` behind the pick.

    Each local model also carries `display_name`; `state` (`loaded`,
    `downloaded` or `not_downloaded`); `placement` — `label` such as
    "GPU · Vulkan" or "NPU · FLM", with `source` `reported` (Lemonade's
    `/health` for a loaded model) or `expected` (its recipe), and a `warning`
    when the two differ; `size_gb`; `fits` this PC's memory; `available` with
    an `unavailable_reason` (no NPU, no usable backend, too large); and
    `tokens_per_second`, the median of its recent turns on this PC.
  </Accordion>

  <Accordion title="GET /api/providers/local/context">
    The context sizes a local model (the `model` query parameter) may use here: `options` from its `min` up
    to `max_fit`, the largest window that fits this PC, plus the `automatic`
    size GAIA picks, the `chosen` one (or `null`), and `loaded_ctx`. **422**
    for a cloud model.
  </Accordion>

  <Accordion title="PUT /api/providers/local/context">
    Remember a context size for a model in `~/.gaia/config.json`
    (`context_sizes`); every load of it uses that size. Body:
    `{"model", "ctx_size"}`, with `ctx_size: null` for Automatic. If the model
    is loaded, GAIA reloads it in the background through its normal load path
    (free-memory check included); `reload` says `{"started": true}`, or
    `started: false` with `reason` `already_loaded` (it is loaded at that size
    already), `busy` (a reply is running), `warm_up` (GAIA is preparing a new
    chat), `restarting`, or `not_gaias_server` (GAIA never reloads a model on a
    server it doesn't run); in the last four cases the size applies on the next
    load. **422** for a size not offered on this PC, or for a cloud model
    (nothing is saved then). A saved size that stops
    fitting, or that can't be checked because this PC's memory can't be read,
    is refused at load with how to fix it; `GAIA_CTX_SIZE` still overrides it.
  </Accordion>

  <Accordion title="GET /api/providers/local/status">
    The sidebar's live status: `state` (`loaded`, `warming`, `idle` or
    `stopped`), `owner` (`gaia`, `user` or `remote`, as in the Model server
    panel), `busy` with `busy_reason` (`request`, or `warm_up` while GAIA primes a new chat), the loaded `model` with its
    `placement` and `ctx_size`, `memory` (`free_gb`, `total_gb`, and
    `model_gb`, its estimated share; `free_gb` never exceeds `total_gb`, and
    is absent for a Lemonade on another machine), `error` with the raw cause in `error_detail`, and `restarting` /
    `restart_error`. Requires `X-Gaia-UI: 1`.
  </Accordion>

  <Accordion title="POST /api/providers/local/restart">
    Start the model server if it is stopped, else reload the loaded chat model
    (or the active one) at its context size. Returns **202**; progress shows in
    `/local/status`. On a server GAIA doesn't run, it never starts the server and
    reloads only with `{"confirm": true}`; without it the **409** explains what
    the reload would interrupt. Also **409** while a restart runs, while the
    model is answering, or while GAIA prepares a new chat (even before that
    first load lists a model); **422** for a cloud model. A server that fails
    to start is reported in `restart_error`.
  </Accordion>

  <Accordion title="POST /api/providers/select">
    Make a model the one new turns run and remember it as `last_model` /
    `last_provider` in `~/.gaia/config.json` (other keys are kept). Body:
    `{"model": "fireworks.glm-5p3-flash"}`. **409** when the model cannot run
    now; **503** while the local model server is still starting. A successful
    pick clears this run's restore notice.
  </Accordion>
</AccordionGroup>

## Security

<Note>
  The backend binds loopback and has no authentication while the tunnel is
  off, so any web page the user's browser visits could otherwise drive it.
  Three layers close that off — see
  [`src/gaia/ui/security.py`](https://github.com/amd/gaia/blob/main/src/gaia/ui/security.py)
  for the enforcing code.
</Note>

1. **CSRF header.** Every mutating (non-GET/HEAD/OPTIONS) request to `/api/*`
   or `/v1/*` must carry `X-Gaia-UI: 1`. A cross-origin page cannot set a
   custom header without triggering a CORS preflight, and the app's CORS
   policy only approves preflights from its own first-party dev origins.
   Missing the header is a `403`. Three reads with side effects carry the same
   requirement: `GET /api/setup/check`, `GET /api/providers` and
   `GET /api/providers/active`.
2. **Origin allowlist.** A mutating request whose `Origin` names anything
   other than this server, loopback, or the live tunnel is refused, so a CORS
   misconfiguration alone isn't enough to get through.
3. **Host allowlist.** DNS rebinding needs a *hostname* that resolves to
   loopback, so a `Host` that is neither an IP literal, loopback, nor the
   live tunnel is refused.

`Origin: null` and a missing `Origin` are both accepted: the packaged
Electron shell serves the SPA from `file://` (an opaque origin), and
non-browser callers send no `Origin` at all. Neither can be produced by a
cross-site page that also carries `X-Gaia-UI`, so layer 1 already stops
those.

`GAIA_UI_ALLOWED_ORIGINS` and `GAIA_UI_ALLOWED_HOSTS` (comma-separated) opt a
reverse-proxied or named-host deployment in; neither is populated by
default.

### Flagship only

The Agent UI frontend sends `X-Gaia-Client: agent-ui` and runs the GAIA agent
only. With that header, `POST /api/sessions` and `POST /api/chat/send` reject
any other `agent_type` (**422**), an omitted one becomes `gaia`, and sending
into a chat stored under another agent is a **409**. Requests without the
header — the eval harness, the MCP bridge — may still pick any registered
agent.

## Database Schema

The Agent UI uses SQLite with four tables:

```sql
-- Global document library
CREATE TABLE documents (
    id TEXT PRIMARY KEY,
    filename TEXT NOT NULL,
    filepath TEXT NOT NULL,
    file_hash TEXT UNIQUE NOT NULL,
    file_size INTEGER DEFAULT 0,
    chunk_count INTEGER DEFAULT 0,
    indexed_at TEXT,
    last_accessed_at TEXT,
    indexing_status TEXT DEFAULT 'complete',  -- pending | indexing | complete | failed | cancelled
    file_mtime REAL                          -- file modification time (Unix epoch)
);

-- Sessions (conversations)
CREATE TABLE sessions (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL DEFAULT 'New Chat',
    created_at TEXT,
    updated_at TEXT,
    model TEXT NOT NULL DEFAULT 'Qwen3.5-35B-A3B-GGUF',
    system_prompt TEXT
);

-- Many-to-many: documents attached to sessions
CREATE TABLE session_documents (
    session_id TEXT REFERENCES sessions(id) ON DELETE CASCADE,
    document_id TEXT REFERENCES documents(id) ON DELETE CASCADE,
    attached_at TEXT,
    PRIMARY KEY (session_id, document_id)
);

-- Messages
CREATE TABLE messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT REFERENCES sessions(id) ON DELETE CASCADE,
    role TEXT CHECK(role IN ('user', 'assistant', 'system')) NOT NULL,
    content TEXT NOT NULL,
    created_at TEXT,
    rag_sources TEXT,          -- JSON array of source citations
    agent_steps TEXT,          -- JSON array of agent execution steps
    inference_stats TEXT,      -- JSON blob with timing/token stats
    tokens_prompt INTEGER,
    tokens_completion INTEGER
);

-- Key/value user settings (e.g. custom_model override)
CREATE TABLE settings (
    key TEXT PRIMARY KEY,
    value TEXT
);
```

**SQLite settings:** Foreign keys enabled, WAL journal mode for concurrent reads.

<Note>
The `indexing_status`, `file_mtime`, `agent_steps`, and `inference_stats`
columns (plus the `settings` table) are added via migrations for databases
created before these existed. New databases include them in the initial schema.
</Note>

### Database Testing

```python
from gaia.ui.database import ChatDatabase

def test_session_crud():
    db = ChatDatabase(":memory:")

    # Create
    session = db.create_session(title="Test")
    assert session["title"] == "Test"

    # Read
    fetched = db.get_session(session["id"])
    assert fetched is not None

    # Update
    updated = db.update_session(session["id"], title="Updated")
    assert updated["title"] == "Updated"

    # Delete
    assert db.delete_session(session["id"]) is True
    assert db.get_session(session["id"]) is None

    db.close()

def test_message_ordering():
    db = ChatDatabase(":memory:")
    session = db.create_session()

    db.add_message(session["id"], "user", "First")
    db.add_message(session["id"], "assistant", "Second")
    db.add_message(session["id"], "user", "Third")

    messages = db.get_messages(session["id"])
    assert len(messages) == 3
    assert messages[0]["content"] == "First"
    assert messages[2]["content"] == "Third"

    db.close()
```

## Integration with the Agent

The Agent UI server delegates to the GAIA [Agent](/sdk/core/agent-system) for LLM communication and tool execution:

```python
from gaia_agent_chat.agent import ChatAgent, ChatAgentConfig

# The server creates a ChatAgent instance per request. ChatAgent derives its
# system prompt from `prompt_profile` ("chat" | "doc" | "file" | "data" |
# "web" | "full") — there is no `system_prompt` config field.
config = ChatAgentConfig(
    model_id=session.get("model", "Qwen3.5-35B-A3B-GGUF"),
    prompt_profile="doc",
    allowed_paths=["/path/to/files"],
)
agent = ChatAgent(config)

# Process a query (agent reasons, uses tools, returns response)
result = agent.process_query(message)
```

Document indexing uses the [RAG SDK](/sdk/sdks/rag):

```python
from gaia.rag.sdk import RAGSDK, RAGConfig

config = RAGConfig()
rag = RAGSDK(config)
result = rag.index_document(filepath)
chunk_count = result.get("num_chunks", 0)
```

## npm Package

GAIA Agent UI is also available as an npm package for quick installation:

```bash
npm install -g @amd-gaia/agent-ui
```

This provides the `gaia-ui` CLI command:

```bash
gaia-ui              # Start Python backend + open browser
gaia-ui --serve      # Serve frontend only (Node.js static server)
gaia-ui --port 8080  # Custom port
gaia-ui --version    # Show version
```

On first run, `gaia-ui` automatically installs the Python backend (uv, Python 3.12, amd-gaia) if not already present. On subsequent runs, it auto-updates if the version doesn't match.

### Package Contents

The npm package includes:

| Path | Description |
|------|-------------|
| `bin/gaia-ui.cjs` | CLI entry point (Node.js) |
| `dist/` | Pre-built frontend (React SPA) |

### Release Management

The package version is sourced from `src/gaia/version.py` (single source of truth for all of GAIA):

```bash
# Check version consistency (package.json matches version.py)
node installer/version/bump-ui-version.mjs --check

# Sync package.json to version.py
node installer/version/bump-ui-version.mjs

# Full release (sync, commit, tag, push)
node installer/version/release-ui.mjs
```

Tags matching `v*` trigger the automated npm publish workflow.
