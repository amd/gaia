Mixins share tool implementations between agents. Inheriting a class does not
necessarily initialize its clients, register its tools, or provide the host state
those tools expect. Start with [Build a Python Agent](/sdk/core/custom-agents) for
the base construction pattern.

## Composable mixins (registry)

`KNOWN_TOOLS` in [the registry](https://github.com/amd/gaia/blob/main/src/gaia/agents/registry.py)
is the name-to-class map used by agent scaffolding. It is not a promise that every
mixin works in a bare subclass with only a registration call.

## A complete composition example

This agent adds repository search. Save it as `research_agent.py` in the Python
environment from the [quickstart](/quickstart):

```python
from gaia.agents.base.agent import Agent
from gaia.agents.tools.code_index_tools import CodeIndexToolsMixin


class ResearchAgent(CodeIndexToolsMixin, Agent):
    def __init__(self, repo_path: str = ".", **kwargs):
        self._init_code_index_state(repo_path=repo_path)
        super().__init__(**kwargs)

    def _register_tools(self):
        self.register_code_index_tools()

    def _get_system_prompt(self) -> str:
        return (
            "Use the code index to answer questions about this repository. "
            "Index it before searching if no index exists."
        )


if __name__ == "__main__":
    agent = ResearchAgent(skip_lemonade=True, silent_mode=True)
    print(sorted(agent.get_tools_info()))
```

```bash
uv run python research_agent.py
```

In a fresh process, this lists `clear_code_index`, `get_index_status`,
`index_codebase`, and `search_code_index` without requesting inference or indexing
files. To run a real query, construct it with your repository path and a configured
backend, omitting `skip_lemonade=True`. Indexing also needs the
[code-index dependencies and embedding model](/sdk/sdks/code-index).
The configured repository is the default file-scope ceiling.

**Do not call `super()._register_tools()` when it resolves to `Agent`.** That
method is abstract and raises `NotImplementedError`. Call the concrete mixin's
registration method from your override.

## Initialization depends on the mixin

| Capability | Integration requirements |
| --- | --- |
| RAG and directory watching | Need retrieval, indexing, and watcher state from their host. Follow the working `ChatAgent` implementation; setting a `documents_path` attribute alone is insufficient. |
| File search and file I/O | Use their respective registration methods and configure the path-validation state expected by the chosen mixin. Similar names do not imply identical signatures. |
| Shell | Its constructor initializes rate limits. Preserve the cooperative constructor chain and apply the host's approval and path policies. |
| Images | `init_sd()` creates output state and registers image-generation tools. `init_vlm()` configures a vision client and registers analysis tools. These are explicit initialization methods, not automatic effects of inheritance. |
| Memory | `MemoryMixin` must precede `Agent` in the base list so its lifecycle overrides run. Call `init_memory()` before base initialization and check whether memory is available. |

There is no universal “Agent first” inheritance rule. Inspect the mixin's
constructor and overridden methods when choosing the method-resolution order.
Run a tool through its real body as well as checking that registration succeeds.

For full host integrations, see
[ChatAgent](https://github.com/amd/gaia/blob/main/hub/agents/chat/python/gaia_agent_chat/agent.py)
and [GaiaAgent](https://github.com/amd/gaia/blob/main/hub/agents/gaia/python/gaia_agent/agent.py).
Their setup, lifecycle, and path policies are part of the integration.
