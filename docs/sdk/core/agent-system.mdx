The harness connects an LLM to registered Python tools, executes a bounded reasoning
loop, and reports progress through an output handler. Use it when you need to embed
an agent or extend its behavior. To operate the terminal application, start with
[the TUI guide](/guides/terminal-hub).

## Runtime boundaries

| Layer | Responsibility | Source |
|---|---|---|
| `Agent` | Prompt composition, tool dispatch, loop limits, result and error accounting | `src/gaia/agents/base/agent.py` |
| `AgentSDK` | Model conversation requests and provider configuration | `src/gaia/chat/sdk.py` |
| Tool mixins | Optional capabilities added to an agent | `src/gaia/agents/tools/` |
| Hub agents | Concrete behavior, tools, prompts, and agent manifests | `hub/agents/` |
| Output handlers and hosts | Display, interactive decisions, session storage, cancellation transport | [Output handlers](/sdk/core/console) |

`GaiaAgent` is the flagship implementation in
`hub/agents/gaia/python/gaia_agent/agent.py`; it extends `ChatAgent` in
`hub/agents/chat/python/gaia_agent_chat/agent.py`. Neither is the base harness.
Installing the core package does not make every hub agent's dependencies available.
The TUI is a separate application; `AgentConsole` is the Python console renderer.

## Implementing an agent

`_register_tools()` is the only abstract method. `_get_system_prompt()` defaults to
an empty string, and `_create_console()` already chooses a normal or silent console.
Override them only when you need different instructions or output.

The registration pattern used in
[`examples/notes_agent.py`](https://github.com/amd/gaia/blob/main/examples/notes_agent.py)
captures the agent instance in nested tool functions. The complete example includes
the database setup and tool bodies:

```python
from examples.notes_agent import NotesAgent

agent = NotesAgent(silent_mode=True)
result = agent.process_query("List my notes", max_steps=10)
print(result["status"])
print(result["result"])
```

Run this from a source checkout with GAIA installed and a configured model backend.
It creates the example's SQLite database under `data/notes.db`.
See [Tools](/sdk/core/tools) for registration, metadata, validation, and permissions.

## Construction and turn lifecycle

Construction resolves the endpoint and, for local inference, prepares Lemonade;
creates or accepts an output handler; calls `_register_tools()`; loads declared
skills when enabled; and creates `AgentSDK`. The composed system prompt is cached
lazily. Initialize any fields your registration method needs **before** calling
`super().__init__()`.

A turn follows this sequence:

1. Bind agent identity, run `_on_task_start()`, discover skills, and refresh the active tool and skill selections.
2. Seed messages from caller-supplied `conversation_history`, then add the current request.
3. Request a model response, execute tool calls or plan steps, and feed results back into the loop.
4. Stop on an answer, a loop/step limit, an unrecoverable request error, or an observed cancellation signal.
5. Return result metadata, optionally write a trace, and run `_after_process_query()` when supplied by a mixin.

The model can use native tool calls or a prompt-based response format. The harness
selects native schemas through its backend/model capability check; do not require
JSON envelopes in every custom prompt. A prompt-based agent defaults to
`response_mode="planning"`; a subclass may set `response_mode="conversational"`
before base initialization.

The internal states are `STATE_PLANNING`, `STATE_EXECUTING_PLAN`,
`STATE_DIRECT_EXECUTION`, `STATE_ERROR_RECOVERY`, and `STATE_COMPLETION`.
These describe loop execution, not durable application workflow states.

## Configuration

| Argument | Default | Meaning |
|---|---|---|
| `model_id` | `None` | Model selection; `AgentSDK` uses `DEFAULT_MODEL_NAME` when omitted. |
| `base_url` | `None` | Resolve the configured Lemonade endpoint, including isolated runtimes. |
| `use_claude`, `use_chatgpt` | `False` | Select the corresponding cloud provider. Configure one backend per agent. |
| `claude_model` | `"claude-sonnet-5"` | Repository default for the direct Claude provider. |
| `skip_lemonade` | `False` | Skip Lemonade startup/management for another OpenAI-compatible endpoint. This does not remove the need for a running backend. |
| `max_steps` | `None` | Use `GAIA_AGENT_MAX_STEPS`, or 50 when unset. A per-query value overrides the instance limit. |
| `max_plan_iterations` | `3` | Plan/replan cycle limit; `0` means unlimited cycles, still subject to the step limit. |
| `max_consecutive_repeats` | `4` | Stop repeated identical tool calls. |
| `streaming` | `False` | Deliver model text incrementally through the handler. |
| `silent_mode` | `False` | Use the default silent handler. An explicit `output_handler` takes precedence. |
| `output_handler` | `None` | Inject the host's output/confirmation implementation. |
| `output_dir` | Current directory | Destination for trace files. |
| `debug_prompts`, `show_prompts`, `debug`, `show_stats` | `False` | Prompt capture, prompt display, debugging, and displayed statistics. |
| `min_context_size` | `32768` | Minimum context requested during local server preparation. |
| `device` | `None` | Explicit `cpu`, `gpu`, or `npu` selection, checked during local preparation. |
| `skill_set` | `None` | Declared skill-set override; invalid names fail with the available choices. |

`GAIA_AGENT_MAX_STEPS` must be a positive integer when set. The tool timeout is a
separate limit: `GAIA_AGENT_TOOL_TIMEOUT` defaults to 180 seconds and can be
overridden per tool. See [timeout and cancellation](/sdk/core/tools#timeouts-and-cancellation).

Cloud flags send requests to their respective providers and require their provider
configuration and credentials. `skip_lemonade=True` is a startup switch, not a
provider-selection flag. See [LLM SDK](/sdk/sdks/llm).

## Query and result contract

```text
Agent.process_query(
    self,
    user_input: str,
    max_steps: int = None,
    trace: bool = False,
    filename: str = None,
) -> dict
```

This is synchronous. A GUI or asynchronous host must run it outside its event loop
and forward output events through a handler.

| Result field | Meaning |
|---|---|
| `status` | `success`, `failed`, or `incomplete`; console cancellation has a separate `cancelled` result. |
| `result` | Final text, or a message explaining why the run ended. Console cancellation returns empty text. |
| `conversation` | This turn's trace entries, including tool outcomes; not a ready-to-replay chat history. |
| `system_prompt` | The composed prompt used by the agent. |
| `steps_taken`, `duration` | Loop steps and elapsed seconds. |
| `input_tokens`, `output_tokens`, `total_tokens` | Aggregated usage on the normal return path; not present on every cancellation return. |
| `error_count`, `error_history` | Recorded errors. A usable answer can still have `status="failed"` when errors were recorded. |
| `output_file` | Present when a trace was written. |
| `turn_metrics` | Present when the optional turn recorder produced metrics. |

`last_result` retains the most recent returned result. `get_error_history()` exposes
the recorded errors; the base class initializes this history at construction and
does not clear it automatically for each query. Hosts reusing an instance must
account for that when interpreting status. Not every failure becomes a result:
initialization errors and some backend recovery errors can raise to the caller.

## Conversation and context ownership

The base class reads `conversation_history` at the start of a turn, but does not
append completed turns to it automatically. Session hosts and concrete agents own
history persistence. Calling `process_query()` twice on a bare subclass does not
by itself provide durable memory. Do not assign `result["conversation"]` as chat
history without adapting its trace format to model messages.

Large structured tool results are truncated using a context/device budget and the
truncation is logged. Context-overflow recovery can replace older tool results with
explicit omission notices and shorten assistant text before a retry. This is
bounded context recovery, not durable memory or a guarantee that every earlier
result remains visible. Return focused, bounded tool results and use the relevant
memory or retrieval capabilities when the application needs persistent knowledge.

## Extension points

- `_get_system_prompt()` adds agent instructions to mixin-provided prompts. `rebuild_system_prompt()` refreshes cached composition after runtime changes.
- `_select_tools_for_turn()` and `_select_skills_for_turn()` control what is advertised for a turn. Tool selection is **not** an execution permission boundary; dispatch still uses the effective registry.
- `load_skill()`, `load_declared_skills()`, and `load_skill_set()` attach skill content and capabilities. Manifest loading and grant checks remain separate from display.
- `finalize_answer()` customizes final text. `on_first_run()` and `on_heartbeat()` are lifecycle hooks for hosts that invoke them; constructing a base agent does not start a scheduler.

Cancellation is cooperative. Hosts may expose a handler `cancelled` event; the loop
checks it during streaming. The internal `_cancel_event` is checked at step
boundaries and follows a different completion path, so callers must not assume
all stops return `status="cancelled"`. Neither mechanism forcibly terminates a
running Python tool thread. See [Output handlers](/sdk/core/console).
