`gaiacpp` is the general-purpose GAIA agent as one native binary: it reads and writes files, works through documents and data with the programs on the PC, runs shell commands, edits code and fetches web pages. It needs no Python runtime, starts instantly, and stays around 15 MB of memory through a multi-step task.

It runs five ways:

| Mode | Command | For |
|---|---|---|
| Interactive | `gaiacpp` | A person at a terminal |
| Headless | `gaiacpp -p "prompt"` | Scripts, CI, eval harnesses: answer on stdout, exit code 0 or 1 |
| Server | `gaiacpp serve` | Apps and [Lemonade](#lemonade-integration): OpenAI-compatible `/v1/chat/completions` |
| MCP server | `gaiacpp --mcp` | Another program's agent: the tools over MCP, with no model of its own |
| Stdio agent | `gaiacpp --stdio` | The [GAIA terminal UI](#running-as-the-agent-of-the-gaia-terminal-ui): queries in, JSON Lines events out |

## Quick start

Every [GAIA release](https://github.com/amd/gaia/releases), release candidates included, carries a prebuilt `gaiacpp` for each platform, stamped with the release's version:

| Platform | Binary | Archive (binary and licenses) |
|---|---|---|
| Windows x64 | `gaiacpp-windows-x64.exe` | `gaiacpp-windows-x64.zip` |
| Linux x64 | `gaiacpp-linux-x64` | `gaiacpp-linux-x64.tar.gz` |
| macOS, Apple silicon | `gaiacpp-darwin-arm64` | `gaiacpp-darwin-arm64.tar.gz` |

`gaiacpp-SHA256SUMS.txt` lists the checksum of each file. To build it yourself:

```bash
cd cpp
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --target gaiacpp
```

With Lemonade running and a model downloaded:

```bash
./build/gaiacpp -p "Summarize the CSV files in this folder" -m Qwen3.6-35B-A3B-GGUF
```

Headless runs deny tools that change things (shell, writes, web) unless you pass `--dangerously-skip-permissions`; each denial is reported on stderr.

## Choosing the model endpoint

`gaiacpp` talks to any OpenAI-compatible endpoint. Settings apply in this order, each overriding the one before:

1. Built-in defaults: Lemonade at `LEMONADE_BASE_URL`, else `http://localhost:13305/api/v1`, `Gemma-4-E4B-it-GGUF`, a 32768-token context window, 16384 output tokens and temperature 0.2
2. The settings file: `--config FILE`, else `$GAIACPP_CONFIG`, else `$XDG_CONFIG_HOME/gaiacpp/config.json` or `~/.config/gaiacpp/config.json` (`%APPDATA%\gaiacpp\config.json` on Windows) when it exists
3. Environment: `GAIA_BASE_URL`, `GAIA_MODEL_ID`, `GAIA_MAX_STEPS`, `GAIA_CONTEXT_SIZE`, `GAIA_MAX_TOKENS`
4. Flags: `--base-url`, `-m/--model`, `--provider`, `--api-key-env`, `--ctx-size`, `--max-tokens`, `--max-steps`, `--temperature`, `--native-tools`

The key for the endpoint is sent as `Authorization: Bearer`. It comes from the variable named by `--api-key-env` (or `apiKeyEnv` in the settings file), else `GAIA_API_KEY`, else `LEMONADE_API_KEY`, which is only ever sent to a loopback address (the local Lemonade). A key is never read from or written to a settings file. A variable that is named but unset stops the agent with an error instead of sending an anonymous request.

`gaiacpp` loads the model at `contextSize` only through Lemonade's `/api/v1` endpoints. Through `/v1`, or any other server, the model runs at whatever window the server gives it.

`--provider fireworks` is shorthand for Fireworks' endpoint with `FIREWORKS_API_KEY`, native tool calls and a 131072-token context window. It replaces a `contextSize` from the settings file or `GAIA_CONTEXT_SIZE`; `--ctx-size` still overrides it:

```bash
gaiacpp -p "…" --provider fireworks -m accounts/fireworks/models/deepseek-v4p1-flash
```

### Settings file

```json
{
  "baseUrl": "http://localhost:13305/api/v1",
  "modelId": "Qwen3.6-35B-A3B-GGUF",
  "contextSize": 65536,
  "apiKeyEnv": "LEMONADE_API_KEY",
  "nativeToolCalls": "always",
  "mcpConfig": "mcp.json"
}
```

Any [`AgentConfig`](/cpp/api-reference) field is accepted. `provider` (`lemonade` or `fireworks`) and `mcpConfig` (relative to the settings file) are the two extras.

### MCP servers

`--mcp-config FILE` connects every server in an `mcp.json` (`mcpServers` object). Both transports work: `command`/`args` for stdio, and `url` (or `"type": "http"`) for Streamable HTTP, such as Lemonade's own MCP server. Header values may reference variables, for example `"Authorization": "Bearer ${LEMONADE_API_KEY}"`; an unset variable is an error. An env or header value can also be `{"$keyring": "gaia.connections:<connector>:<KEY>"}`, the reference `gaia connectors` writes: `gaiacpp` reads the secret from the OS keyring (Windows Credential Manager, macOS Keychain, or the Secret Service through `secret-tool` on Linux) and keeps it in memory only. A missing secret, or a keyring that can't be reached, stops the agent with the reason. A server that fails to connect stops the agent. A server's tools become the agent's tools; when it also offers resources or prompts, the agent gets `list_mcp_resources` / `read_mcp_resource` and `list_mcp_prompts` / `get_mcp_prompt`, which name the server.

### Where the agent may work

The file, git and shell tools are confined to the working directory (`--cwd`) and any folder added with `--allow-dir DIR`. A file tool given a path outside them is refused, and so is a shell command that names an existing folder outside them, other than system folders such as `/usr`, `/etc` and `/tmp`. The prompt tells the model which folders it has. The shell check reads the command text: it stops an agent from wandering, for example a whole-disk `find` or a path a document planted, but it is not a sandbox. `--full-access` removes the confinement.

### Documents

`index_document` indexes a file or a folder: PDFs (through `pdftotext`, so each passage keeps its page number), Word `.docx`, text, Markdown and code. `query_documents` returns the passages that answer a question, with file and page. Retrieval ranks passages by keywords (BM25), and also by meaning when an embedding model is set with `--embedding-model` or `embeddingModel` in the settings file (`--provider fireworks` uses `nomic-ai/nomic-embed-text-v1.5`); the two rankings are merged. Every result says which mode produced it. A PDF with no text layer, or a file that can't be read, is reported as a failure instead of being indexed empty.

### Code

`index_codebase` indexes a project (default: the working folder), honoring `.gitignore` and skipping `.git`, `node_modules`, virtual environments, build output and files over 1 MB. `search_code` then finds code by keywords or, with an embedding model, by meaning, and returns file paths and snippets. Code has its own index, so document questions never rank source files.

### Models

With Lemonade, `gaiacpp models list` lists the server's models and `gaiacpp models pull <name>` downloads one. A built-in model is pulled by name alone; `--checkpoint` and `--recipe` register a new model and need a name starting with `user.`. Both commands use the same settings as a run and take `--base-url`, `--provider`, `--api-key-env` and `--config`.

### Images

`analyze_image` sends an image file (PNG, JPEG, GIF, WebP, BMP) to a model that accepts images and returns its answer about it: text, charts, tables, screenshots, photos. It uses the agent's own model unless `--vision-model` names another on the same endpoint. A model that can't read images is reported as an error that says to set `--vision-model`.

### Audio and image generation

`transcribe_audio` turns a recording (wav, mp3, m4a, ogg, flac, webm) into text through the endpoint's `/audio/transcriptions`, and `generate_image` saves a PNG made by `/images/generations`. Lemonade serves both. Each tool exists only when its model is set: `--transcribe-model` (for example `Whisper-Base`) and `--image-model` (for example `SDXL-Turbo`), or `transcribeModel` / `imageModel` in the settings file; `audioBaseUrl` sends transcription to a different host. A failed request is reported with the server's reason.

`--screenshots` adds `take_screenshot`, which saves the screen to a PNG in the working folder (PowerShell on Windows, `screencapture` on macOS, `grim`, `gnome-screenshot`, `scrot` or ImageMagick on Linux) for `analyze_image` to read. It is off by default and asks before each capture, because a screenshot can show anything on screen.

### Memory

`remember`, `recall`, `update_memory` and `forget` keep facts, preferences and notes across sessions in `$GAIA_HOME/memory-cpp.db` (`~/.gaia/memory-cpp.db` by default). Stored preferences are added to the prompt; other facts are found with `recall`, which searches by keyword. Text that looks like a credential is refused: API keys and tokens, a password or PIN stated outright, card numbers and security codes, and US social security numbers. The check is a backstop, not a guarantee. `forget` asks for confirmation. `--no-memory` turns memory off. The file is separate from the Python agent's memory database.

### Skills

`gaiacpp` reads the same `SKILL.md` skills as the Python agent. It lists installed skills in its prompt by name and description, and loads a skill's instructions with `load_skill` when the request calls for it. It looks in these folders, and an earlier folder's skill wins over a same-named one later (`list_skills` reports the shadowed copy):

1. `skills/` beside the `gaiacpp` binary
2. `~/.gaia/skills/` (`$GAIA_HOME/skills` when `GAIA_HOME` is set)
3. `./.claude/skills/` and `~/.claude/skills/`: loadable by name, not listed

A skill that ships Python tools (`tools.py`) loads as instructions only, and `load_skill` says so. `--no-skills` leaves skills out.

`gaiacpp skills install <name>[@version]` downloads a skill from the hub (`GAIA_HUB_URL`, default `https://hub.amd-gaia.ai`), checks the bundle against the SHA-256 the hub lists, and verifies its `SIGNATURE.json` the same way the Python runtime does: Ed25519 over every file's digest, checked against the built-in AMD key and `~/.gaia/skills/trusted-keys.json`. A signature that doesn't verify, or files that changed after signing, stop the install. The signature sets the skill's tier: AMD-signed skills are `verified`, ones signed by a key you trust are `community`, and unsigned ones or ones signed by an unknown key are `experimental`, which install only with `--allow-experimental`. `gaiacpp skills install <folder>` applies the same checks to a local folder. `gaiacpp skills list` and `gaiacpp skills remove <name>` do the rest. Installing is the user's command, not a tool the agent can call.

Installing from the hub, or from a folder that has a `SIGNATURE.json`, needs a build with OpenSSL: it does the HTTPS download, the SHA-256 check and the signature check. A build without it stops the install and says so. The release binaries include it.

## Headless runs

```bash
gaiacpp -p "prompt" --output-format json --cwd ./task
echo "prompt" | gaiacpp -p
gaiacpp --prompt-file prompt.txt
```

`--output-format json` prints one line:

```json
{"result": "…", "status": "success", "steps": 3, "tool_errors": 0,
 "model": "…", "duration_s": 5.2, "peak_rss_mb": 16.7, "cpu_s": 0.03,
 "num_steps": 3, "num_llm_calls": 3, "num_tool_calls": 2, "error_count": 0,
 "input_tokens": 14547, "cached_tokens": 8492, "output_tokens": 199,
 "peak_context_tokens": 5042,
 "usage": {"prompt_tokens": 14547, "completion_tokens": 199, "total_tokens": 14746,
           "cached_tokens": 8492, "peak_context_tokens": 5042}}
```

`status` is `success`, `error` (the model failed, the step budget ran out, or a tool-call loop was stopped) or `cancelled` (Ctrl+C). `peak_rss_mb` is the agent process's own peak memory; programs it ran are not counted. `cpu_s` is the CPU time that same process used, in seconds. Progress goes to stderr, so stdout carries only the answer. `--debug` turns on verbose logging.

The counters use the same names as `gaia -p --output-format json`, so one script can read both agents:

| Field | Meaning |
|---|---|
| `num_steps` | Turns of the agent loop (same as `steps`) |
| `num_llm_calls` | Requests sent to the model, including a closing answer after the step limit |
| `num_tool_calls` | Tools run |
| `error_count` | Tool calls that failed (same as `tool_errors`) |
| `input_tokens` | Prompt tokens, summed over every model request |
| `cached_tokens` | The part of `input_tokens` the provider served from its cache. A local model reports none, so this is 0 |
| `output_tokens` | Tokens the model wrote |
| `peak_context_tokens` | The largest single request, prompt plus reply: how full the context window got |

The token fields are 0 when the server reports no usage.

Set `GAIA_TURN_LOG` to a file path and every `-p` run also appends one JSON line to it: the same counters, plus `llm_calls` (step, seconds, and input, cached and output tokens for each request) and `tool_calls` (step, tool name, seconds, and whether it succeeded). A path that cannot be written stops the run before it starts.

With `-p` and no prompt argument, the prompt is read from stdin until it closes.

## MCP server mode

`gaiacpp --mcp` serves the agent's tools over the Model Context Protocol on stdin and stdout, so a program that already has its own agent and model can call them. No model is contacted. It answers `initialize`, `ping`, `tools/list` and `tools/call`; logs go to stderr.

```json
{"mcpServers": {"gaiacpp": {"command": "gaiacpp", "args": ["--mcp", "--cwd", "/path/to/project"]}}}
```

The folder scope and the other options apply as in a headless run. Nobody can answer an approval card over MCP, so a tool that needs approval (a shell command that changes something, a file write) is refused unless the server was started with `--dangerously-skip-permissions`.

## Server mode

```bash
SERVE_KEY=$(openssl rand -hex 32) gaiacpp serve --port 0 --server-key-env SERVE_KEY
```

Once bound, the server prints one JSON line on stdout, so a supervisor learns the port:

```json
{"event": "ready", "url": "http://127.0.0.1:41733", "model": "…", "version": "0.1.0"}
```

| Route | Purpose |
|---|---|
| `POST /v1/chat/completions` | Run the agent on the conversation. With `stream: true`, steps and tool activity arrive live as empty-delta `chat.completion.chunk`s carrying a `gaia` field, and the answer follows when the run ends |
| `GET /v1/models` | The agent's model |
| `GET /v1/tools` | The agent's tools and their parameters |
| `GET /health` | Status, version, `busy`. Open without a key, for readiness probes |
| `POST /v1/tools/:name` | Run a tool directly. Off unless `--expose-tool-routes` |

Each request carries its whole conversation, so the server keeps no state between requests. It runs one completion at a time and answers a second with 409. A client that disconnects from a stream cancels the run. A run that fails, runs out of steps or is cancelled comes back as an error (HTTP 500, or an error event on a stream) whose `code` is the run's status, with the agent's own summary as the message; it never ends with `finish_reason: "stop"`.

The server binds `127.0.0.1` and refuses to bind any other address without a key. It sends no CORS headers and rejects requests that carry an `Origin` header unless you allow that origin with `--allow-origin`, and it rejects a `Host` header that isn't `localhost` or a loopback address. A web page in the user's browser therefore can't drive the agent. Tools run without confirmation in this mode: whoever starts the server and holds its key owns that decision.

## Running as the GAIA agent in the Agent UI

`gaiacpp` can stand in for the Python flagship behind the GAIA daemon, so the Agent UI chats with it unchanged. The daemon starts an installed agent binary as `<binary> --host 127.0.0.1 --port <P>` with its token in `GAIA_GAIA_SIDECAR_TOKEN_FILE`; when that variable (or `GAIA_GAIA_SIDECAR_TOKEN`) is set, `gaiacpp` serves the flagship's sidecar API, version 2.27:

- Chat over Server-Sent Events: streamed text, tool activity, approvals with "always allow in this chat", Stop, and full access.
- Per-chat folder scope (`allowed_paths`), working folder, attached documents, memory on, private or off, and internet off. Each can change between turns, and internet and memory also apply mid-turn.
- Each chat's tools (`/sessions/{id}/tools`), its "always" answers (`/sessions/{id}/grants`), the skills list (`/skills`) and the memory list (`/memory`).

A few things answer the way an older flagship would, and the UI copes with each:

- A message sent mid-turn gets 409, so the UI sends it as the next message.
- Undo reports "Undo may not work for this turn", because file changes aren't recorded yet.
- The reply carries no context-window measurement.

"Always allow" is offered only for shell commands, and covers that program (`mkdir`), or program and subcommand (`git status`), or the exact text of a chained or piped command, in that chat only; the answers are kept in memory. A file write, web fetch or any other tool asks every time, because a grant for one file would otherwise approve every later write. A shell command that only reads runs without asking: `ls`, `cat`, `grep`, or `find` without `-exec` or `-delete`, chained or piped, with output thrown away by `2>/dev/null`. Under cmd.exe only the built-ins `dir`, `type`, `cd` and `echo` qualify, because cmd runs a `find.bat` in the current folder before the real `find`. `git` always asks, because a repository's own config can make `git status` run a program. With the internet off, the chat refuses `web_fetch` to other hosts, every MCP tool, and shell commands that go online, before any approval card. On Windows the shell is Git Bash when Git for Windows is installed, found next to `git.exe` if it isn't on `PATH`, and `cmd.exe` otherwise; the WSL launcher (`System32\bash.exe`) is never used, because it can't see `C:\` paths. The system prompt names the shell in use.

To try it, put the binary in `~/.gaia/agents/gaia/` with an `.installed` file naming it (`"artifact_kind": "binary"`, `"executable"` set to the file's name, `"artifact_sha256"` set to its SHA-256, and `"version"` set to `0.1.0` or later, since the daemon refuses to start a binary whose version it can't read). A local build names the file `gaiacpp.exe` (`gaiacpp` on Linux and macOS); the hub package from `cpp/packaging/package_agents.py` names it `gaia-win-x64.exe`, `gaia-linux-x64` or `gaia-darwin-arm64`. The Agent UI then relays to it whenever the Python `gaia_agent` package isn't importable in its environment.

## Running as the agent of the GAIA terminal UI

`gaiacpp --stdio` speaks the protocol the terminal UI uses with its agent child process: one line per message on stdin, one JSON event per line on stdout, and logs on stderr. The process stays up for the whole session, so the conversation, "always" answers and a switched model carry from one turn to the next. The wire names are pinned by `tests/fixtures/stdio/gaia_stdio_wire.json`, which the Python flagship and the terminal UI are tested against too.

```bash
printf '%s\n' '{"gaia_query": "What is in this folder?"}' | gaiacpp --stdio -m Qwen3.6-35B-A3B-GGUF
```

```json
{"type":"status","message":"","model_id":"Qwen3.6-35B-A3B-GGUF","model_display":"Qwen3.6-35B-A3B-GGUF","model_backend":"lemonade","model_remote":false,"lemonade_reachable":true,"lemonade_version":"…","lemonade_base_url":"http://localhost:13305/api/v1","agent_version":"…","gaia_version":"…"}
{"type":"status","message":"Thinking"}
{"type":"tool_call","tool":"bash_execute","args":{"command":"ls"},"narration":"Running ls"}
{"type":"tool_result","tool":"bash_execute","data":{"…":"…"},"preview":"…"}
{"type":"final","answer":"…","usage":{"steps":2,"input_tokens":2100,"cached_tokens":900,"tokens":60}}
```

**What it reads.** A line is a query: either `{"gaia_query": "text"}`, which keeps a multi-line question as one question, or any other text, taken as written. A JSON object with a `gaia_control` key is a control message instead. Controls are read on their own thread, so they take effect while a turn is running, and they never write anything to stdout.

| Control | Fields | Effect |
|---|---|---|
| `tool_decision` | `decision` (`allow`, `deny`, `always`, `timeout`), `confirm_id` | Answers the open approval. An answer for another `confirm_id`, or with nothing waiting, is dropped and the tool does not run. Without a `confirm_id` it answers the open approval |
| `full_access` | `enabled` | Approval prompts off or on, from the next tool call |
| `accept_edits` | `enabled` | File edits inside the working directory run without asking |
| `cancel` | | Stops the running turn, which still ends with its one terminal event. A query that was read but hasn't started ends at once with an empty `final`. `/model` and the sentinel queries run to completion once started. The process and the conversation stay |
| `clear_history` | | Forgets the conversation after the running turn |

A control with a field of the wrong type is rejected with a line on stderr and changes nothing, except that an unreadable `tool_decision` denies the approval it was meant for.

**What it writes.** Only these event types: `status`, `token`, `tool_call`, `tool_result`, `needs_confirmation`, `final` and `error`. Every query ends with exactly one `final` or `error`, and nothing follows it until the next query.

- The first line, and the line before the `final` of a successful `/model <id>`, is a `status` naming the model: `model_id`, `model_display`, `model_backend` (`lemonade`, or `fireworks` / `amd` for a cloud model), `model_remote`, `lemonade_reachable`, `lemonade_base_url`, `lemonade_version` when the server reports one, `agent_version` and `gaia_version`. It is sent even when no model server answers, after waiting a few seconds at most.
- `token` events carry the answer as it streams, when the model calls tools natively. Otherwise the answer arrives whole in `final`. Reasoning inside `<think>` tags is left out.
- `needs_confirmation` carries `run_id`, `action` (the tool), `summary`, `confirm_id`, `risk` (`read`, `write` or `execute`) and, for a shell command only, `always_scope` (what an `always` answer would cover). Without `always_scope`, "always" isn't on offer, and an `always` answer allows that one call.
- A turn the model server could not answer ends in `error`. A cancelled turn ends in a `final` with an empty answer.

**Queries it answers itself.** `/model` lists the models the server can run now, and `/model <id>` switches to one, or ends in `error` and keeps the current model. The `model_id` it reports is the server's own spelling, so `Foo` becomes `user.Foo` when that is how the server lists it. Three sentinel queries never reach the model:

| Query | `final` answer |
|---|---|
| `"\u0000gaia:clear_conversation\u0000"` | `conversation_cleared`, with the history forgotten |
| `"\u0000gaia:memory_dump\u0000"` | The stored memories as a JSON string: `available`, `stats`, `contexts`, `shown`, `total`, `items`. With `--no-memory`, `available` is false and `reason` says why |
| `"\u0000gaia:warm_up\u0000"` | `warmed_up` once a local model is loaded, `warm_up_skipped` for a cloud model. A model that can't be loaded ends in `error` |

**Approvals.** A shell command that changes something, a file write or edit, a web fetch and an MCP tool that isn't known to be read-only ask first. `always` is offered for shell commands only and remembered until the process exits: the program for single-purpose commands (`mkdir`), program and subcommand for tools such as `git` and `npm`, and the exact command otherwise. Every other tool asks each time, so approving one file write never approves the next. With "accept edits" on, `file_write` and `file_edit` run without asking when the file is inside the working directory. They still ask for anything under `.git`, a dotfile or dot-folder, a folder on `PATH`, and on Windows a file `cmd.exe` would run in place of a program on `PATH`; a home folder or a drive root never counts as the working directory. 

**When the host goes away.** Once stdin closes, queries already read still run while something reads stdout, so `echo '{"gaia_query": "hi"}' | gaiacpp --stdio` prints its answer, and an approval nobody can answer is denied. When stdout has no reader either, or a write to it fails, the process exits at once with code 0, without waiting for a model call or a tool in flight. Commands the agent runs never get its stdin: they read end of input.

**Flags.** Besides the model and run options above, `--stdio` takes the flags the terminal UI passes: `-m/--model`, `--full-access`, `--accept-edits` and `--dev` (step-by-step `status` events, debug lines on stderr). `--accept-edits` and `--dev` are refused without `--stdio`. The endpoint comes from `LEMONADE_BASE_URL`, as in every other mode.

- With `--stdio`, `--full-access` means approval prompts are off. The tools stay inside the working directory; add folders with `--allow-dir`.
- `--use-claude` and `--claude-model` stop the program with exit code 2, because `gaiacpp` has no Claude provider.
- `GAIA_LEMONADE_EMBEDDED=1` is not acted on: `gaiacpp` keeps the `LEMONADE_BASE_URL` it started with, so if GAIA's own model server restarts on another port, turns end in `error` until the terminal UI restarts the agent.

The terminal UI does not start `gaiacpp` by itself yet: it looks for a program named `gaia-agent` and does not pass `--stdio`.

## Lemonade integration

Lemonade's agent host installs agents from a pinned GitHub release asset, configures them for the local server, and launches them (see Lemonade's `docs/guide/agents.md`). `gaiacpp` provides what that contract needs:

| Lemonade needs | gaiacpp provides |
|---|---|
| A release asset per platform, binary at the archive root, pinned by SHA-256 | `cpp/packaging/package_lemonade.py` builds `gaiacpp-<os>-<arch>.tar.gz` (`.zip` on Windows) and writes its checksum entry to `agent_versions.gaia.json`, to copy into Lemonade's `agent_versions.json`. `build_agents.yml` runs it for each platform, and on a release tag joins the three files into one with `--merge` |
| Point the agent at this server, without writing the key to disk | The settings file (`baseUrl`, `modelId`, `contextSize`). When lemond has a key, the host adds `apiKeyEnv: "LEMONADE_API_KEY"` and passes the key in the environment; without one it leaves `apiKeyEnv` out |
| Lemonade's tools in the agent | `mcpConfig` naming Lemonade's MCP server by URL |
| A launch command for a terminal | `gaiacpp -m <model>` (interactive) |
| A served agent | `gaiacpp serve --port 0 --server-key-env <VAR>`, ready line on stdout, `GET /health` for readiness |
| No surprise upgrades | `--version`; the binary has no self-update |

The release build links OpenSSL statically on every platform and, on Linux, the C++ runtime too (`GAIA_STATIC_CXX_RUNTIME=ON`), so the Linux binary needs only glibc from the system. A build made without OpenSSL has no HTTPS: it can't reach an `https://` endpoint or install skills from the hub. glibc is the floor of the build host, so build Linux releases on the oldest distribution you support (CI uses `ubuntu-latest`).

## What the agent loop handles

- **Tool protocol:** native tool calls for every model GAIA lists and for any model Lemonade labels `tool-calling` (cloud models included); other models are asked for the call as JSON in text. `--native-tools always` or `never` overrides this.
- **A model already loaded:** before each request the agent checks that its model is loaded at its context size and loads it if not. Speech, transcription and embedding models loaded beside it don't trigger a reload, and a cloud model is never reloaded.
- **Knows what is in the folder:** the prompt lists the working folder two levels deep (up to 60 names, hidden files left out) as it was when the turn began, so a small model reads the files that are there in place of guessing names. The home folder and a drive root are not listed.
- **A reply cut off at its limit:** when the model spends its whole reply limit before answering, the turn ends saying so and naming `--max-tokens` (default 16384).
- **Transient failures:** connection errors and HTTP 408, 409, 425, 429 and 5xx are retried with exponential backoff (`llmRetries`, default 3). Other errors fail the turn with the server's message.
- **Full context window:** on an overflow error, older tool outputs are replaced with references and the request is sent once more.
- **Large tool output:** output beyond `maxToolResultChars` (default 16000) keeps its head and tail in the conversation; the model reads the rest with `read_tool_output`.
- **Malformed tool calls:** invalid arguments are returned to the model to resend, up to three times in a row. Whole-string numbers and `"true"`/`"false"` are converted to the declared parameter type.
- **Loops:** the fourth identical call in a row is refused with a note asking the model to change course; a second loop ends the turn.
- **Step budget:** the model is told when few steps remain (default budget 50). At the limit, one call without tools asks for an honest summary of what was done and what wasn't.
- **Claims checked against what happened:** an answer is sent back once when it says it saved a file that doesn't exist, that tests or a command ran when no command ran, or that something is missing when the agent never looked. Agents built on the framework add their own checks by overriding `reviewFinalAnswer()`, using `turnToolCalls()`.
- **"Always allow" is scoped:** in the interactive session, always allowing a shell command covers that program (`pytest`), or program and subcommand (`git status`), or the exact text of a chained or piped command, never every shell command.
- **Reasoning text:** `<think>…</think>` blocks never reach the answer. A reply that is empty, for example reasoning cut off by `maxTokens`, is asked for once more.
- **Cancel:** `requestCancel()` (Ctrl+C, or a server client disconnecting) stops the run at the next step, and mid-stream when the agent streams (`GAIA_STREAMING=1`). A second Ctrl+C exits at once, for a model call or tool that won't return.
- **Web access:** `web_fetch` follows redirects itself and refuses any hop that resolves to a loopback, private, link-local or metadata address, so a page can't steer the agent at Lemonade or other local services. `GAIA_WEB_FETCH_ALLOW_PRIVATE=1` allows the local network, and `--no-web` leaves the tool out.
