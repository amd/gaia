## Credential storage

GAIA never writes tokens or API keys to plaintext files. Your OS credential store protects a single 32-byte AES-256-GCM master key (`gaia.connections` / `vault-master-key`), which unlocks an encrypted `0600` vault file at `~/.gaia/connectors/vault.enc` holding OAuth refresh tokens, OAuth client credentials, cloud/gateway API keys, Slack and Discord bot tokens, and the browser session key:

| Platform | Store |
|---|---|
| macOS | Keychain |
| Linux | gnome-keyring or kwallet |
| Windows | Credential Locker |

Keeping one master key in the OS credential store avoids prompting once per saved secret when an unsigned macOS build updates. Existing per-slot OS keyring entries are copied into `vault.enc` on first read; after that GAIA reads them from the vault only. Deleting the last entry in `vault.enc` removes both `vault.enc` and `vault-master-key`.

**Transition release.** This release keeps the old per-slot keyring entries you already had, so downgrading GAIA or running an older agent build that reads them directly still finds you connected. When you sign in, save an API key, or set up messaging, GAIA also updates the old entry for that secret, but only if the secret was copied from one and its value changed. Background token refreshes update `vault.enc` only, so they never raise a credential-store prompt; after a downgrade, an account whose token rotated since your last sign-in may ask you to sign in again. A fresh install never creates old-style entries. The next release stops updating them and removes them; downgrading past that point means signing in again.

**macOS trade-off.** Before the vault, macOS asked separately for each saved secret, so you could approve one connection and decline another. Now one approval of the master key unlocks every secret GAIA's Python processes keep in the vault (connector sign-ins, cloud and gateway keys, Slack and Discord tokens, the browser session key). MCP server keys are not in the vault and are still approved one by one.

keyring's `null` backend stores nothing, so on it saving any of these secrets fails with an error instead of appearing to succeed. Where no credential store exists, supply the secret through its environment variable.

The `vault.enc` envelope format (version 1) is fixed for cross-runtime compatibility: 6-byte magic `GAIAV1`, 1-byte version (`0x01`), 12-byte random nonce, and AES-256-GCM ciphertext plus 16-byte tag over UTF-8 JSON `{"entries":{"<slot>":"<value>"},"v":1}` with associated data `gaia.connections:vault:v1`.

GAIA refuses a plaintext or weakly encrypted keyring backend (`keyrings.alt`'s `PlaintextKeyring`, `EncryptedKeyring`, `Win32CryptoKeyring`, or anything derived from them) before every read and write — for connector tokens, API keys, Slack and Discord bot tokens, the browser session key, MCP server secrets and Agent Hub publisher tokens alike. If keyring chains several backends, every one of them is checked, and a chain GAIA cannot fully inspect is refused. Deleting a secret still works on such a backend, since it only reduces what is exposed: GAIA removes it and logs a warning to switch backends. That includes disconnecting a Google or Microsoft account, with one difference: revoking GAIA's access at the provider needs the stored token, which GAIA will not read there, so the disconnect removes the account from this PC only and tells you to remove GAIA from your account's app permissions page ([Google](https://myaccount.google.com/permissions), [Microsoft personal](https://account.live.com/consent/Manage), [Microsoft work or school](https://myapps.microsoft.com)). To fix the error, install a system credential store (gnome-keyring or kwallet on Linux), or point `PYTHON_KEYRING_BACKEND` at one, and restart GAIA.

On macOS, the GAIA daemon reads the keychain for the flagship agent, using a credential only that agent receives. The keychain ties approval to the exact build asking, so this keeps agent updates from prompting again. The trade-off: when macOS asks, **Always Allow** now approves the daemon's Python interpreter, not the agent, and any script that same interpreter runs can then read these items without a prompt. An agent started without the daemon reads the keychain itself.

MCP server tokens stay directly in the OS keyring under `gaia.connections:<connector-id>:<secret-name>` so both Python and the native C++ runtime (`gaiacpp`) resolve `$keyring:<slot>` references in `~/.gaia/mcp_servers.json` — the JSON file itself contains no actual secrets.

OAuth refresh tokens, API keys, and messaging tokens are AES-256-GCM encrypted at rest in `vault.enc` under the OS-keyring-protected master key and decrypted in memory only when needed; MCP server API keys are encrypted at rest by the OS keyring.

## Per-agent grant + activation model

Connecting a service does **not** give every agent access to it. Access is gated at up to three levels depending on connector type:

1. **Connection** — you store a credential once in the keyring (OAuth refresh token or PAT).
2. **Grant** — you explicitly allow a specific agent to use that credential for a specific scope. Gates **credential access** (`get_access_token`). Applies to every connector type.
3. **Activation** — you explicitly enable a specific agent to *see* an MCP server's tools in its system prompt. Gates **MCP tool visibility**. Defaults to OFF — least-privilege opt-in. **Applies to `mcp_server` connectors only.** The one exception is an MCP server you added to `mcp_servers.json` yourself: writing the entry was your opt-in, so GAIA (`installed:gaia`) can use it until you turn it off; other agents still need an activation.

```
User → connects mcp-github once                   (credential)
User → grants chat-agent the GitHub PAT scope     (credential access)
User → activates chat-agent for mcp-github        (MCP tool visibility)
```

OAuth connectors (e.g. Google) reach the provider through native Python `@tool` functions that call `get_credential_sync` directly — there is no MCP tool surface for activations to gate. Per-agent control for OAuth is handled entirely by the per-scope grant toggles. Calling `activate()` / `deactivate()` for an OAuth connector raises `ConfigurationError`; the HTTP route returns `400 Bad Request`; the CLI exits with code 3.

An agent that calls `get_credential_sync("google", agent_id=..., required_scopes=["gmail.readonly"])` without a matching grant receives `AuthRequiredError(reason=AGENT_NOT_GRANTED)` and cannot proceed. No token is ever returned to an ungranted agent.

Without an activation, an MCP connector's tools never enter the agent's tool list — they don't bloat the system prompt, and the agent cannot select them even if it has a grant.

Grants are stored in `~/.gaia/connectors/grants.json` and activations in `~/.gaia/connectors/activations.json` — both flat files that are **not** secret stores. They contain agent IDs and scope/boolean values, never credentials.

When a grant is requested during OAuth connect, GAIA records only the
intersection of the agent's requested scopes and the scopes the token endpoint
actually grants.

The connection record itself is the opposite: it stores exactly the scope set the
token endpoint returned, including scopes granted by an earlier connect that
Google folds back in. The record therefore states what the refresh token can do,
while grants state what each agent may use it for.

## Revocation

You can revoke access at any level:

| Action | Effect |
|---|---|
| Settings → Connectors → \<connector\> → **Disconnect** | Removes token from keyring AND clears all grants AND all activations for that connector; all agent calls fail with `NOT_CONNECTED`. An OAuth connector with several accounts asks which one to remove (or all); grants are cleared only when the last account goes. GAIA also revokes its access at the provider where the provider allows it; when it can't (Microsoft, or a keyring GAIA refuses to read), the result says so and where to revoke by hand |
| `gaia connectors grants revoke <connector> <agent>` | Removes the per-agent grant; that agent's calls fail with `AGENT_NOT_GRANTED` |
| `gaia connectors activations deactivate <mcp-server-connector> <agent>` | Turns the per-agent activation off; that agent stops seeing the MCP server's tools but the grant survives so re-activation is one click. Only valid for `mcp_server` connectors, including a server you added to `mcp_servers.json` yourself |
| Revoke the PAT/OAuth client at the provider | Invalidates the token at the source; GAIA's next API call surfaces the provider's error |

## Threat model

| Threat | Mitigation |
|---|---|
| Malicious process reads `mcp_servers.json` | File contains only `$keyring:...` references, never raw tokens |
| Malicious agent requests a credential it wasn't granted | `get_credential_sync` checks the grants ledger before returning; unapproved calls raise `AuthRequiredError` |
| Agent code runs a tool in its own thread and loses its identity | The runtime copies the calling context into every tool thread; a credential request inside an agent turn with no identity is refused, never treated as an un-scoped CLI call |
| Grant ledger written with scopes the connector never advertised | `grant_agent` rejects any scope outside the connector's catalog entry and any unknown connector id, so the Agent UI, the CLI, and the SDK share one ceiling |
| Connector re-added after disconnect silently inherits prior tool visibility | `disconnect` wipes both grants AND activations for that `connector_id`; re-adding requires explicit re-grant + re-activate |
| Token leak via logging | Connector code never logs token values; credentials are redacted before any log statement |
| Token exfiltration via a rogue custom agent | Custom agents run in the same process as GAIA — they are trusted code you install yourself, analogous to a browser extension |
