# Releasing the flagship GAIA agent (frozen binary + npm)

How the flagship agent — a frozen, no-Python REST sidecar plus the `@amd-gaia/gaia`
npm launcher — reaches GAIA's download server (`hub.amd-gaia.ai`) and npm, via the
tag-triggered CI release. The pieces: `hub/agents/gaia/python/` +
`hub/agents/gaia/npm/` + `.github/workflows/release_agent_gaia.yml` (its header
comments are the contract of record).

This is a **phased process with one hard human gate** (the `agent-publish`
environment). Stop and confirm before anything irreversible — pushing a release
tag, approving the publish gate. Publishes are **immutable per filename**: a bad
release is fixed by a new version, never an overwrite.

## Scope

This is maintainer release tooling, not a user-facing product: GAIA ships one
agent (the flagship) through two apps, the TUI and the Agent UI, and there is no
public agent catalog to publish into. The standalone email agent that once shared
this pipeline was removed (#4825).

## Distribution model (the mental picture)

```
freeze.py (PyInstaller, native per-OS, no cross-compile)
   └─ gaia-agent-<platform>[.exe]   ← one-file binary, boots the REST sidecar
        └─ POST /publish  →  download-server Worker (workers/agent-hub/) ── R2 bucket "gaia-hub"
             • stores each object IMMUTABLY under agents/gaia/<ver>/<file>
             • computes SHA-256 server-side
             • rebuilds index.json (what `gaia init` and the daemon read)
             • the Linux sidecar is past the Worker's body cap: PUT straight to R2,
               then published by reference
        download = plain public GET at hub.amd-gaia.ai/agents/gaia/<ver>/<file>
   └─ terminal UI — CONSUMED, not built: the `terminal-hub` component that
        release_components.yml publishes at agents/terminal-hub/<ver>/
   └─ @amd-gaia/gaia (npm)  ← launcher: fetch + verify both binaries, start the TUI
        • binaries.lock.json (schemaVersion 3.0) carries one lane per component,
          each with its own version, baseUrl and per-platform sha256 + size
        • published via npm OIDC trusted publishing (provenance, NO npm token)
```

The Worker fronts the bucket; CI POSTs to `/publish` so uploads are
server-checksummed and the catalog is rebuilt atomically. The manifest rides along
inside the publish.

## What the package carries

| Path | Role |
|------|------|
| `hub/agents/gaia/python/packaging/` | `freeze.py`, `smoke_test.py`, `server.py`, `gen_binaries_lock.py`, `publish_to_r2.py`, `stamp_version.py`, `gen_scorecard.py` |
| `hub/agents/gaia/npm/package.json` | the `@amd-gaia/gaia` launcher |
| `hub/agents/gaia/npm/binaries.lock.json` | two lanes (sidecar + terminal-hub) → artifact + **sha256** + size + `baseUrl` |
| `hub/agents/gaia/npm/{README,SPEC,SKILL,CHANGELOG,SCORECARD}.md` | integrator docs, kept in sync per CLAUDE.md |
| `.github/workflows/release_agent_gaia.yml` | the tag-triggered release |
| `.github/workflows/build_flagship_sidecar.yml` | the per-platform freeze matrix, shared with `publish.yml` |

Notes:
- **Manifest validation:** validate `gaia-agent.yaml` with `gaia agent test
  --lint`. Do **not** validate it against
  `workers/agent-hub/schemas/manifest.schema.json` — that is the Hub's *server-side
  aggregate* schema and requires fields you never hand-write (`versions`,
  `latest_version`, `deprecated`, `security_tier`, `permissions`).
- **Platform-name skew (easy bug):** the manifest's `requirements.platforms` uses
  `win-x64`; `binaries.lock.json` and the CI matrix use `win32-x64`. Don't copy
  one into the other.

## The three version numbers the release checks

The `version` job fails loudly unless all three are identical, and runs before
any freezing:

1. the **tag** (or `workflow_dispatch` input) — `agent-pkg-gaia-v<version>` → `<version>`
2. `hub/agents/gaia/npm/package.json` → `.version`
3. `hub/agents/gaia/python/gaia-agent.yaml` → `version`

Bump with **`gaia agent version patch|minor|major --path hub/agents/gaia/python`**.
It bumps from the `gaia-agent.yaml` value, rewrites `pyproject.toml` and the
package's version, then runs `packaging/stamp_version.py`, which moves the npm
`package.json`, `package-lock.json` and `binaries.lock.json`, and then `--check`s.
If any file can't be moved, the command fails and names it. The lock's hashes are
**regenerated by CI** — don't hand-edit them.

## Cutting a release

1. **Version-bump PR → main.** `gaia agent version <bump>`, add the CHANGELOG
   entry, merge to `main` (publishing is allowed only from a `main` ancestor).
2. **Pre-flight** in `hub/agents/gaia/npm/`: `npm ci && npm run build && npm
   test`, and `npm pack --dry-run` to confirm the docs ship. Before any publish,
   `python util/verify_publish_pipeline.py` proves the publisher against a local
   Worker (see `docs/reference/dev.mdx`).
3. **Tag from main** (or `workflow_dispatch` with the version):
   ```bash
   git tag agent-pkg-gaia-v<version> && git push origin --tags
   ```
   Namespace is `agent-pkg-gaia-*` (NOT `v*`) — it deliberately does not fire the
   core `publish.yml`.
4. **Freeze** on 4 platforms — `win32-x64`, `darwin-arm64`, `linux-x64`
   **required**; `darwin-x64` (Intel) **best-effort** — smoke-test each, hash it.
   The `tui` job proves the pinned `terminal-hub` version is published and
   cross-checks its six artifacts against the hub's own SHA-256; a missing version
   fails the release, with no fallback build.
5. **Gates:** `tests` (Python suite + npm vitest) and `scorecard-gate` (parses
   `hub/agents/gaia/npm/SCORECARD.md`, bar from
   `tests/fixtures/gaia/quality_gate_thresholds.json`, regression vs the previous
   `agent-pkg-gaia-*` tag) block publish. `gaia-eval` runs a judged subset on
   self-hosted hardware and only reports.
6. **Approve the gate.** `publish` pauses on the `agent-publish` environment until
   a maintainer approves; the publish secrets aren't readable until then.
7. **Publish** (atomic): upload the sidecars → regenerate `binaries.lock.json` with
   the **real** hashes for both lanes → **fetch-verify every entry** at the public
   origin → `npm publish` via OIDC → trigger `deploy_website.yml`.
8. **Merge the lock PR.** `pin-lock` opens a PR committing the verified lock to
   main (branch `flagship-lock/v<version>`), because the installer build and the
   final core release read the committed copy. Merge it before tagging the core
   release; don't pin hashes by hand. Re-running the job is safe.

Monitor with `gh run watch`. The npm step goes through `util/npm_publish_once.py`:
it skips a version already on npm with the same tarball, fails if npm holds
different bytes under that version, and refuses a prerelease version. `/publish`
is a verified 409 no-op for identical bytes, so a failed run is safe to re-run with
`gh run rerun <run-id> --failed`.

## One-time infrastructure (verify it exists)

Per the workflow header, these are **maintainer setup** — confirm each before a
release:

- **GitHub environment `agent-publish`** with **required reviewers**; restrict its
  deployment branches/tags to `main` **and** the `agent-pkg-*` tag pattern (a
  main-only rule blocks the tag-triggered gate).
- **Secret `GAIA_HUB_TOKEN`** — download-server Bearer token matching an entry in
  the Worker's `PUBLISH_TOKENS`, scoped to the `AMD` author. An **environment**
  secret on `agent-publish`, not a repo secret. (The publish script reads it as
  `AGENT_HUB_PUBLISH_TOKEN`.)
- **Secrets `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `CLOUDFLARE_ACCOUNT_ID`** —
  required every release, because the Linux sidecar goes straight to R2. Same
  environment-secret placement.
- **Var `GAIA_HUB_BASE_URL`** — public Worker origin for downloads and the lock
  `baseUrl` (default `https://hub.amd-gaia.ai`).
- **Var `GAIA_HUB_PUBLISH_URL`** — the Worker's **workers.dev** URL for uploads; the
  WAF on the `hub.amd-gaia.ai` custom domain 403s large uploads. **Required** — the
  release fails loudly if it is unset.
- **npm trusted publisher** for `@amd-gaia/gaia`, registered against the exact
  filename `release_agent_gaia.yml`. ⚠️ Renaming the workflow breaks publish.
- "Allow GitHub Actions to create and approve pull requests" stays on, so
  `pin-lock` can open its PR.

## Invariants & gotchas

- **Immutable per filename.** The Worker `409`s on any re-POST of an existing
  filename. The publish script then re-fetches and hashes the stored object:
  identical bytes → idempotent no-op, a hash mismatch → fail loudly.
- **Publish only from main.** The job asserts the release commit is on `main`.
- **Best-effort Intel.** If `darwin-x64` fails or is absent it is **dropped** (a
  3-platform release) with a loud `::warning::`; Intel users get a clear "no
  binary" install error, never a placeholder.
- **SHA-256 provenance.** `publish_to_r2.py` hashes each binary locally and asserts
  the Worker's server-side hash matches before writing it to the lock. The lock
  hash is then the gate the install-time fetcher enforces.
- **Fetch-verify is the real gate.** After `/publish`, CI re-fetches every object
  and checks bytes-hash-to-lock (bounded retry for edge propagation) before
  `npm publish`.
- **Website is rebuilt, not patched.** The publish job triggers
  `deploy_website.yml` on `main`.
- **Write the CHANGELOG entry, PR body, and your status reports** per [CLAUDE.md → How You
  Communicate](../../../CLAUDE.md#how-you-communicate): lead with what changes for someone
  installing the agent, put versions, hashes, and workflow mechanics underneath. Always say
  which platforms actually shipped — a dropped Intel build is the headline, not a footnote.
