# GAIA Installer

This directory holds everything that goes into producing and running GAIA's install-time artifacts: build scripts, platform-specific installer assets, and release helpers. It was created as part of the [desktop installer plan](../docs/plans/desktop-installer.mdx).

The architectural inspiration for this layout is Lemonade Server's installer tree: <https://github.com/lemonade-sdk/lemonade>. That project keeps a single `installer/` directory as the source of truth for NSIS, DEB, macOS, and Linux packaging, and GAIA follows the same shape so the two codebases stay easy to cross-reference.

## Layout

```
installer/
├── README.md      ← you are here
├── scripts/       build + bootstrap scripts (PowerShell, POSIX sh, Node)
├── version/       version normalization and bump helpers (Node)
├── nsis/          NSIS assets: the Agent UI's electron-builder include, the
│                  developer shareable build, and the shared icon/sidebar
├── debian/        Debian packaging metadata for the Agent UI (postinst, prerm, postrm)
├── macos/         DMG layout, entitlements, icon for the Agent UI
├── linux/         AppImage/DEB icon for the Agent UI (the .desktop entry is
│                  generated by electron-builder)
├── tui/           the one Windows GAIA setup (desktop app and/or terminal),
│                  and the Terminal UI's macOS .pkg and DEB/RPM — see
│                  [`tui/README.md`](tui/README.md)
├── headless/      the installer journeys CI runs on clean runners (below)
└── install_time_thresholds.json   measured install-time limits for those journeys
```

### Which installer is which

| Who | Installer | Source |
|---|---|---|
| Users on Windows | `gaia-<version>-win-x64-setup.exe` — one installer; the user picks the desktop app, the terminal, or both | `tui/nsis/gaia-setup.nsi`, built by `windows_setup.yml` |
| Users on macOS / Linux | the Agent UI `.dmg` / `.deb` / `.AppImage`, and the terminal's `.pkg` / `.deb` / `.rpm` | `electron-builder.yml`; `tui/` |
| Developers | `install.ps1` / `install.sh`, `pip`/`uv`, npm, or a [shareable build](../docs/deployment/shareable-build.mdx) | `scripts/`; `nsis/gaia.nsi` |

The Agent UI's own electron-builder installer (`nsis/installer.nsh` is its
include) still builds every release: the Windows setup embeds it unchanged as
its desktop app component, and electron-updater re-runs it to update the app.

`nsis/gaia.nsi` is the developer shareable build. It puts its own `gaia-tui`
on PATH under its own "GAIA" Installed-apps entry, so the GAIA setup refuses to
install beside it rather than leave two of each.

`debian/`, `macos/` and `linux/` back the Agent UI's Electron packaging.
`tui/` is a separate, self-contained set of installers for the Go terminal
hub (`gaia-tui`) and the flagship agent sidecar it bundles — see its own
README for the per-platform builders and payload-staging steps.

## `scripts/` — bootstrap and build scripts

| Script | Purpose |
|---|---|
| `install.ps1` | One-shot Windows installer pulled via `irm https://amd-gaia.ai/install.ps1 \| iex` |
| `install.sh` | One-shot Linux/macOS installer pulled via `curl -fsSL https://amd-gaia.ai/install.sh \| sh`. POSIX `sh` only — the one-liner pipes into `sh`, which is `dash` on Debian/Ubuntu, so bash-only syntax breaks there. |
| `build-gaia-installer.ps1` | Package the two GAIA binaries into a single shareable Windows `.exe` |
| `build-ui-installer.ps1` / `.sh` | Build the Electron Agent UI installer locally |
| `start-agent-ui.ps1` / `.sh` | Launch the Agent UI (backend + frontend) during development |
| `start-lemonade.ps1` | Launch a local Lemonade Server for development and CI (Windows). On Linux, build the argv with `gaia.llm.lemonade_launcher.build_start_command` — see `test_gaia_cli_linux.yml` |

### What the one-line installers download

Both scripts install the `amd-gaia[api]` package from PyPI, the terminal binary
(`gaia-<os>-<arch>`) from a GitHub release checked against that release's
`gaia-tui-SHA256SUMS.txt`, and the GAIA agent (`gaia-agent`). Nothing installs
without a matching SHA-256, and there is no fallback source.

`GAIA_RELEASE_TAG` picks the release, and pins all three to it:

| `GAIA_RELEASE_TAG` | Core package | Terminal binary | GAIA agent |
|---|---|---|---|
| unset | latest `amd-gaia` | latest release | Agent Hub (`hub.amd-gaia.ai`), as `gaia init` |
| `v0.25.0` | `amd-gaia==0.25.0` | that release | Agent Hub |
| `v0.25.1-rc2` | `amd-gaia==0.25.1rc2` | that pre-release | frozen on that pre-release (`gaia-agent-release.json`), as an RC core installs it |

Any other value fails before anything installs.

```bash
curl -fsSL https://amd-gaia.ai/install.sh | GAIA_RELEASE_TAG=v0.25.1-rc2 sh
```
```powershell
$env:GAIA_RELEASE_TAG = "v0.25.1-rc2"; irm https://amd-gaia.ai/install.ps1 | iex
Remove-Item Env:GAIA_RELEASE_TAG   # or the next run pins it too
```

### Building the GAIA terminal installer locally

This is the one you send to a colleague: a single per-user `.exe` that installs
`gaia-tui` and the GAIA agent on a machine with no Python, no Go and no clone.

**[docs/deployment/shareable-build.mdx](../docs/deployment/shareable-build.mdx)**

### Building the Agent UI installer locally

Phase C landed, so `src/gaia/apps/webui/` builds with `electron-builder` driven by
`electron-builder.yml` — `forge.config.cjs` is gone. Build from that directory:

```bash
cd src/gaia/apps/webui

npm run package          # current host platform
npm run package:win      # or :mac / :linux
```

`npm run make` is kept as an alias for `npm run package`.

> **Note:** the `build-ui-installer.ps1` / `.sh` scripts in `scripts/` still shell out
> to `npx electron-forge package` / `make`, which no longer matches this tree —
> `electron-forge` isn't a dependency any more. Use the `package:*` npm scripts above
> until those two scripts are migrated.
> See [§7 Phase C](../docs/plans/desktop-installer.mdx) for the migration history.

## `version/` — version helpers

| Script | Purpose |
|---|---|
| `bump-ui-version.mjs` | Sync `src/gaia/apps/webui/package.json` with `src/gaia/version.py`. `python util/release_versions.py --stamp` does the same and stamps every other version field too; prefer it for a release bump. |
| `release-ui.mjs` | Release helper that tags and publishes a new Agent UI version. |

Typical usage:

```bash
# Verify package.json matches version.py (used in CI)
node installer/version/bump-ui-version.mjs --check

# Sync package.json to match version.py
node installer/version/bump-ui-version.mjs

# Full release flow
node installer/version/release-ui.mjs
```

See [`docs/plans/desktop-installer.mdx`](../docs/plans/desktop-installer.mdx) §8 for the full file-by-file layout and phase history.

## `headless/` — installer journeys on clean runners

[`test_installers_headless.yml`](../.github/workflows/test_installers_headless.yml)
installs each published installer on a fresh GitHub-hosted runner the way a user
would: silent install, a headless launch, a health check, uninstall, and a check
that nothing is left behind. It also runs an upgrade from the previous stable
release, and `install.sh` / `install.ps1` in a sandbox home. The workflow header
lists the rows and what "healthy" means for each. It runs on release tags, on
PRs that touch installers, install scripts or the download page, and on demand
(`gh workflow run test_installers_headless.yml -f release_tag=v0.25.1-rc2`).

| File | Purpose |
|---|---|
| `journey.py` | Runs a row's phases, times each with the monotonic clock, records results, and applies the gates below |
| `posix-journey.sh`, `windows-journey.ps1` | One phase of one row. They refuse to run outside GitHub Actions: they install and remove system packages |
| `fake_model_server.py` | A stand-in Lemonade, so the terminal can complete one real turn through the installed `gaia-agent` without a model |
| `resolve_release.py` | Picks the release under test and waits for its assets |
| `known_failures.json` | Filed installer bugs the journeys hit; each shows as `known #N` instead of failing, and fails again once it stops reproducing |
| `propose_thresholds.py` | Re-measures install times from recent runs and proposes new thresholds |

### Install-time thresholds

Install, first launch to healthy, upgrade and uninstall are each gated per row
by [`install_time_thresholds.json`](install_time_thresholds.json). Download time
is reported but not gated, because it measures the network, not the installer.
Every threshold comes from real runs: the file records each row's sample count,
median, p95, runner images and source run ids, and sets
`threshold = ceil(max(p95 × 1.5, p95 + 60 s))`. A row with no threshold yet
warns rather than passes.

Refresh it from data, never by hand:

```bash
python installer/headless/propose_thresholds.py --runs 5            # show proposed vs current
python installer/headless/propose_thresholds.py --runs 5 --write    # rewrite the file
```

Re-measure when a runner image changes, or when an installer change makes a
phase legitimately slower. Commit the regenerated file together with the reason.
